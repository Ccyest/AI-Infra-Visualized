## Background

A model computes keys and values, or KV, for the tokens it reads. During
generation, attention uses this KV to look back at the context. When another
request starts with the same token prefix, SGLang can reuse its KV and compute
only the new suffix. This reduces prefill work and time to first token, or TTFT.

The capacity of GPU memory limits that reuse. Conversations grow with every
turn, and more clients bring more histories. Once the cache fills up, a prefix
may be evicted just before the next request needs it. SGLang's HiCache retains
these prefixes in larger memory tiers. For that capacity to help, restoring a
prefix must cost less than recomputing it, and the restored state must be
sufficient to continue the model from that prefix.

HiCache first added CPU memory, then external storage. Later work extended
recovery to hybrid-model and draft state, and introduced a proposal to use host
memory only as a transfer buffer. The timeline places these changes in context;
the rest of the article follows the engineering problems they address.

## HiCache

### Design and mechanism

Keeping every reusable prefix on the GPU would compete with the memory needed
for active requests. HiCache therefore separates where a prefix is retained
from where the model uses it. GPU HBM is L1, CPU DRAM is L2, and external storage
is L3. The GPU still performs attention; lower tiers preserve data that would
otherwise be discarded. A cache controller backs up and reloads that data.

<StorageLocationViz client:visible lang="en" />

Suppose two requests start with the same document but ask different questions.
SGLang can reuse the document’s KV and compute only the new question.
HiRadixTree matches the shared prefix and tracks its local cache locations;
HiCache brings lower-tier copies back to the GPU when needed.

<CacheReuseViz client:visible lang="en" />

An L1 hit is ready to reuse. An L2 hit must be loaded into L1. An L3 hit must
first be fetched into L2, then loaded into L1. Only the parts missing from all
three tiers need recomputation. This is HiCache’s benefit: a prefix evicted
from GPU memory can still avoid recomputation if a lower tier retains it.
Reuse requires identical prefix tokens; similar meaning alone is not enough.

### Engineering overview

The hierarchy creates a path for retaining and recovering prefixes. Making that
path useful introduces several implementation problems:

- **Memory layout:** GPU computation and storage I/O prefer different data
  orders. How can both transfer paths stay efficient?
- **Overlapping data transfers and computation:** waiting for every layer's KV delays computation.
  Which transfers can run while the GPU is already working?
- **Cache policies:** prefetching and backup spend time, bandwidth, and capacity.
  When is waiting or saving another copy worthwhile?
- **Hybrid-model and draft state:** a token match can leave required history
  missing. What must travel with the prefix for recovery to be complete?
- **Host memory:** each instance has a private L2 pool. When L3 retains the
  history, how much data must remain in host memory?
- **Storage backends:** different systems expose different I/O implementations.
  How can they share HiCache's scheduling and recovery mechanisms?




















### Memory layout

This optimization handles the different KV layouts used by GPU computation and storage I/O. The GPU processes one model layer at a time, so its KV is grouped by layer for convenient access. External L3 storage reads and writes pages: for example, page 1 contains tokens 1–4 and page 2 contains tokens 5–8.

If Host keeps the same layout, transfers incur the overhead of many small copies, as shown in the diagram. With a page-first Host layout, a whole page can be transferred to external L3 storage at once, reducing the number of transfers and their overhead.

**HiCache therefore uses a page-first Host layout as an intermediate buffer.** It converts the layout during transfers, as shown in the diagram. Page 1 is highlighted: before, its pieces occupy separate Host regions; after, they sit together. Host → storage backup can read that contiguous region directly, and storage → Host recovery can fill it directly, reducing overhead.



<LayoutViz client:visible lang="en" />

On **GPU ↔ Host**, SGLang’s GPU-assisted I/O kernels achieve up to **3× the transfer throughput** of the standard `cudaMemcpyAsync` path. On **Host ↔ storage**, page-first layout enables large contiguous reads and writes; zero-copy lets the storage client access those blocks directly in the Host pool. Together, page-first and zero-copy deliver up to **2× the Host–storage throughput**.

### Overlapping data transfers and computation

The previous section explained how to make transfers faster. This optimization overlaps **Host → GPU transfers of cached KV** with **GPU computation on the new tokens**. We want the GPU to compute as data arrives instead of waiting through the transfer. HiCache therefore starts computation as soon as the first model layer’s KV is ready, while later layers’ KV continues loading.

For a three-layer model, first load the document’s layer-0 KV from Host to GPU. The GPU then processes the new question through layer 0, using that cached KV to attend to the document. At the same time, the transfer stream loads the document’s layer-1 and layer-2 KV.

This works because each model layer uses its own KV. Layer 0 can compute before layer 1's KV arrives. When computation reaches layer 1, it checks that layer 1's load has finished; if so, it proceeds immediately, otherwise it waits for that load. An L2 hit starts this Host → GPU process directly. For an L3 hit, storage first brings the KV into Host, after which the same overlap applies.

### Cache policies

Cache policies decide when to save KV and when to wait for it. Backup copies KV from GPU memory to Host so a later request can reuse it. Prefetch reads saved KV from L3 into Host before that request runs. Saving more data increases future reuse, but costs bandwidth and memory now; waiting for more data can avoid recomputation, but delays the request.

#### Prefetch

Suppose the GPU is processing request A when request B arrives. B needs a document whose KV is saved in L3. HiCache can start reading B's KV into Host while B waits for scheduling, overlapping that read with A's computation. When B gets its turn, it can load the KV already in Host to the GPU instead of starting the storage read then.

If B is ready to run but its L3 read is unfinished, the prefetch policy decides what happens next. Best-effort stops waiting, reuses the prefix already available, and recomputes the rest. Wait-complete keeps B waiting for the read to finish. Timeout gives the read more time, up to a limit, then proceeds with the available prefix.

<PrefetchViz client:visible lang="en" />

Waiting is useful when loading the missing KV takes less time than recomputing it. For a long cached document, a short extra wait can save substantial prefill work. When the storage read is much slower, recomputing can finish sooner. Prefetch tries to complete the read before this choice is necessary; the policy handles whatever wait remains.

#### Backup

A later request can hit Host memory only if the KV was backed up earlier. After the GPU computes a document's KV, HiCache can copy it to Host and, with L3 enabled, retain it in storage as well. A backup adds a copy in a lower tier. The GPU copy can remain until it is evicted. The same prefix KV can therefore coexist in L1, L2, and L3, although not every prefix always has three copies. Copying every cached prefix also spends bandwidth and memory on documents that nobody asks about again.

For GPU → Host backup, HiCache provides three choices:

| Policy | Backup timing | Main tradeoff |
| --- | --- | --- |
| Write-through | Proactively copy KV to Host when it enters the cache | Preserve more prefixes, with more backup traffic |
| Write-through-selective | Use hit counts to select hot prefixes for Host backup | Spend less bandwidth on rarely reused prefixes |
| Write-back | Defer Host backup until the KV is being evicted from GPU memory | Save the early copy, but add backup work at eviction |

For a frequently reused document, proactive backup leaves a Host copy ready after its GPU copy is evicted. Selective backup favors these hot documents over one-off inputs. Write-back keeps the KV on the GPU until eviction makes the backup necessary, trading less early backup traffic for work at eviction time.

### Hybrid-model state

Hybrid models may need sliding-window KV and recurrent state snapshots (checkpoints), alongside full-attention KV. [Unified Radix Cache](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/unified-radix-cache/#the-safe-reuse-boundary) checks that the required states are available and determines where computation can resume. HiCache backs up these states across Host and L3, then restores them to the GPU when needed.

#### Branch checkpoints

A new branch can need a checkpoint that did not exist when the KV was first backed up. In the diagram, Host holds the full-attention KV through P3 and checkpoint S0 at P3. A later request branches at the earlier position P2 and produces checkpoint S1 there. S0 already includes the tokens between P2 and P3, so the branch needs S1. A backup check that sees the existing Host KV and skips the node would miss this new checkpoint.

SGLang adds incremental checkpoint backup on the write-through path: keep the full-attention KV already in Host, and copy the newly created S1 separately. After S1 is evicted from GPU memory, a later request can restore it from Host and resume at P2.

<StateRestoreViz client:visible lang="en" />

The write-through recovery test builds new branch checkpoints, evicts them from the GPU, and requests the shared prefix again. Full recovery of the 6.4K shared prefix rises from **1/10 to 10/10 requests**; the token hit rate rises from **15.74% to 64.00%**. Each request has 6.4K shared tokens and 3.6K new tokens, so 64% means the entire shared prefix was recovered. See the [branch-backup test](https://github.com/sgl-project/sglang/pull/33639).

### Draft-state recovery

Speculative decoding uses a draft model to propose tokens and a target model to verify them. The draft can keep its own KV and other history buffers for the same document. If a cache hit restores only the target's data, the draft may have lost its history or be looking in the wrong memory slots. Its proposals can then become less likely to pass verification, even though the target successfully reused the prefix.

HiCache therefore backs up and restores the associated draft state in the same operation as the target state. With compatible layouts, it packs draft data into the matching target Host pool. Other layouts use a separate sidecar pool whose slots follow the target's KV or sliding-window slots. Both arrangements preserve which draft data belongs to each cached prefix through L2 and L3 transfers.

<DraftRestoreViz client:visible lang="en" />

The DSpark test runs the same 200 prompts on DeepSeek-V4-Flash-0731, first cold and then after restoring from L3. Before the fix, draft acceptance falls from **46.77% to 33.57%** on restore. After the fix, the two runs achieve **46.12% and 46.86%**. Restoring the draft's history keeps its proposals useful after a cache hit. See the [draft-recovery validation](https://github.com/sgl-project/sglang/pull/30393).

### Host memory as a buffer

Keeping a document's KV in Host gives the next request a fast L2 hit. But each serving instance has a private Host pool. In the diagram, instances A and B can each retain the same prefix P in Host, while shared L3 also holds a copy. Retaining more documents therefore keeps consuming each instance's Host memory even when L3 already stores them.

Buffer-only mode uses Host memory only while data is in transit. For backup, A copies P from GPU to Host and writes it to L3; once the transfer finishes and no longer needs the buffer, those Host slots can be reused. For recovery, B reads P from L3 into its Host buffer and loads it to the GPU, then releases the buffer. L3 retains P for future requests, while A and B reuse their Host slots for other transfers.

<HostModeViz client:visible lang="en" />

Host memory now needs room for the transfers in progress rather than a retained collection of documents. The tradeoff is that a future GPU miss must read L3 again instead of hitting a long-lived Host copy. A smaller Host buffer also holds fewer simultaneous transfers. Buffer-only saves retained Host copies by relying more on L3 reads.

### Storage backends

Suppose a deployment switches L3 from local files to Mooncake. Reading and writing KV now uses a storage service instead of file operations. But HiCache still needs to check for cached prefixes, start prefetches, schedule Host → GPU loads, and wait for the data before using it. These jobs should not need a new implementation for every storage backend.

HiCache separates storage access from cache scheduling. A backend implements how to check whether a key exists, read its data into Host, and write Host data to storage. The shared cache controller decides when to issue these operations and coordinates their completion. Mooncake, DeepSeek 3FS, and local files use this interface; NIXL connects storage systems through a transfer library.

Adding a backend therefore means implementing its storage access, while keeping HiCache's existing prefetch, backup, and GPU-loading flow. Deployments can choose where to retain their KV without building another cache scheduler.

## Results

Long inputs and multi-turn conversations can outgrow GPU memory. The following
benchmarks add CPU memory and external storage in turn, measuring how retaining
more history changes time to first token and input throughput.

### Long context · 2025

The original LooGLE evaluation tests whether lower tiers can avoid repeated
prefill for long inputs. It runs DeepSeek-R1 on eight H20-3e GPUs and compares
GPU-only caching, an added CPU L2, an added 3FS L3, and a separately prepopulated
L3. The chart shows average TTFT and input throughput.

<ResultsViz client:visible lang="en" />

With ordinary L3, input throughput is 51,168 tokens/s and average TTFT is
1.83 seconds. Filling L3 with reusable KV before requests arrive lets more
requests load cached prefixes immediately. Throughput reaches 76,322 tokens/s
and average TTFT falls to 1.43 seconds.

### Hybrid multi-turn workloads · 2026

Multi-turn conversations provide a growing working set: every round adds history
that later requests may reuse. The August 2026 evaluation compares GPU L1,
L1 plus CPU L2, and L1 plus L2 plus a 500 GiB Mooncake L3. DeepSeek-V4-Flash uses
FULL and SWA; Inkling-Small uses FULL, SWA, and MAMBA.

<MultiTurnBenchViz client:visible lang="en" />

L1 loses reusable history first, and L2 delays that capacity limit. Adding L3
raises DeepSeek-V4-Flash's effective input throughput from 9.4K to 145.5K tokens/s
relative to L1, with cache hits near 98%. Inkling-Small rises from 15.5K to 67.1K
and finishes at a 96.8% hit rate. These results show that lower tiers can preserve
reuse as hybrid-model conversation histories outgrow the smaller caches. See
the [multi-turn evaluation](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/).

Input throughput counts all input tokens served per second, including cached
tokens. Reusing a long prefix lets the service handle those tokens without
recomputing their KV, leaving more GPU time for new input.

## Summary

HiCache extends the lifetime of reusable prefixes beyond GPU memory. Its
engineering choices make that extra capacity usable: layout and loading reduce
transfer overhead, policies control when I/O is worthwhile, and component and
draft recovery preserve the state needed to continue inference. Host-buffer and
backend choices adapt the same hierarchy to deployment resources.

The combined benefit appears when saved prefill work exceeds recovery cost and
the lower tiers retain history that would otherwise be lost. The benchmarks
show that benefit for long inputs and growing conversations.
