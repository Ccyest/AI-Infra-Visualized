## Background

A model computes keys and values, or KV, for the tokens it reads. During generation,
attention uses this KV to look back at the context. If a later request starts with
the same token prefix, SGLang can reuse the corresponding KV and compute only the
new suffix. This saves prefill work and shortens time to first token, or TTFT.

The difficulty is keeping the old KV available. Long conversations take more space
with every turn. More clients add more histories. When the GPU cache fills up,
eviction can remove a prefix just before the next request needs it. A larger cache
helps only if loading the saved KV costs less than computing it again.

## Development timeline

The original hierarchical-cache proposal #2693 opened on January 1, 2025 and
merged on February 24. Storage integration followed in July. The 2026 work adds
new state types, speculative decoding, parallel layouts, and host-memory modes.
The timeline uses UTC merge dates into main; it distinguishes the merged MLA

## HiCache

### Design and mechanism

SGLang HiCache keeps reusable KV across GPU HBM, CPU DRAM, and external storage.
The GPU still performs attention. CPU memory and storage retain KV that would
otherwise be discarded, and the cache controller handles transfers between tiers.

HiRadixTree indexes the local cache by token sequence. Each node holds a token
segment and references to its KV in the GPU and CPU pools. Concatenating the
segments along a path gives the shared prefix. A GPU hit is ready to use; a CPU hit
needs a transfer to newly allocated GPU slots. If the prefix is absent locally,
the controller can query external storage using prefix-derived keys and prefetch
matching pages into CPU memory. A local tree miss does not by itself prove a
storage hit.

<CacheTreeViz client:visible lang="en" />

The diagram uses short token segments and arbitrary pool indices. For prefix
A → B, A is already on the GPU and B comes from CPU memory. For A → C, C starts
outside the local tree and appears only after a successful storage read. Backup
copies can coexist across tiers. Moving KV does not require deleting every copy
from the tier it came from.

### Storage backends

The 2025 design supports Mooncake, DeepSeek 3FS, NIXL, and a local file backend.
The backend supplies key lookup, reads, and writes; the central controller handles
scheduling and synchronization. NIXL is a transfer library that can connect to
other storage systems, so these backends should not be read as four equivalent
storage devices.

## Data movement

### Memory layout

A model consumes KV one layer at a time. GPU memory therefore keeps the
layer-first layout expected by its computation kernels. Storage I/O benefits from
larger contiguous transfers. HiCache gives the host pool a page-first layout,
placing one page's KV for different layers next to each other. The same data has
a different physical order on the two sides.

<LayoutViz client:visible lang="en" />

SGLang uses GPU-assisted I/O kernels for CPU–GPU movement. The blog reports up to
3× the transfer throughput of the standard `cudaMemcpyAsync` path. Page-first
layout together with zero-copy I/O reaches up to 2× higher throughput between
host memory and storage in typical deployments. These are improvements to
different transfer paths, not factors to multiply into an end-to-end speedup.
The Mooncake and 3FS changes are linked in the references.

### Layer-wise loading

A CPU hit does not need to wait for every layer's KV before computation starts.
Once layer 0 is loaded, the GPU can execute it while later layers are still being
transferred. Each layer must wait for its own KV, but it does not need the KV for
all later layers. This overlap can hide part of the transfer time.

<OverlapViz client:visible lang="en" />

The first load still takes time. If transfers are slower than computation,
later layers can still stall. The animation assumes fixed transfer and compute
durations to show the dependency; its timeline is not a hardware benchmark.

## Cache policies

### Prefetch

Storage latency is usually higher and less predictable than CPU–GPU latency.
HiCache starts prefetching into CPU memory while a request waits for scheduling.
Best-effort prefetch can stop when the request is ready to run, using the
available prefix and recomputing what is missing. Waiting longer can preserve
more reuse, but also delays the request. A timeout policy bounds that wait.

<PrefetchViz client:visible lang="en" />

The example treats the requested prefix as one indivisible block. Real requests
can reuse a completed prefix of a larger transfer. With fast storage, both
policies finish the read before scheduling. With a moderately late read,
waiting can avoid a larger recomputation. With very slow storage, waiting loses.
More cache hits alone do not guarantee a lower TTFT.

### Backup

Backing up every cached region spends bandwidth now to improve the chance of
reuse later. HiCache exposes three choices:

| Policy | Backup timing | Main tradeoff |
| --- | --- | --- |
| Write-through | Back up cached KV proactively | More retained data, more I/O |
| Write-through-selective | Use hit counts to back up hot regions | Less I/O, less coverage for cold regions |
| Write-back | Defer backup until eviction from the faster tier | Less early backup traffic, work on the eviction path |

The useful setting depends on transfer bandwidth and capacity in the lower tiers.
Adding storage does not remove those limits.

## Hybrid models

The sections above describe the original 2025 design. The following additions
cover merged work and public evaluations checked on September 11, 2026.

### More than full-attention KV

New models do not all retain the same kind of history. Full attention keeps KV
for the whole reusable prefix. Sliding-window attention only needs its trailing
window. A recurrent layer needs a state saved at the exact prefix boundary.
Saving Full KV alone cannot reconstruct that state without more computation.
SGLang's Unified Radix Cache puts these components on the same token tree, while
each component checks whether its own data is valid for reuse.

This extended HiCache to new combinations. Mooncake gained DSA and Mamba-state
storage in #21259, with Qwen3.5-9B and DeepSeek-V3.2-Exp validation. NIXL gained
hybrid side-pool storage in #29191, including Qwen3.5 recurrent state and DSA
indexer buffers. A storage backend must handle these additional buffers as well
as ordinary KV. The MAMBA component names a recurrent-state cache abstraction;
it does not mean every model using that component has the original Mamba architecture.

### Branch checkpoints

A shared prefix may already have Full KV in CPU memory when a new request creates
another recurrent-state checkpoint along that prefix. Treating the whole node as
already backed up would skip the new state. After GPU eviction, the Full KV could
be recovered but the new checkpoint would be missing. #33639 adds an incremental
backup of the newly available component, without copying Full KV again.

<StateRestoreViz client:visible lang="en" />

The PR verifies this by building shared prefixes, forcing them to Host, creating
new branch states, evicting again, and testing recovery. In its final ten-request
stage, full 6.4K-prefix hits rise from 1/10 to 10/10. This is a recovery result,
not a throughput measurement. The change initially covers write-through; it does
not establish the same incremental-backup behavior for write-back.

### Hybrid-model results

The August 2026 Unified Radix Cache evaluation compares GPU L1, L1 plus CPU L2,
and L1 plus L2 plus a 500 GiB Mooncake L3. It uses DeepSeek-V4-Flash with FULL and
SWA, and Inkling-Small with FULL, SWA, and MAMBA. The configurations and scales
differ between models, so compare tiers within each model.

<MultiTurnBenchViz client:visible lang="en" />

On DeepSeek-V4-Flash, effective input throughput increases from 9.4K to 145.5K
tokens/s with L3, and the hit rate stays near 98%. Inkling-Small reaches 67.1K
instead of 15.5K and ends at a 96.8% hit rate. These measurements include cached
input tokens in serving progress. They show the benefit of retaining growing
conversation histories, not a corresponding multiplication of raw GPU compute.

## Agents and speculative decoding

### Draft-state recovery

Speculative decoding uses a draft model to propose tokens for the target model
to verify. The draft can have its own KV, indexer, or sliding-window buffers.
Recovering only the target cache can leave draft state missing or mapped to the
wrong slots. A target-side cache hit can then coexist with a lower draft acceptance
rate. #30393 makes the matching target and draft state travel together.

SGLang uses two layouts. Compatible NextN MTP/EAGLE models and DeepSeek-V4 DSpark
append draft buffers to the corresponding target host pools. Standalone EAGLE,
DFlash, and other supported DSpark topologies use separate sidecar pools whose
indices follow target KV or SWA. Both paths attach the draft buffers to the same
L2/L3 operation. Inkling HiCache MTP is explicitly outside this PR's support.

<DraftRestoreViz client:visible lang="en" />

The chart uses the PR's cold-run and L3-replay validation on the same prompts.
After the change, replay acceptance remains close to the cold run instead of
falling after cache recovery. Acceptance rate is the measured outcome here;
these numbers are not an end-to-end throughput benchmark.

### DCP compatibility

Decode context parallelism, or DCP, partitions context KV across ranks. A rank's
physical cache rows no longer cover the entire logical index range. This matters
when a draft pool inherits target indices: allocating it from only the rank's
physical row count can make valid logical indices fall outside the host pool.

SGLang added DCP with HiCache L2 in #33112. #35221 then enabled the DSpark
combination and sized draft host pools for the target's logical capacity. The PR
validates Kimi-K3 with its DSpark draft on 8 B300 GPUs at TP8/DCP8, with 64/64
requests completing under eviction pressure. This establishes that tested
combination; it does not imply every speculative algorithm works with DCP.

### Session-aware eviction

An agent often returns to the same prefix after a tool call. Ordinary LRU knows
when KV was last accessed, but not whether an active session still needs it.
#29173 adds session references to Unified Radix Cache. GPU and host eviction
prefer unreferenced entries; referenced entries remain evictable if more space
is needed. Closing a session releases the reference without immediately deleting KV.

<SweBenchViz client:visible lang="en" />

The 2026 SWE-bench evaluation reports up to 16.6% lower TTFT for the session-aware
Unified configuration. The comparison changes both the tree implementation and
the eviction policy relative to ordinary HiRadixCache with LRU, so it is not an
isolated measurement of session references. This session policy covers L1 and L2,
not eviction inside the external L3 service.

## Host memory and storage

### Private L2 and shared L3

Each serving instance owns its GPU and CPU cache pools. Two instances on the same
machine do not automatically share one L2 cache. An external L3 can make stored
KV available across compatible instances. Increasing one instance's host-memory
budget only enlarges its own L2. The sharing boundary is made explicit in #37050;
#31920 also adds model-aware isolation for Mooncake keys. Matching token text
alone is not enough to make KV from different model configurations interchangeable.

### Buffer-only mode

The original design treats CPU memory as another persistent cache. #34798 adds
a different choice: use host memory as a temporary transfer buffer between the
GPU and L3. Backups pass through it on their way to storage, and prefetches pass
through it on their way to the GPU. Once a transfer completes and releases its
ownership, the staging space can serve another transfer. The host pool no longer
has to retain a large second copy of the working set.

<HostModeViz client:visible lang="en" />

This mode requires a storage backend and still moves data through CPU memory.
It does not mean every backend has a direct GPU-to-storage path. A smaller host
pool also limits how much I/O can be in flight, and losing persistent L2 reuse
can increase L3 traffic. The original buffer-only PR does not publish a general
speedup; its main contribution is another way to use limited host memory.

### Buffer-only with sidecars

The September 4 change #37424 brings sidecar pools into buffer mode. Its validation
combines DeepSeek-V4-Flash-0731, Mooncake L3, and DSpark on 8 H100 GPUs. It first
runs all 198 GPQA Diamond examples to populate storage, flushes device/radix
cache, then runs the dataset again from L3.

Both runs score 181/198, or 91.41%. DSpark acceptance is 45.84% on the first run
and 45.83% on replay. All 140 prompts with at least one cacheable page load their
expected tokens from L3; 58 prompts are too short for a cacheable page. This
validates the combined cache and draft-state path, rather than claiming a new
latency record.

## Platform adaptations

**AMD and DeepSeek-V4.** #29417 adds HiCache for the `unified_kv_triton` layout.
It retains compressed C4/C128 KV, while the SWA ring's trailing window is
re-prefilled. In the PR's TP4 warm-run test with 50K input tokens, 200 output
tokens, and concurrency 64, output throughput rises from 66 to 789 tokens/s;
median TTFT falls from 91.128 to 3.982 seconds. The GPU-only warm run cannot
retain this working set. These are warm-cache results under capacity pressure,
not cold-start gains.

**Additional storage.** #25377 adds AMD's UMBP-backed tiered storage integration.
Its published DRAM test uses a five-layer DeepSeek-V3 model on 8 MI355X GPUs;
average TTFT falls from 175.6 to 50.0 ms. The row labeled with SSD configuration
has SSD disabled, so that row is a configuration smoke test, not evidence of
SSD performance. NIXL's later hybrid support also makes storage integration
cover recurrent and auxiliary pools, not just Full KV.

**Ascend I/O.** The September 10 merge #38826 adds Memfabric-mapped host memory
and an AscendC sparse-copy path for L2 transfers. It also avoids a host-to-device
upload synchronization that would drain the stream and serialize the pipeline.
This is a new host-memory and I/O adaptation; it does not establish a universal
speedup across all Ascend models.

Two related efforts need a different status label. #36800 has merged only the
building blocks for MLA host-copy deduplication; the scheduler/controller
integration in #26691 is still open at the review date. Ascend Mamba async I/O
in #35815 merged into `qwen_optimize`, while its main-branch counterpart #32500
is still open. Neither should be presented as a completed, generally available
mainline feature.

## Original 2025 benchmarks

### Long context

The original LooGLE benchmark uses DeepSeek-R1 on eight H20-3e GPUs. The chart
compares GPU-only caching, an added CPU L2, an added 3FS L3, and a separately
prepopulated L3. Switch the metric to compare average TTFT and input throughput.

<ResultsViz client:visible lang="en" />

The ordinary L3 result is 51,168 input tokens/s with 1.83-second average TTFT.
Prepopulating L3 produces 76,322 input tokens/s and 1.43 seconds under a different
warmup condition. Keep these conditions separate when interpreting the headline.
Input throughput under cache reuse includes progress through cached input;
it is not the rate at which the GPU newly computes every token's KV.

### Multi-turn conversations

The Mooncake experiment uses Qwen3-235B-A22B-Instruct-2507 on eight H800 GPUs with
eight RDMA NICs. It runs 80 clients for 10 rounds, adding 2,048 input tokens and
generating one output token per request to approximate the prefill side of a
prefill/decode split. By the final round, the original plot shows GPU-only TTFT
at about 4.5 seconds and L3 at about 0.8 seconds. The L3 hit rate is about 90%,
while the smaller tiers have lost much of their reusable history. These values
are approximate readings from the plot, not published raw samples.

The community reports cover different workloads. Novita AI reports a 56%
reduction in average TTFT and doubled inference throughput for a
Qwen3-Coder-480B coding agent using 3FS. Ant Group reports an 84% TTFT reduction
for cache hits versus full recomputation on DeepSeek-R1-671B QA requests with
Mooncake. Neither result is a controlled comparison between the two backends.
