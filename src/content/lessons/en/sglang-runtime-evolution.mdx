Adapted from Ying Sheng's MIT 6.S979 lecture, *SGLang: The Evolution of an LLM Runtime* (November 18, 2026). The lecture traces the runtime through its cache system, because caching makes each design decision concrete.

## Background

A coding task is a program, not a request. In the AgentX trace of 393 Claude Code sessions, the median session has 43 turns. The median turn sends 320 input tokens for every output token, and 44% of sessions fork subagents. One task is many model calls, and the calls are related. Each turn resends the history, and branches start from a shared context.

The application knows how its calls relate. The request stream does not say. This article uses one example throughout: an agent reads a repository, then forks into Fix bug (two turns) and Write tests. The server receives three requests, each with its full history.

<ProgramViz client:visible lang="en" />

The idea behind SGLang is that program structure is an optimization resource. Some of that structure is visible in the tokens, and the rest has to be declared.

- **Shared prefixes** are in the tokens. The runtime can find them and reuse state.
- **Branches about to arrive** are known to the application in advance. Declaring them lets the shared part be computed once.
- **Sessions and weight updates** are not in the tokens at all. They must be declared, so the runtime knows whether to keep, drop, or refresh state.

The four parts below follow how the line between inferred and declared has moved.

## The original design

There are two ways to find shared prefixes. The frontend can declare the branches, so the program says where requests share context. Or the runtime can match incoming token prefixes against the cache. The 2024 SGLang paper combined both.

### Frontend

In the SGLang frontend, a prompt is a state `s`. `fork` creates branches from the same point, and `gen` requests a completion for each branch.

```python
s += shared_context
branches = s.fork(2)
branches[0] += "Fix bug"
branches[1] += "Write tests"
for b in branches:
    b += gen("result")
```

The frontend knows about the fork before either request exists. It uses that as a hint and sends the shared context first. The runtime computes it once, and both branches reuse it. Without the hint, caching still works for requests that arrive later. The difference is timing.

<ForkHintViz client:visible lang="en" />

### RadixAttention

Serving KV involves three separate jobs. Allocation decides where KV fits in GPU memory, which is what PagedAttention does. The prefix index answers which prefix is already cached, which is what RadixAttention does. Movement carries KV between GPUs, host memory, and storage. It arrives later, with HiCache.

Reuse matters because KV is expensive. Take a model with 32 layers, 8 KV heads of 128 dimensions, and BF16 values. One token takes 128 KiB of KV, and a 32K-token context takes 4 GiB. With a prefix index, a shared prefix is stored once, and requests point to the same pages.

<PageShareViz client:visible lang="en" />

RadixAttention stores cached prefixes in a radix tree. Each node holds a span of tokens, the page ids of that span's KV, and a lock count. A new request walks the tree from the root and reuses KV up to its first token that differs. A match is rounded down to whole pages. A token's KV depends on every token before it, so nothing after the first difference can be reused, even if the text is identical.

A running request raises the lock count on every node along its path. A node can be evicted only when its count is 0, and eviction takes unlocked leaves first. A shared prefix therefore outlives the branches below it.

<RadixTreeViz client:visible lang="en" />

### Scheduling

The order of requests changes how much prefill the cache saves. Take a cache that holds 6 tokens and two pairs of requests, where each pair shares a 4-token prefix. Alternating between the pairs computes 24 tokens. Grouping by prefix computes 16. For an offline batch, a depth-first walk of the tree gives the minimum. Each node's tokens are computed once, which is 4 + 2 + 1 + 3 = 10 tokens on the running example.

Online serving pays for this. Longest-prefix-first sends uncached requests to the back of the queue. The scheduler can also find a fork without the frontend. When two queued requests share a prefix that nothing has cached yet, it holds one back for a batch. The first request caches the prefix, and the second reuses it.

<ScheduleViz client:visible lang="en" />

What ships today is more conservative. The default is first come, first served, and the cache-aware rules are opt-in with `--schedule-policy lpm`. The deferral threshold is 32 tokens. Above 128 waiting requests the scheduler falls back to arrival order, because matching and sorting every waiting request costs too much.

### Structured output

A shared prefix is structure in the input. A schema is structure in the output. In `{"summary": "...", "grade": "A"}`, the field names and punctuation are fixed syntax. Only the summary text and the grade are the model's choice. The schema limits which tokens can be sampled.

The original design added jump-forward. When the grammar allows only one string, it is appended in one step instead of being decoded token by token. The forced tokens still need KV, so that step is a prefill over them. Jump-forward saves model passes, not KV.

<JumpForwardViz client:visible lang="en" />

### Looking back

Three kinds of structure show where a declaration is needed.

- **Shared prefixes.** Cached prefixes are found by matching tokens. Requests that arrive together must be declared, or one of them waits.
- **Output constraints.** The application supplies a schema or grammar.
- **Session lifetime.** The runtime cannot tell whether a tool pause means the session is done. The Workloads part returns to this.

Not all of the original design survived.

- **Stayed: automatic prefix reuse.** It is on by default. One prefix tree now covers full KV, sliding-window KV, and recurrent state.
- **Changed: scheduling and the entry point.** The default queue order is first come, first served. Applications call an OpenAI-compatible server instead of the frontend language.
- **Stepping stone: jump-forward.** It was removed in 2025. Token masking by a grammar backend stayed, with xgrammar as the default.

## Models and memory

The original design kept KV for every token, all on the GPU. Neither assumption still holds. Each new layer type and memory tier changed what a cached prefix must hold. New layer types each got their own cache at first, and in 2026 they merged into one.

<TimelineViz client:visible lang="en" />

Every layer type has to answer the same five questions. The original design answered the first four, for full attention only.

1. **State.** What must be kept to resume?
2. **Resume point.** Where can a request restart?
3. **Protection.** What is locked, and what is evicted?
4. **Memory.** Which pool holds the state?
5. **Movement.** Where does it live beyond the GPU?

### Sliding window

A sliding-window layer attends only to recent tokens, so it keeps only recent KV. With a 4-token window, resuming after token N needs KV for tokens N−3 to N. Older KV can be evicted. Which KV counts as old depends on the request, because a request that matches fewer tokens needs an earlier window. In the figure, click a block to evict or restore it.

<WindowViz client:visible lang="en" />

### Recurrent state

A recurrent layer keeps one state for all tokens. Full-attention KV has one entry per token, so a request can resume after any matched token. A recurrent state folds the tokens together and cannot be rolled back. A request can only resume where a copy of the state was saved, and it recomputes from there.

Where states are saved decides how much is recomputed. By default SGLang saves them at request ends and where requests diverge. A denser level also saves one per prefill chunk. More saved states mean less recompute, but each one is a full copy of the state.

<CheckpointViz client:visible lang="en" />

A recurrent state also changes as tokens are processed, so two requests cannot share one. Each request copies the saved state when it matches the prefix, and then advances its own copy. Full-attention KV is shared, not copied.

<StateCopyViz client:visible lang="en" />

### One tree

A hybrid model mixes these layer types, and all of them live on one radix tree. The same 8 tokens on one tree path mean 8 KV entries for full attention, 4 for a sliding window, and 1 saved state for a recurrent layer.

A request resumes where every layer type has usable state. That is the deepest position all of them allow, not the longest match of any single one. In the figure, click a token in the recurrent row to save a state there.

<ResumePointViz client:visible lang="en" />

Protection differs in the same way. A running request needs the whole path for full attention, one window for a sliding-window layer, and one state for a recurrent layer. Evicting full KV on a node also evicts its window KV and recurrent state, but not the other way round. [Unified Radix Cache in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/unified-radix-cache/) covers the tree in detail.

<LockViz client:visible lang="en" />

### Unified memory

Every new layer type brought its own memory pool, sized at startup. Each state type needs a different amount of memory, and demand shifts with the workload. Full KV grows with the retained context. Window KV depends on the window size and the active branches. Recurrent state depends on the running requests and the saved states. On Reflection Beam, a hybrid-attention model, longer contexts need a smaller share for window KV.

<ShareViz client:visible lang="en" />

The default split gives window KV 80% of KV memory, and agent traffic needs 9%. With long contexts, the full-attention pool runs out while the window pool sits idle.

<PoolSplitViz client:visible lang="en" />

Unified Memory (`--enable-unified-memory`) replaces the fixed splits with one arena. Full-attention KV, window KV, recurrent state, and draft-model KV all share it, and free pages serve whichever pool needs them. On 4× B300, Reflection Beam fits 4.7× as many concurrent long-context requests as with the default split. In a 64-session agent replay, median TTFT falls from 688 ms to 462 ms, and the prefix-cache hit rate rises from 87% to 95%.

Pools that share one arena fragment its free space, so pages have to move. A request holds a page id, and a page table maps the id to a physical slot. To move a page, the runtime copies its data and changes one table entry. The request never sees the move.

<CompactionViz client:visible lang="en" />

The old slot cannot be reused right away, and neither can the slots of a finished request. With overlap scheduling, the CPU frees a finished request while a GPU forward is still running and may still read those slots. Freeing is therefore split into two stages. The page id is free at once, and the physical slot waits until the forward ends. [Unified Memory in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/unified-memory/) covers the allocator.

<DeferredFreeViz client:visible lang="en" />

### HiCache

Cached state no longer fits on the GPU. HiCache keeps evicted state in host memory and in optional shared storage, and loads it back on a hit. On Inkling-Small with 8× H200 and a 500 GiB storage tier, effective input throughput rises from 15.5K tokens/s with the GPU cache alone to 67.1K.

One index covers GPU and host memory, and storage is queried on demand. Attention reads only from GPU memory, so a hit lower down needs a transfer first. The deeper the hit, the more copies before the request can run.

<TierViz client:visible lang="en" />

Each layer type is backed up differently, and only the full-attention copy grows with the node. On restore, a recurrent state comes back only where one was backed up, and later tokens are recomputed.

<BackupViz client:visible lang="en" />

A transfer is not always worth it. Restoring 1 GiB of KV at 50 GiB/s with a 2 ms fixed cost takes 22 ms. If recomputing takes 35 ms, restoring wins. If it takes 12 ms, recomputing wins. By default SGLang recomputes host hits under 10 tokens and skips storage prefetches under 256.

<RestoreViz client:visible lang="en" />

When a restore is worth it, SGLang hides it in time the request already spends. It prefetches from storage while the request waits in the queue. It also pipelines the load with the compute, so each layer's compute waits only for its own layer's load. The copy still happens, but the request no longer waits for it.

<HideTransferViz client:visible lang="en" />

State in shared storage raises one more question: what identifies it? A page is reusable only if three things match the reader.

- **Input identity:** token ids, positions, and any additional model inputs.
- **Model identity:** weights, adapters, and a compatible model configuration.
- **Storage format:** state type, dtype, layout, and GPU sharding.

Token matching cannot see model identity, and the RL section returns to this. [HiCache in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hicache/) covers the tiers and transfers.

### Sparse attention

Sparse attention reads only a few KV entries per step, yet a GPU-only cache still holds the full context. HiSparse keeps the full KV in host memory and only the selected entries on the GPU. At each decode step, only the selected misses move from host to GPU.

<SparseViz client:visible lang="en" />

The freed GPU memory fits larger decode batches. With GLM-5.1-FP8 on one 8× H200 server, at 256 concurrent requests with 32K input and 8K output tokens, decode throughput is more than 3× higher. At low concurrency the swap-in overhead can hurt. See [HiSparse in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hisparse/).

### Answers by layer type

| | Full attention | Sliding window | Recurrent state |
| --- | --- | --- | --- |
| State | KV for every token | KV for the last window | The saved recurrent state |
| Resume point | Any matched token, rounded down to a whole page | Where a full window of KV sits right before it | The deepest saved state; recompute the rest |
| Protection | Lock the whole path to the root. Evict unlocked leaves, with their window KV and state | Lock the nodes that span one window. Evict older KV; the node stays | Lock one node. Evict the state alone |
| Memory | Full KV pool; grows with the context | Window KV pool; bounded by the window | State pool of fixed-size slots |
| Movement | The node's KV | KV within one window | One state slot |

The new layer types need nothing new from the application.

## Execution

The previous part made more state reusable. This part follows the time that a cache hit leaves behind.

### Hit rate and TTFT

A higher hit rate does not lower time to first token by the same amount. Hit rate counts tokens: reused tokens divided by input tokens. TTFT counts time: the wait in the queue, the CPU work of matching the prefix and building the batch, and the GPU prefill of the new tokens. A hit shortens only the last part. The CPU time stays the same and becomes a larger share, so the CPU starts to set the pace.

<HitTtftViz client:visible lang="en" />

### Overlap scheduling

SGLang prepares the next batch while the GPU runs the current one. With 2 ms of CPU and 6 ms of GPU work per batch, a serial loop takes 8 ms per batch. An overlapped loop takes 6 ms, because the GPU never waits for the CPU.

<OverlapViz client:visible lang="en" />

One dependency stands in the way. The input of batch N+1 is the token sampled by batch N, and waiting for it would undo the overlap. So the CPU never waits for the token. It names a slot in a GPU buffer of sampled tokens as the input, and the GPU fills the slot.

<FutureSlotViz client:visible lang="en" />

Overlap has a limit. A step costs max(CPU, GPU) instead of their sum. With 8 ms of CPU and 6 ms of GPU per batch, a serial step takes 14 ms and an overlapped step takes 8 ms, with the GPU idle for 2 ms. Prefix hits shrink the GPU step, and once the CPU step is the longer one, the CPU sets the pace.

### Less CPU work

When overlap is not enough, the remaining lever is to shrink the CPU work. With short prefills, kernel launches and tree operations dominate.

An eager forward launches every kernel from the CPU. A CUDA graph replays captured kernels instead, but some operations cannot be captured. A breakable graph runs such an operation between two captured segments. Graph A replays, the operation runs and writes a fixed buffer, and graph B replays and reads that buffer. On gpt-oss-120b with TP4 on 4× GB300, prefill is 1.70× faster than eager. See [Breakable CUDA Graph in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/breakable-cuda-graph/).

The radix tree's match, insert, and evict operations run in Rust, and Python only orchestrates the cache. The Rust tree prototype lowers TTFT by up to 38%.

## Workloads

Agent and RL workloads raise two questions that the request stream cannot answer. The first is whether a session is over. When a turn finishes and no new request has arrived, a tool call may still be running, or the user may have left. The second is whether cached KV comes from the current weights. A new request can match a cached prefix token for token after the weights were updated. In both cases the tokens are the same, so the runtime cannot tell which case it is in.

### Sessions

While a request runs, its KV cannot be evicted. Once it finishes, the KV is evictable. While a tool runs, nothing protects the session's KV, and the cache sees it as unused. If another request needs memory, the KV is evicted, and the next turn pays for the full history again.

The application can say which requests form a session. With `--enable-session-radix-cache`, it tags the turns with one session id, or calls `open_session` and `close_session`. Session KV is then evicted last, and other unused KV goes first. Closing the session, or a timeout, removes the tag, and the KV becomes ordinary cache again. Each cached node counts the open sessions that reach it, so shared KV stays protected until the last session that uses it ends.

<SessionViz client:visible lang="en" />

### RL rollouts

In RL, new weights can invalidate old KV. The same prompt tokens under new weights give different KV, and token matching cannot see the change. The update call makes the choice. `flush_cache` defaults to true, so the cache is dropped and the prompt is recomputed with the new weights. Keeping the KV is fast but stale. `--enable-prefill-weight-versions` reports which weights computed each token's KV.

<WeightsViz client:visible lang="en" />

### Distribution

With several engines, reuse also depends on where a request lands. Miles, an RL framework on SGLang, sends a session's turns to the same engine and DP rank. A DP rank is a data-parallel replica with its own cache. Miles reports about 96% prefix-cache hits in a GLM-5.2 agentic RL run.

<AffinityViz client:visible lang="en" />

For general traffic, the router tracks which engine has each prefix. Each engine streams KV events, and sgl-router's `cache_aware` policy keeps one prefix index. The policy is opt-in, and the default is `round_robin`. The index can be stale, because an engine may evict a prefix before the request reaches it. The engine then checks its local state and restores or recomputes. A stale index costs a recompute, never a wrong answer.

<RouterIndexViz client:visible lang="en" />

A cache hit is not always the fastest route either. The router compares queue time plus remaining work on each engine, and a load-pressure guard can override the best cache match.

<RouterViz client:visible lang="en" />

The index only works if both sides see the same tokens. If the router and the engine each render the chat, a slightly different template changes one token, and the match stops there. So the router tokenizes once and forwards the ids ([#28744](https://github.com/sgl-project/sglang/pull/28744)). The engine skips its own tokenizer.

<TokenizeViz client:visible lang="en" />

Prefill/decode disaggregation uses the same reuse to save transfers. With `--disaggregation-decode-enable-radix-cache`, a decode worker that already holds KV for earlier tokens receives only the missing pages. The reused pages stay locked until the request finishes or fails, so they cannot be evicted while the missing ones are still arriving.

<PdViz client:visible lang="en" />

## Summary

The runtime infers more, and the application declares the rest. In 2024 the application declared the whole program. Today the runtime finds shared prefixes on its own, in every layer type and on GPU, host, and storage. The application declares only what tokens cannot show: the output schema, which requests form a session, and when the weights changed.

<DeclareViz client:visible lang="en" />

### Open problems

Some hints would help, but an application cannot declare them today.

- **Expected tool duration.** Should a paused session's state stay on the GPU, move to host memory, or be freed?
- **Fan-out about to happen.** Should the shared prefix be prefilled once, before the branches arrive?
- **Chance that a prefix returns.** Which state is worth keeping, or backing up to host memory?
- **Deadline.** Which state should be evicted first? Requests carry a priority today, not a deadline.

Two questions go beyond the cache. Agents now write the programs, so can the runtime learn their structure without a frontend? And when KV is shared across tenants, can reuse leak one tenant's prompt to another through timing?
