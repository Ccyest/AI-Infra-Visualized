## Background

A coding agent does not send one request per task. In the AgentX trace of 393 Claude Code sessions, the median session has 43 turns. The median turn sends 320 input tokens for every output token, and 44% of sessions fork subagents. Each turn resends the whole history, and branches start from a shared context.

The application knows how these calls relate. The server does not. It receives separate requests, each carrying its full history. This article uses one example throughout: an agent reads a repository, then forks into Fix bug (two turns) and Write tests.

<ProgramViz client:visible lang="en" />

Shared prefixes can be recovered by comparing tokens. Other facts are not in the tokens: which branches are about to arrive, what the output must look like, and whether a session is over. The sections below follow how SGLang handles both kinds.

## The original design

The 2024 SGLang paper paired a frontend language with a runtime. The frontend declared the program's structure. The runtime found shared prefixes on its own.

### Fork

In the frontend, `s.fork(2)` creates two prompt branches from the same state. The frontend knows about both branches before either request exists. It sends the shared context first, so the runtime computes it once and both branches reuse it.

<ForkHintViz client:visible lang="en" />

### RadixAttention

KV is expensive to keep and to recompute. Take a model with 32 layers, 8 KV heads of 128 dimensions, and BF16 values. One token takes 128 KiB of KV, and a 32K-token context takes 4 GiB.

RadixAttention stores cached prefixes in a radix tree. Each node holds a span of tokens, the page ids of that span's KV, and a lock count. A new request walks the tree from the root and reuses KV up to its first token that differs. A token's KV depends on every token before it, so nothing after that point can be reused, even if the text is identical.

A running request raises the lock count on every node along its path. Eviction only removes unlocked leaves, so a shared prefix outlives the branches below it.

<RadixTreeViz client:visible lang="en" />

### Scheduling

The order of requests changes how much prefill the cache saves. Serving two pairs of related requests in alternating order computes 24 tokens. Grouping them by prefix computes 16. For an offline batch, a depth-first walk of the tree computes each node's tokens exactly once, which is the minimum. On the example above that is 4 + 2 + 1 + 3 = 10 tokens.

Online serving pays for this. Longest-prefix-first (`--schedule-policy lpm`) sends uncached requests to the back of the queue. SGLang's default today is first come, first served, and `lpm` is opt-in. A cache-aware policy can also hold back a request for one batch when it shares an uncached prefix with another request in the queue. The first request caches the prefix, and the second reuses it.

<ScheduleViz client:visible lang="en" />

### Structured output

A schema is structure on the output side. In `{"summary": "...", "grade": "A"}`, the field names and punctuation are fixed, and only the values are the model's choice. The original design added jump-forward: when the grammar allows only one string, append it in one step instead of decoding it token by token. The forced tokens still need KV, so that step is a prefill over them.

<JumpForwardViz client:visible lang="en" />

Jump-forward was removed in 2025. Token masking by a grammar backend stayed, with xgrammar as the default.

## Models and memory

The original design kept KV for every token, all on the GPU. Neither assumption held. Each new layer type and memory tier changed what a cached prefix has to contain.

<TimelineViz client:visible lang="en" />

### Resume point

Full attention keeps KV for every token, so a request can resume after any matched token. A sliding-window layer reads only recent tokens. With a 4-token window, resuming after token N needs KV for tokens N−3 to N, and older KV can be evicted. A recurrent layer folds all tokens into one state. The state cannot be rolled back, so a request can only resume where a copy of the state was saved. Each request then works on its own copy, because the state changes as tokens are processed.

One tree serves all three. A request resumes at the deepest token where every layer type has usable state, and recomputes the rest. In the figure, click a token in the recurrent row to save a state there. [Unified Radix Cache in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/unified-radix-cache/) covers the tree in detail.

### Unified memory

Each layer type first got its own memory pool, sized at startup. Demand shifts with the workload. On Reflection Beam, a hybrid-attention model, the default split gives window KV 80% of KV memory. Agent traffic with about 60K input tokens needs 9%. The full-attention pool runs out while the window pool sits idle.

<PoolSplitViz client:visible lang="en" />

Unified Memory (`--enable-unified-memory`) puts every KV and state pool in one arena. Free pages go to whichever pool needs them. On 4× B300, Reflection Beam fits 4.7× as many concurrent long-context requests. In a 64-session agent replay, median TTFT falls from 688 ms to 462 ms, and the prefix-cache hit rate rises from 87% to 95%. See [Unified Memory in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/unified-memory/) for the allocator.

### HiCache

Cached state also outgrew the GPU. HiCache keeps evicted state in host memory and shared storage, and loads it back on a hit. On Inkling-Small with 8× H200, a 500 GiB storage tier raises effective input throughput from 15.5K to 67.1K tokens/s.

A hit below the GPU needs a transfer, and a transfer is not always worth it. Restoring 1 GiB of KV at 50 GiB/s with a 2 ms fixed cost takes 22 ms. If recomputing takes 35 ms, restoring wins. If it takes 12 ms, recomputing wins. By default SGLang recomputes host hits under 10 tokens and skips storage prefetches under 256.

<RestoreViz client:visible lang="en" />

SGLang also starts the transfer while the request is still queued, so the request waits less for the copy. See [HiCache in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hicache/) for the tiers and transfers.

Sparse attention adds one more case. A sparse layer reads only a few KV entries per step. HiSparse keeps the full KV in host memory and only the selected entries on the GPU, which frees GPU memory for larger decode batches. With GLM-5.1-FP8 on one 8× H200 server, decode throughput at 256 concurrent requests is more than 3× higher. At low concurrency the swap-in overhead can hurt. See [HiSparse in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hisparse/).

## Execution

A higher hit rate does not lower time to first token by the same amount. Hit rate counts tokens skipped. TTFT also includes the queue wait and the CPU work of matching the prefix and building the batch, which a hit does not shorten. When the prefix is cached, GPU time shrinks, and the same CPU time becomes a larger share.

SGLang overlaps the two. The CPU prepares batch N+1 while the GPU runs batch N. The input token for batch N+1 is not sampled yet, so the CPU names a slot in a GPU buffer and the GPU fills it later. A step then costs max(CPU, GPU) instead of their sum. Once prefix hits shrink the GPU step below the CPU step, the CPU sets the pace.

<OverlapViz client:visible lang="en" />

The remaining lever is to shrink the CPU work itself. Breakable CUDA graphs replay captured kernels instead of launching each one. On gpt-oss-120b with TP4 on 4× GB300, prefill is 1.70× faster than eager. A Rust radix tree prototype lowers TTFT by up to 38%. See [Breakable CUDA Graph in SGLang](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/breakable-cuda-graph/).

## Workloads

Agent and RL workloads raise questions that token matching cannot answer.

### Sessions

A running request locks its KV. Between turns, while a tool runs, no request exists, so the cache sees the session's KV as unused. If another request needs memory, that KV can be evicted, and the next turn recomputes the whole history.

The application can say which requests form a session. With `--enable-session-radix-cache`, it sends a session id on each request, or calls `open_session` and `close_session`. Session KV is then evicted last. When the session closes or times out, its KV becomes ordinary cache again. KV shared by several sessions stays protected until the last one ends.

<SessionViz client:visible lang="en" />

### RL rollouts

In RL, the weights change between rollouts. The same prompt tokens under new weights produce different KV, and token matching cannot see the change. The weight update call makes the choice. By default it flushes the cache, and the prompt is recomputed with the new weights. Keeping the KV is faster, but the KV is stale.

### Distribution

With several engines, reuse depends on where a request lands. Miles, an RL framework on SGLang, sends all turns of a session to the same engine and DP rank. It reports about 96% prefix-cache hits in a GLM-5.2 agentic RL run.

For general traffic, sgl-router's `cache_aware` policy keeps an index of which engine holds each prefix. The engines feed it with KV events. A cache hit is not always the fastest route. A warm engine with a long queue can finish later than a cold one, so a load guard can override the best match.

<RouterViz client:visible lang="en" />

Two details keep this correct. First, the index can be stale, because an engine may evict a prefix before the request reaches it. The engine checks its own state and restores or recomputes. A stale index costs time, never a wrong answer. Second, the router tokenizes once and forwards the token ids ([#28744](https://github.com/sgl-project/sglang/pull/28744)). The router and the engine then match on the same ids.

Prefill/decode disaggregation follows the same idea. With `--disaggregation-decode-enable-radix-cache`, a decode worker that already holds KV for 256 of 384 input tokens receives only the missing 128.

## Summary

In 2024 the application declared the whole program. Today the runtime finds shared prefixes on its own, across every layer type and memory tier. The application declares only what tokens cannot show: the output schema, which requests form a session, and when the weights changed.
