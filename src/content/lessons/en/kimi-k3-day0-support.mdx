> **In one sentence**: K3 departs from convention in attention, MoE, and
> quantization at the same time, so every "of course" baked into a serving
> stack breaks. SGLang's day-0 support rewrites three fronts at once — memory
> (a unified pool), prefill (chunked PP), decode (DCP) — plus speculative
> decoding with DSpark.

## K3 in 60 seconds

- **2.8T parameters**, 1M-token context — the first open model in the 3T class;
- Of its 93 layers, **69 are KDA linear attention and 24 are MLA**, interleaved;
- **LatentMoE**: 896 experts, top-16 routing, in a 3584-dim latent space;
- Native **MXFP4** weights; MoonViT3d vision tower.

For serving, the second bullet is the killer: two attention types mean **two
inference states with opposite personalities** —

| | MLA (24 layers) | KDA (69 layers) |
| --- | --- | --- |
| State shape | KV cache, appends per token | Recurrent state, fixed size |
| Growth | ~27 KB per token, append-only | ~54 MB per request (TP=8), **overwritten in place** each step |

## Challenge 1: two state types, one pool of memory

The old approach carves the memory pool in half at startup — a guess. But KDA
demand tracks **concurrency** while MLA demand tracks **total context length**;
skew the workload and one side starves while the other idles. SGLang switches
to a unified pool: fixed KDA blocks fill from the left, MLA pages from the
right, and whatever sits in the middle is contiguous free memory for whoever
needs it:

<PoolViz client:visible lang="en" />

Watch t=14: the split layout's MLA side runs dry and R2 is evicted
mid-generation — while 6 KDA pages sit free next door. The unified pool sails
through the same moment.

On the prefix-cache (radix tree) side, KDA state is overwritten in place, so it
can't be shared like KV. SGLang manages it with three operations —
**copy-on-write** (restore a shared checkpoint to a private slot before
mutating), **snapshot** (ping-pong buffered capture), and **donate** (hand the
state to the radix tree by slot index). Race-free by construction; details in
the blog below.

## Challenge 2: prefill as a layer-wise pipeline, no AllReduce

TP8 has all 8 GPUs co-compute each chunk, but every layer pays an AllReduce —
communication squarely on the critical path. Chunked PP8 flips it: split the
model into 8 stages by layer, stream prompt chunks through, and hide P2P
hand-offs behind the next chunk's compute (91% hidden in practice):

<PipelineViz client:visible lang="en" />

The warm-up bubble is paid once; at steady state a chunk ships every 2 columns.
Measured in SGLang: PP8 prefill delivers **1.45–1.72× the throughput of a TEP8
node** (TEP = tensor + expert parallelism; the diagram simplifies it to plain
TP for teaching).

## Challenge 3: decode shards KV by position (DCP)

Decode's bottleneck is memory, not compute: under TP every GPU stores a full
copy of the KV. DCP shards by token position instead — rank r keeps only the
positions where `p mod N = r`, attends locally, then a single all-to-all merges
the partial outputs (log-sum-exp keeps the result bit-consistent with one GPU):

<DcpViz client:visible lang="en" />

Measured on K3: DCP8 multiplies logical context capacity by **7.9×**. On long
agent sessions, TP8 collapses at 16 concurrent sessions while DCP8 sustains
**48 at 541 tok/s**. Note that KDA state has no position axis, so KDA layers
stay TP-sharded — with a hybrid model, even parallelism is per-layer hybrid.

## How fast can one GPU go? (numbers at a glance)

Before speculation enters the picture, BS=1 decode climbed from **63.8 tok/s**
to **~113 tok/s** through four families of work (per-item gains from the blog
in parentheses):

| Family | Representative moves |
| --- | --- |
| Launch elimination (+19.9 tok/s) | Collapse the MoE front into one GEMM, merge KDA projections, register-resident routing |
| Dedicated kernels (+10.3) | Fused KDA decode, W4A8 MoE, TMA attention-residual aggregation |
| Communication fusion (+27.6) | Fused all-reduce family: multicast + NVLS in-switch reduction with residual/RMSNorm folded in |
| Overlap & prologue (+10.4) | GEMV–GEMM overlap, fused residual write-back, PDL attention arming |

On top of that, DSpark speculative decoding lifts BS=1 to **~423 tok/s**
(~3.7×).

The combined serving frontier: PP8 prefill feeding TP8 decode reaches
**2,808 tok/s per GPU** (fp4); interactive configs trade down to **116+ tok/s
per user**. The one line from the blog worth memorizing:

> All-reduce is a synchronization point — a microsecond saved there converts
> one-for-one into step time; a kernel in another stream's overlap slack
> converts at roughly one-tenth.

## Diagram ↔ real system

| In the diagram | In a real system |
| --- | --- |
| One memory-pool page | Several MB; a real KDA block ≈ 54 MB while MLA is ~27 KB/token — far more lopsided than drawn |
| A KDA cell in the pool bar | Fixed-size recurrent state, overwritten every step (the overwrite isn't animated) |
| One pipeline column | One scheduling beat; real P2P hand-offs are 91% overlapped and omitted here |
| The upper "TP8" grid | Simplified to plain tensor parallelism for teaching; the blog's measured baseline is TEP8 (tensor + expert parallelism) |
| Gray AllReduce cell | Critical-path communication; its real share depends on the interconnect |
| One DCP grid cell | One token position's MLA KV; real systems manage pages and use N=8 |
