## The Kimi K3 architecture

K3 is a 2.8T-parameter MoE model with 104B parameters active per token. It
supports a native 1M-token context. Its MoE expert weights ship in MXFP4, with
MXFP8 activations. The interesting part is how it makes the compute and memory
fit: 69 of its 93 layers use KDA linear attention, while 24 use global MLA. Every
attention layer is paired with a Stable LatentMoE FFN, while Attention Residual
aggregates representations across blocks. Click the diagram for the complete structure:

<ArchViz client:visible lang="en" />

### KV cache at 1M tokens

Start with memory. After MLA compression, K3's 24 MLA layers need about 27KB
of KV cache per token in total. If all 93 layers used MLA, one 1M-token request
would need roughly 110GB; uncompressed MHA would cost another order of
magnitude. K3 therefore cannot keep context-growing softmax attention in most
layers.

K3 interleaves 3 KDA + 1 MLA. The KDA recurrent state has a fixed size, about
0.4GB per request across the machine, and updates in place each step. MLA keeps
global attention. The model uses no RoPE (NoPE); position comes implicitly from
the KDA recurrence:

<CacheViz client:visible lang="en" />

At 1M tokens, the 24 MLA layers need about 28GB, or 1/3.9 of the all-MLA
hypothetical. Compute follows the same pattern: softmax attention scans the
history for every decoded token (`O(N)`), while KDA updates a fixed-size state
(`O(1)`).

### MHA: scan the whole history each step

First look at what KDA replaces. In ordinary MHA, token `N` computes a score
`zᵢ = qᵀkᵢ / √d` against each of the `N−1` cached tokens, applies softmax, and
reads `o = Σᵢaᵢvᵢ`. That is about `N²/2` dot products over a full sequence:
`O(N²)` compute and `O(N)` cache. In the diagram, "it" can place its weight
directly on "cat" several tokens earlier:

<MhaViz client:visible lang="en" />

Softmax attention buys direct, per-position reads. The cost is rescanning the
entire history for every new token.

### Linear attention: a fixed-size state

Linear attention no longer keeps one KV entry per token. It accumulates history
into a fixed-size matrix, `S = Σᵢkᵢvᵢᵀ`. Think of S as associative memory: k selects
a write direction, v is the content, and q reads with `o = Sᵀq`. No matter how
long the context becomes, each step reads and writes only S.

Each head therefore owns a <code>128×128</code> state <code>Sʰ</code>. These heads are learned feature spaces, not literal slices of the 7168 input coordinates.</p>
  <p>After fixing head <code>h</code>, <code>chⱼ = kₜʰ[j]</code> is key-feature dimension <code>j</code> inside that head. Increasing <code>dₖ</code> adds key-feature axes; increasing <code>dᵥ</code> widens the value stored along each axis. State and update cost per head grow as <code>dₖ×dᵥ</code>. K3 sets both to 128, giving 16,384 state scalars per head.</p>
</details>

### DeltaNet: adding a delete operation to the fixed state

Plain accumulation can write but cannot overwrite. If the same key direction
first receives 1 and then 4, both values remain in S and the next read returns
a mixture.

DeltaNet first reads the old value r, then writes only the difference:
`Sₜ = Sₜ₋₁ + β·k·(v − Sₜ₋₁ᵀk)ᵀ`. The new readout is
`r′ = (1−β)r + βv`. The coefficient β controls rewrite strength; β=1 fully
replaces the old association.

<DeltaRuleViz client:visible lang="en" />

This fixes same-direction rewriting, but not capacity: as unrelated history
enters the fixed-size S, what should decay? Real key vectors are also not
perfectly orthogonal, so a write in one direction can project into another and
create crosstalk.

<details className="lesson-details">
  <summary>Math details: A/B in the diagram and the crosstalk term</summary>
  <p>A and B are full directions in key space, not token slots or individual channels. <code>A=1</code> is shorthand for “k points along A and v represents 1.” Colors trace the contribution from each write; the real S stores only their sum.</p>
  <p>If <code>q<sub>A</sub> = k<sub>A</sub></code> and S contains both <code>k<sub>A</sub>v<sub>A</sub>ᵀ</code> and <code>k<sub>B</sub>v<sub>B</sub>ᵀ</code>, then <code>o<sub>A</sub> = Sᵀq<sub>A</sub> = v<sub>A</sub> + (k<sub>A</sub>ᵀk<sub>B</sub>)v<sub>B</sub></code>. The second term is B leaking into A, scaled by the inner product of the two keys.</p>
</details>

### KDA: delta rule with per-channel gating

KDA stacks two operations. A gate `Diag(αₜ)` computed from the current token first
decays the old state channel by channel; DeltaNet then performs the rewrite.
The model can learn which state should remain and which can release capacity
more quickly.

<details className="lesson-details">
  <summary>Math details: how KDA gates and rewrites the same S</summary>
  <p>The full update is <code>Sₜ = (I−βₜkₜkₜᵀ)·Diag(αₜ)·Sₜ₋₁ + βₜkₜvₜᵀ</code>, where <code>αₜ ∈ (0,1)<sup>dₖ</sup></code> and each entry scales one key channel of S. It does not select A or B directly or rotate keys into orthogonal directions; every historical contribution in a row is scaled together.</p>
  <p>The diagram reduces the real state to 2D, with <code>k<sub>A</sub>=(1/√2)[1,1]ᵀ</code> and <code>k<sub>B</sub>=(1/√2)[1,−1]ᵀ</code>. Both A and B span ch₁/ch₂. The gate scales both rows, then the delta rule writes the residual needed to reach target value 4 along the full <code>k<sub>A</sub></code>.</p>
</details>

<KdaGateViz client:visible lang="en" />

The Kimi Linear paper also interprets the gate as learned position encoding in
place of RoPE's fixed rotation. Its chunkwise kernel for the constrained DPLR
form is about twice as fast as the general implementation, making 69 KDA layers
practical.

### Attention Residual

An ordinary Transformer accumulates every layer's update into one residual
stream. As the model grows deeper, shallow information must remain
distinguishable after dozens of additions.

K3 keeps the ordinary residual inside each group and saves one block output
every 12 layers. Later blocks use a learned pseudo-query to weight the embedding
and these saved summaries, directly retrieving the shallow representation most
useful now:

<AttnResViz client:visible lang="en" />

This creates a shorter path across depth, and different deep blocks can retrieve
different historical representations.

<details className="lesson-details">
  <summary>Math and cost: why K3 saves one summary every 12 layers</summary>
  <p>For a later block ℓ, the pseudo-query produces weights <code>α<sub>ℓi</sub></code> and retrieves <code>r<sub>ℓ</sub> = Σ<sub>i&lt;ℓ</sub> α<sub>ℓi</sub>v<sub>i</sub></code>. This is a softmax-weighted mixture of the embedding and earlier block summaries, not a hard choice of one layer.</p>
  <p>Full AttnRes saves every layer output and gives the finest retrieval, but costs more memory, bandwidth, and pipeline communication. Block AttnRes saves one summary per group, reducing state from <code>O(Ld)</code> to <code>O(Nd)</code>. K3 uses one summary every 12 layers. In the optimized implementation, typical inference-latency overhead is below 2%, while training wall-clock overhead under pipeline parallelism is below 4%.</p>
</details>

### LatentMoE

Every K3 FFN uses MoE: each token selects 16 of 896 routed experts, while 2
shared experts are always active. The routed-pool selection rate is therefore
`16/896 ≈ 1.8%`; the separate whole-model ratio is `104B/2.8T ≈ 3.7%` active
parameters per token.

Routing and expert compute project the 7168-d hidden state down to a 3584-d
latent space, then project back to full width. This halves both the 16-way
all-to-all dispatch traffic and expert weight volume:

<MoeViz lang="en" />

High sparsity makes training harder to stabilize. K3 uses RMSNorm, bounded
SiTU-GLU, and Quantile Balancing, which derives expert quotas directly from
router-score quantiles.

### The training side

Four other training choices are worth remembering: quantization-aware training
for MoE expert weights in MXFP4 and their input activations in MXFP8 begins at
SFT; Per-Head Muon applies orthogonalized updates per attention head; context
grows through an 8K → 64K → 256K → 1M curriculum; and RL covers general,
agentic, and coding workflows.

## SGLang's day-0 adaptations

K3's hybrid architecture creates two inference states with completely
different lifecycles:

| | MLA (24 layers) | KDA (69 layers) |
| --- | --- | --- |
| State shape | KV cache, appends per token | Recurrent state, fixed size |
| Growth | ~27KB per token, append-only | ~54MB per request (TP=8), overwritten in place each step |

MLA appends KV per token, while KDA reserves a fixed amount per request and
overwrites it every step. That difference propagates into memory allocation,
prefill parallelism, and decode scaling—the three parts of SGLang's day-0 work.

### Memory management for two state types

The old approach preallocates separate KDA and MLA regions at startup. KDA
demand follows concurrency, while MLA demand follows total context length. If
the workload differs from the estimate, one region fills while the other sits
idle. SGLang puts both in one pool: fixed KDA blocks allocate from the left,
MLA pages from the right, and both share the free space in the middle:

<PoolViz client:visible lang="en" />

At t=14, the split layout exhausts its MLA region and evicts R2 while six KDA
pages remain free. The unified pool continues running every request.

Prefix caching also changes. KDA state is overwritten in place and cannot be
shared like KV. SGLang uses copy-on-write, snapshot, and donate to manage KDA
checkpoints in the radix tree without letting requests overwrite shared state.

### Chunked pipeline prefill

Prefill processes many prompt tokens at once, providing enough chunks to fill a
pipeline. TP8 keeps all eight GPUs in lockstep at every layer, pays an AllReduce
per layer, and narrows each GEMM. Chunked PP8 instead assigns ranges of the 93
layers to G1–G8 and lets different GPUs process different chunks. GPUs pass only
the activation from the preceding stage, allowing P2P transfers to overlap
with computation on the next chunk:

<PipelineViz client:visible lang="en" />

This removes per-layer AllReduce, restores full-width GEMMs, and hides 91% of
inter-stage P2P. In an 8K-prefill comparison on 2×4 GB300, a representative
PP8×TP1 point reaches 5,958 input tok/s/GPU, 1.64× TEP8. Across configurations,
prefill capacity improves by 1.45–1.72×.

Decode usually has only one new token per step, not enough work to fill a deep
pipeline, and it is more sensitive to step latency. TP8 remains the better fit.
A common PD-disaggregated split is `PP8 prefill → TP8 / DCP8 decode`. PP still
pays fill and drain bubbles, so it does not win with too few requests or chunks.

### Decode context parallelism (DCP)

MLA has multiple attention heads, but they all share the same compressed KV latent,
leaving no cache head axis for TP to shard. Every TP8 rank therefore replicates the
complete MLA KV latent, and adding GPUs does not increase logical context capacity.
DCP shards by token position instead: each GPU computes partial attention over its local 1/N KV,
then one packed all-to-all merges the result exactly:

<DcpViz client:visible lang="en" />

DCP primarily increases capacity and concurrency, not latency for one short
request. Keeping more long sessions on the GPU avoids host offload, re-prefill,
and throughput collapse. On K3, DCP8 raises logical capacity from 1.5M to
12.2M tokens (7.9×) and reaches 541 tok/s at 48 agent sessions. It costs one
all-to-all per MLA layer. KDA state has no token-position axis and remains
TP/head-sharded.
