## The Kimi K3 architecture

K3 is a 2.8T-parameter MoE model with 104B active per token; 69 of its 93
layers are KDA linear attention and the other 24 are global MLA; context is
natively 1M tokens and the weights ship in MXFP4. The overall structure,
with each part clickable:

<ArchViz client:visible lang="en" />

### KV cache at 1M tokens

Start with the memory math. Extrapolating from the compressed-MLA rate of
27 KB/token (across 24 layers), a 93-layer all-MLA stack would hold about
110 GB per request at 1M tokens; uncompressed MHA is an order of magnitude
beyond that. That number rules out softmax attention for most layers.

K3 interleaves 3 KDA + 1 MLA. A KDA layer's state has a fixed size (≈0.4 GB
per request in total) and is overwritten in place each step; MLA layers keep
global attention, and the model uses no RoPE at all (NoPE), position coming
implicitly from the KDA recurrence:

<CacheViz client:visible lang="en" />

The 24 MLA layers hold about 28 GB at 1M tokens, 1/3.9 of the all-MLA
hypothetical. Compute follows the same pattern: softmax attention scans the
whole history per generated token (`O(N)`); KDA updates a fixed-size state
(`O(1)`).

### MHA: scan the whole history each step

Start with what got replaced. Decode a sentence token by token: "The cat
chased the mouse because it was hungry". Token `N` dots against each of the
`N−1` tokens already in the cache (the lines in the diagram). This first gives
scores `zᵢ = qᵀkᵢ / √d`, then `aᵢ = softmax(z)ᵢ` normalizes them, and finally
`o = Σᵢaᵢvᵢ` takes the weighted value sum before the token's own KV is appended.
Over the whole sentence that is about `N²/2` dot products: `O(N²)` compute,
`O(N)` cache. Watch "it" at `t=7`: its referent "cat" sits six tokens back,
and that is where the weight should land:

<MhaViz client:visible lang="en" />

Both sides of softmax attention in one picture: every historical position is
scored independently, so distance does not automatically decay through a
recurrence; the cost still keeps climbing with context, as the previous
section's 1M-token bill showed.

### Linear attention: a fixed-size state

Linear attention drops the softmax and first accumulates all historical writes
into the fixed-size matrix `S = Σᵢkᵢvᵢᵀ`. After fixing one head `h`, K3 has
`kₜʰ ∈ ℝ¹²⁸` and `vₜʰ ∈ ℝ¹²⁸`, so one outer product `kₜʰ(vₜʰ)ᵀ` has shape
`128×128`, as does the accumulated state `Sʰ`. A query
`qₜʰ ∈ ℝ¹²⁸` reads it as `oₜʰ = (Sʰ)ᵀqₜʰ`. S is an associative-memory matrix:
each token's k picks the direction to write into, while v is the content. The
cache is gone; each step touches only S.

The `128` here is not the full token-embedding width. K3 has hidden size `7168`;
learned Q/K/V projections produce `96` KDA heads, each with head dimension `128`.
This is a learned feature space, not a literal partition of the 7168 input
coordinates into 96 pieces. Here `h` is the head index. Once a particular head
`h` is fixed, `chⱼ = kₜʰ[j]` means coordinate `j` inside that head—not head
`j`. Those 128 coordinates already exist in naive linear attention; more
precisely, they are key feature dimensions. We call them channels here to match
KDA's later channel-wise gate. The naive rule merely accumulates into row `j`
of `Sʰ` according to `k[j]`; KDA additionally applies `Diag(αₜ)` to decay those
rows independently:

<StateChannelViz client:visible lang="en" />

`128` is a capacity/cost design choice, not a requirement of linear attention.
Increasing `dₖ` adds key feature axes; increasing `dᵥ` gives each axis a wider
value representation. The state and update cost per head grow as `dₖ×dᵥ`.
K3 sets both to 128, giving `16,384` state scalars per head. With that state in
view, run the same sentence again:

<LinearFlowViz client:visible lang="en" />

In “Math” mode, the diagram reduces the real <code>128×128</code> state to a
<code>dₖ=2, dᵥ=1</code> slice. A/B are full key arrows and ch₁/ch₂ are the two
rows of S. Colors inside a row only expose the provenance of contributions;
the real S does not preserve those colored pieces separately.

The step for "it" is the whole point: last section had a 0.72 line straight
to "cat", but S has no position axis, that line cannot be drawn, and the
read is a blend of the whole history.

### DeltaNet: adding a delete operation to the fixed state

The first problem with linear attention is not that it cannot remember, but
that it cannot delete. With the plain accumulation `S = Σ k·vᵀ`, writing the
same key direction twice leaves the old and new values together in S. Here A
is neither a token nor a query; it is a toy name for one direction in
the state space. From the first write token, the model computes a key vector
`k₁` and value vector `v₁`. The diagram abbreviates “`k₁` points along A and
`v₁` represents 1” as `A=1`. A therefore denotes the full key direction `kₐ`,
not one `chⱼ` from the preceding diagram. Only in a one-hot toy case would
`kₐ` line up with one channel; a real `kₐ` is usually dense across many
channels. The later `A=4` is a different write token whose
`k₂` points in approximately the same direction while `v₂` represents 4.
`A?` is a third, read token: its query q points along A and reads the value
currently bound to that direction through `Sᵀq`. These labels only make the
vector operations drawable; the model does not literally receive text tokens
named “A=1” or “A?”.

With plain accumulation, the contributions from `A=1` and `A=4` both remain
in S, so the next `A?` reads a blend rather than just the latest value.

DeltaNet replaces the write with the delta rule. Before writing the new value,
it reads the old value along the current k, computes the gap between old and
new, and writes that gap back. One common form is
`Sₜ = Sₜ₋₁ + β·k·(v − Sₜ₋₁ᵀk)ᵀ`. If the old readout is r, the new one is
`r′ = r + β(v−r) = (1−β)r + βv`. The update therefore erases a β fraction of
the old association and writes a β fraction of the new one; only β=1 performs
a full replacement.

Break one rebinding into its actual steps: when `A=4` arrives, DeltaNet uses
A's `k` to read the old value 1 and computes `4−1=3`. The diagram lets β vary.
At β=1, the same matrix update can be read either as `1+(4−1)=4`, or as
subtracting the old association 1 and adding the new association 4. The 2D
state rows show A and B contributing to the same numbers rather than depicting
them as independent slots:

<DeltaRuleViz client:visible lang="en" />

But DeltaNet only solves same-key rebinding. It does not answer the next
question: as more unrelated history fills the fixed-size S, which content
should decay and which should stay? That is the part KDA adds.

One more phenomenon has to be explicit first: real key vectors are generally
not perfectly orthogonal. Let <code>q<sub>A</sub> = k<sub>A</sub></code>, and let
the state contain both <code>k<sub>A</sub>v<sub>A</sub>ᵀ</code> and
<code>k<sub>B</sub>v<sub>B</sub>ᵀ</code>. Reading A gives
<code>o<sub>A</sub> = Sᵀq<sub>A</sub> = v<sub>A</sub> + (k<sub>A</sub>ᵀk<sub>B</sub>)v<sub>B</sub></code>.
The second term is B leaking into A; its size is set by the inner product of
the two keys. The diagram below reduces the geometry to 2D and sets
<code>v<sub>A</sub> = v<sub>B</sub> = 1</code>. Keep A fixed and drag B to see its
projection onto A enter the readout from S.

<KeyOverlapViz client:visible lang="en" />

### KDA: delta rule with per-channel gating

KDA is easiest to read as two changes stacked together. The bottom layer is
still DeltaNet's erase-before-write rule, which fixes same-key rebinding. On
top of that, KDA adds a per-channel gate `Diag(αₜ)` computed from the current
token. The exact order is old-state decay first, then the delta update:
`Sₜ = (I−βₜkₜkₜᵀ)·Diag(αₜ)·Sₜ₋₁ + βₜkₜvₜᵀ`.

The entries of α do not assign one switch to each toy “variable” A or B. The
real state is a matrix <code>S ∈ ℝ<sup>dₖ×dᵥ</sup></code>, while the gate is
a vector <code>αₜ ∈ (0,1)<sup>dₖ</sup></code>; each entry scales one key
channel of S. KDA also does not rotate non-orthogonal keys into orthogonal ones.
Instead, before a new write, it shrinks old state components channel by channel
so that some old influence on later readouts can decay. The diagram keeps the
same `A=1 → B=2 → A=4 → qₐ?` sequence used by Naive / DeltaNet and opens up a
minimal 2D interior:
<code>k<sub>A</sub>=(1/√2)[1,1]ᵀ</code> and
<code>k<sub>B</sub>=(1/√2)[1,−1]ᵀ</code>. Both A and B therefore span ch₁/ch₂;
neither equals one channel.

Before A=4 arrives, A=1 and B=2 are already superposed in one S; their colors
remain only to trace provenance. <code>Diag(α)</code> multiplies the ch₁/ch₂ rows
by α₁/α₂, so the A and B history inside each row shrinks together. The ordinary
delta rule then still runs: it reads the gated old association along the full
kₐ and, with β=1, writes the residual required to reach target value 4. Thus
qₐ still reads 4 at the end, while the change in qᵦ shows how channel-wise
decay affects another full key direction.

<KdaGateViz client:visible lang="en" />

Channels that may still matter can decay slowly, while clearly stale or
off-topic channels can give capacity back faster. The Kimi Linear paper reads
this gate as a learned position encoding replacing RoPE's fixed rotation. A
chunkwise kernel for the constrained DPLR form runs about twice as fast as the
general implementation, which is what lets KDA cover 69 layers.

### Attention Residual

First, what does it mean for a Transformer residual to pass information to the
next layer? An ordinary layer does not output only its new computation
<code>F<sub>ℓ</sub>(h<sub>ℓ−1</sub>)</code>; it adds the layer input back:

<code>h<sub>ℓ</sub> = h<sub>ℓ−1</sub> + F<sub>ℓ</sub>(h<sub>ℓ−1</sub>)</code>.

That sum becomes the next layer's input. Unrolled through depth, a deep layer
receives one vector containing the embedding plus all intermediate updates. It
does not receive separately addressable copies of “layer 2,” “layer 17,” and
“layer 53.” The identity path helps information and gradients flow, but all
depth history is still compressed into one residual stream. A shallow feature
needed at layer 93 must remain distinguishable after dozens of intervening
updates and additions.

Attention Residual keeps the ordinary residuals inside each group and adds a
separate **retrieval path across depth**. K3 groups every 12 layers into a
block and retains the embedding and earlier block outputs separately. A
learned pseudo-query for a later block assigns weights
<code>α<sub>ℓi</sub></code> and forms
<code>r<sub>ℓ</sub> = Σ<sub>i&lt;ℓ</sub> α<sub>ℓi</sub>v<sub>i</sub></code>.
The deep block can therefore reread a useful shallow representation directly
and give irrelevant blocks low weight, instead of relying only on a heavily
accumulated stream:

<AttnResViz client:visible lang="en" />

This adds two capabilities over the standard path: a shorter route between
deep and shallow blocks, and content-dependent selection so different deep
blocks can retrieve different prior representations. It reduces compression
and interference across depth; it does not replace ordinary residuals. Doing
the cross-block retrieval once per 12 layers keeps the added training and
inference cost modest.

### LatentMoE

Every FFN is MoE: 16 of 896 routed experts per token, plus 2 shared experts
that every token passes through. Within the routed pool, `16/896 ≈ 1.8%` are
selected. Separately, at the whole-model level, each token activates
`104B/2.8T ≈ 3.7%` of all parameters. Those percentages use different
denominators; against K2's 8 of 384 routed experts, sparsity moves up another
step.

Routing and dispatch do not run at the 7168-d hidden width: tokens first
project down to a 3584-d latent space, the router scores the half-width
vector, experts compute at half width, and the result projects back up. The
16-way all-to-all dispatch traffic and the expert weights both halve:

<MoeViz lang="en" />

Training with only 1.8% of the routed pool selected tends to be unstable; the
report uses three tools: RMSNorm, bounded SiTU-GLU activations, and Quantile
Balancing (expert quotas derive directly from router-score quantiles, with no
aux-loss coefficient left to tune).

### The training side

- Quantization-aware training starts at the SFT stage: MXFP4 weights with
  MXFP8 activations, so the released weights are already low-precision;
- The optimizer is Per-Head Muon, orthogonalized updates applied per
  attention head;
- The 1M context grows on a curriculum: 8K → 64K → 256K → 1M;
- RL covers general, agentic, and coding domains across multiple
  reasoning-effort levels; tools, prompts, memory, and subagent scaffolds
  keep changing during training so the model doesn't settle into one
  workflow.

## SGLang's day-0 adaptations

Inside an inference engine, the first thing this architecture creates is two
kinds of inference state:

| | MLA (24 layers) | KDA (69 layers) |
| --- | --- | --- |
| State shape | KV cache, appends per token | Recurrent state, fixed size |
| Growth | ~27 KB per token, append-only | ~54 MB per request (TP=8), overwritten in place each step |

Per-token KV appends and page-level sharing, the default assumptions of a
serving stack, hold for neither. SGLang's adaptations start here.

### Memory management for two state types

The old approach carves the memory pool into a KDA region and an MLA region at
startup, based on a guess. But KDA demand tracks concurrency while MLA demand
tracks total context length, so a skewed workload exhausts one side while the
other sits idle. SGLang switched to a unified pool: fixed KDA blocks allocate
from the left, MLA pages from the right, and the middle stays contiguous free
memory:

<PoolViz client:visible lang="en" />

Watch t=14: the split layout's MLA side runs out and R2 is evicted
mid-generation, while 6 KDA pages are still free. The unified pool has no
failures at the same moment.

On the prefix-cache (radix tree) side, KDA state is overwritten in place and
cannot be shared like KV. SGLang manages it with three operations:
copy-on-write (restore a shared checkpoint to a private slot before mutating),
snapshot (ping-pong buffered capture), and donate (hand the state to the radix
tree by slot index). The design is race-free by construction; details in the
blog below.

### Chunked pipeline prefill

TP8 has all 8 GPUs co-compute each chunk, with an AllReduce every layer, so
communication sits on the critical path. Chunked PP8 splits the model into 8
stages by layer and streams prompt chunks through; P2P hand-offs hide behind
the next chunk's compute (91% hidden in practice):

<PipelineViz client:visible lang="en" />

The warm-up bubble is paid once; at steady state a chunk ships every 2 columns.
Measured: PP8 prefill delivers 1.45–1.72× the throughput of a TEP8 node
(TEP = tensor + expert parallelism; the diagram simplifies it to plain TP).

### Decode context parallelism (DCP)

Decode's bottleneck is memory: under TP every GPU stores a full copy of the KV.
DCP shards by token position, so rank r keeps only the positions where
`p mod N = r`. Each decode step runs local attention first, then one
all-to-all exchanges the partial results; a log-sum-exp merge reproduces the
single-GPU output exactly:

<DcpViz client:visible lang="en" />

Measured on K3: DCP8 multiplies logical context capacity by 7.9×. On long
agent sessions TP8 collapses at 16 concurrent sessions, while DCP8 sustains 48
at 541 tok/s. KDA state has no position axis, so KDA layers stay TP-sharded —
with a hybrid model, parallelism is also per-layer hybrid.

### Single-GPU numbers

Before speculation, BS=1 decode went from 63.8 tok/s to about 113 tok/s
through four families of work (per-item gains from the blog in parentheses):

| Family | Representative moves |
| --- | --- |
| Launch elimination (+19.9 tok/s) | Collapse the MoE front into one GEMM, merge KDA projections, register-resident routing |
| Dedicated kernels (+10.3) | Fused KDA decode, W4A8 MoE, TMA attention-residual aggregation |
| Communication fusion (+27.6) | Fused all-reduce: multicast + NVLS in-switch reduction with residual/RMSNorm folded in |
| Overlap & prologue (+10.4) | GEMV–GEMM overlap, fused residual write-back, PDL attention arming |

On top of that, DSpark speculative decoding lifts BS=1 to about 423 tok/s
(~3.7×).

The combined serving frontier: PP8 prefill feeding TP8 decode reaches
2,808 tok/s per GPU (fp4); interactive configs trade down to 116+ tok/s per
user. One line from the blog worth remembering:

> All-reduce is a synchronization point, so a microsecond saved there converts
> one-for-one into step time; a kernel in another stream's overlap slack
> converts at roughly one-tenth.
