> **In one sentence**: speculative decoding lets a small model over-write and a
> big model grade a whole block per forward. At small batches verification is
> nearly free; at large batches every verify token costs real money — DSpark
> uses confidence to decide how many tokens each request is worth verifying,
> then packs the ragged verify work tightly.

## Why grading is cheaper than writing

Decode is memory-bound: a target-model forward mostly moves weights, so
verifying K tokens costs about the same as generating 1 (at small batch). So
let a drafter write K tokens first, and have the target grade them all in one
forward: the accepted prefix is banked, and the grading forward emits one
bonus token for free.

DSpark's drafter is a **semi-autoregressive block drafter**: the small model
also emits an entire block per forward instead of grinding token by token —
fast to draft, and acceptance stays high. Watch the race:

<SpecRaceViz client:visible lang="en" />

Rejected drafts (hatched) waste only cheap drafter compute; what they save is
expensive target forwards. At small batch, this trade always wins.

## The large-batch reversal: verification is no longer free

Once the batch grows, the GPU has no idle capacity — verify tokens now crowd
out other requests' compute. DSpark models the marginal cost of the M-th
verify token at load bs with an additive model `T(bs, K) = bias + α(bs) + θ(M)`,
calibrated by a one-time server profile — the real curve is a staircase of
shelves and risers, not a smooth line.

On the other side, the drafter carries a trained **confidence head** that
scores each position's survival probability. The scheduler trims per request:
positions whose expected value can't cover marginal cost simply aren't sent to
verify. Switch the load preset and watch the windows shrink — unevenly:

<TrimViz client:visible lang="en" />

Math drafts get accepted easily, so their windows survive; free-form writing
diverges, and at large batch is only worth verifying two or three tokens. That
matches production mixed traffic: gsm8k gets 5.24-token windows on average,
poetry gets 2.91, with utilization pinned at 0.88–0.97 of the acceptance
ceiling.

## The engineering floor: ragged packing + state replay

**Ragged verification**: after trimming, verify lengths differ per request,
but CUDA graphs demand fixed shapes. Instead of padding to the max block
length, front-pack the requests end to end and round up to a pre-captured tier:

<PackViz client:visible lang="en" />

**ReplaySSM** (K3-specific): KDA recurrent state is overwritten in place, so
rejected speculation must be rolled back. Instead of snapshotting whole states
(512 KB), store each draft step's compact raw inputs (16 KB — 32× smaller) and
replay the accepted prefix with a fold kernel — bit-identical to the
snapshotting baseline, and the freed scratch memory converts straight into
concurrency. With the overlap scheduler's async futures and device-side
barriers, iterations run back to back, about 1.5× tighter.

## Numbers at a glance

| Setting | Result |
| --- | --- |
| K3, BS=1 decode | 113 → **423 tok/s** (~3.7×, net of draft + verify overhead) |
| Chat workload, batch 256 | **+68%** throughput over the verify-all speculation baseline (mean accept 2.7 → 2.2 — verifying less on purpose, and faster for it) |
| DeepSeek-V4-Flash, H200 DP4 | Best throughput/latency frontier across the whole concurrency sweep, ahead of MTP and the non-spec floor |
