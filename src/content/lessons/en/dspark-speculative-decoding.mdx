> **TL;DR** Speculative decoding drafts with a small model and verifies a whole
> block per target forward. At small batches verification is nearly free; at
> large batches every verify token has a real cost. DSpark uses a confidence
> head to decide how many tokens each request is worth verifying, then packs
> the ragged verify work tightly into CUDA graphs.

## Why verification is cheaper than generation

Decode is memory-bound: a target-model forward mostly moves weights, so
verifying K tokens costs about the same as generating one (at small batch).
So a drafter writes K tokens first, and the target verifies them all in one
forward: the accepted prefix is committed, and the verify forward emits one
bonus token as a side effect.

DSpark's drafter is a semi-autoregressive block drafter: the small model also
emits a whole block per forward instead of generating token by token, which is
fast and keeps acceptance high. The comparison:

<SpecRaceViz client:visible lang="en" />

Rejected drafts (hatched) cost drafter compute; what they save is target
forwards. At small batch this trade is always favorable.

## Verification stops being free at large batches

Once the batch grows, the GPU has no idle capacity, and verify tokens compete
with other requests' compute. DSpark models the marginal cost of the M-th
verify token at load bs with an additive model
`T(bs, K) = bias + α(bs) + θ(M)`, where θ is measured per load by a one-time
server profile. The measured curve is a staircase of shelves and risers, not a
smooth line.

On the drafter side, a trained confidence head outputs a survival probability
for each draft position. The scheduler trims per request: positions whose
expected value falls below marginal cost are not sent to verify. Switch the
load preset to see the windows shrink, unevenly across requests:

<TrimViz client:visible lang="en" />

Math drafts get accepted easily, so their windows survive; free-form writing
diverges and is only worth verifying two or three tokens at large batch. This
matches the mixed-traffic measurements: gsm8k averages 5.24-token windows,
poetry 2.91, with utilization at 0.88–0.97 of the acceptance ceiling.

## Engineering: ragged packing and state replay

After trimming, verify lengths differ per request, and CUDA graphs require
fixed input shapes. Instead of padding every request to the maximum block
length, DSpark front-packs the verify requests into one compact buffer and
rounds up to the nearest pre-captured tier:

<PackViz client:visible lang="en" />

ReplaySSM addresses a K3-specific problem: KDA recurrent state is overwritten
in place, so rejected speculation needs a rollback. Rather than snapshotting
whole states (512 KB), store each draft step's compact raw inputs (16 KB, 32×
smaller) and replay the accepted prefix with a fold kernel; the output is
bit-identical to the snapshotting baseline. The freed scratch memory converts
directly into concurrency. With the overlap scheduler's async futures and
device-side barriers, iterations run without bubbles, about 1.5× tighter.

## Numbers

| Setting | Result |
| --- | --- |
| K3, BS=1 decode | 113 → 423 tok/s (~3.7×, net of draft + verify overhead) |
| Chat workload, batch 256 | +68% throughput over the verify-all speculation baseline (mean accept 2.7 → 2.2; verifying less, and faster for it) |
| DeepSeek-V4-Flash, H200 DP4 | Best throughput/latency frontier across the concurrency sweep, ahead of MTP and the non-spec floor |
