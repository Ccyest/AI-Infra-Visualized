## Background

### Sparse attention

When a model generates a token, attention looks back at the context again and
again. The KV cache was invented for this. It stores keys and values for every
earlier token at every layer. Full attention reads all of that KV. With a
32K-token context, every step reads 32K entries, so the cost of a step grows
with the context.

Sparse attention is an optimization built on the same attention mechanism. It
reads only part of the context. DeepSeek-V3.2 and GLM-5.1 use a design called
DeepSeek Sparse Attention (DSA). It works in two stages. First, a small module
called the indexer gives every earlier token a score for the current step. The
indexer has its own compact keys, so scoring the whole context is cheap.
Second, the model keeps the k tokens with the highest scores and runs attention
on those tokens only. k is fixed. It is 2048 in the configurations used here,
however long the context is.

The diagram shows sparse attention at work. The indexer scores the context at
every step. The k tokens with the highest scores are selected, and attention
runs on those tokens only. The cost of attention at each step is therefore
fixed and does not grow with the context.

### Indexer scoring

Each attention layer has an indexer. It keeps one small vector for every token,
called an index key. Take DeepSeek-V3.2 as an example. A token's hidden state
at a layer has 7,168 dimensions. $W_K$ is a 128 × 7,168 matrix, so multiplying
the hidden state by it gives 128 dimensions. Those 128 numbers are the token's
index key. It is computed once and stored on the GPU.

At each decoding step, the indexer computes two things for the current token.
The first is the query. $W_Q$ is an 8,192 × 1,536 matrix. Its input is a
1,536-dimensional vector that attention has already computed from the hidden
state. Its output has 8,192 dimensions and is cut into 64 parts of 128
dimensions, one part per head. The second is 64 weights, one per head. $W_w$ is
a 64 × 7,168 matrix that turns the hidden state into those 64 weights.

To score an earlier token, the indexer takes the dot product of its
128-dimensional key with each of the 64 query parts. That gives 64 numbers.
Negative ones are set to zero. The rest are multiplied by their head weights
and added up. The sum is the token's score. The 2,048 tokens with the highest
scores go to attention.

This starts the same way as attention, with a query and a key in a dot product.
The indexer is much lighter, though. It has no values and no softmax, because
it only needs one score per token. It also reads only 128 numbers per token.

<IndexerViz client:visible lang="en" />

A stored index key never changes. Only the queries and the weights are new at
each step. The same token can therefore score high at one step and low at the
next.

### The memory limit

Sparse attention cuts the work of each step. It does not cut the memory. Any
token may be selected later, so the KV of the whole context stays in GPU
memory.

GPU memory then decides how many requests can decode together. Once it is full,
sending more concurrent requests adds no throughput. The benchmark below shows
this as well. The baseline stops scaling at 32 concurrent requests.

## HiSparse

### Design and mechanism

SGLang's HiSparse was built to solve this problem. HiSparse stores the KV cache
in two places. CPU memory holds the full KV of every request. GPU memory holds
a small buffer for each request, called the hot device buffer, with a fixed
number of slots. The indexer's keys also stay on the GPU, because the indexer
still scores the whole context.

Each decoding step then runs five actions:

1. Score. The indexer scores every earlier token and keeps the top k.
2. Look up. HiSparse checks which of the top-k tokens are already in the
   buffer.
3. Swap in. The KV of each missing token is copied from CPU memory into the
   buffer. If the buffer is full, it replaces the least recently used token.
4. Attention. The model reads the top-k KV from the buffer and generates the
   next token.
5. Append. The new token's KV is copied to CPU memory, and its index key joins
   the index keys on the GPU.

The buffer has more slots than k, so it also keeps tokens that were selected in
recent steps. Because of how the indexer and model contexts behave, consecutive
steps select many of the same tokens. Most lookups therefore hit the buffer,
and each step moves only a few KV entries instead of the whole top-k.

<HiSparseFlowViz client:visible lang="en" />

Nothing stored earlier is rewritten during a step. The KV and the index key of
a token are computed once. Each step only appends one of each for the new
token.

With HiSparse, a request takes a fixed number of KV slots on the GPU, however
long its context is. The same GPU holds many more requests, and the decode
batch grows with it.

### Swap-in kernel

The swap-in step runs in every decoding step, so its latency matters. SGLang
implements it as a single CUDA kernel. The kernel does three things. It finds
the top-k tokens that are missing from the buffer. It picks the slots to free
with a least-recently-used (LRU) policy. It updates the page table and copies
the missing KV from CPU memory to the GPU.

Every miss costs one copy from CPU memory, so fewer misses mean a faster
swap-in. Two choices reduce the misses: a larger buffer and a better eviction
policy. The figure compares them on DeepSeek-V3.2. Growing the buffer from 2048
to 4096 slots removes a large share of the misses. With 4096 slots, LRU misses
less than FIFO and random eviction.

### Prefill-decode disaggregation

SGLang can run prefill and decode on separate instances. HiSparse works on the
decode instance. The prefill instance sends its KV directly into the CPU memory
of the decode instance. The decode GPU never holds the full KV, not even during
the transfer. The prefill instance needs no change.

## Results

The second benchmark sweeps input and output lengths on GLM-5.1-FP8. HiSparse
generates 1,720 to 2,320 tokens/s across the six configurations. The baseline
generates 352 to 752 tokens/s. The gap widens as the context grows. It is 3.1×
at the shortest configuration and more than 5× at 40K input with 20K output.

<SweepBenchViz client:visible lang="en" />

HiSparse is built for high concurrency. At low concurrency it is slower than
the baseline, because the extra copies cost more than the memory they save.
The concurrency chart above shows this at 32 concurrent requests and below.
HiSparse is still an experimental feature. It first supported the DSA model families,
DeepSeek-V3.2 and GLM-5.1. The
[HiSparse guide](https://docs.sglang.io/docs/advanced_features/hisparse_guide)
lists the models and flags supported today.
