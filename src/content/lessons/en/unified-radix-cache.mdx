## Background

Prefix caching reuses KV when requests share a token prefix. Under full
attention the rule is simple. KV only appends as tokens arrive, and shared
tokens will be reused, so we only need to compute the later-arriving tokens.

Hybrid models break the single rule. One request can carry full attention KV,
sliding window attention KV, and recurrent states at the same time. Full
attention KV is reusable across the whole matched prefix. Sliding window KV
covers only the trailing window. A recurrent state mutates in place as tokens
are read, so it is valid only at an exact checkpoint. Forcing one boundary
across all three either discards valid reuse or permits invalid reuse.

<ReuseRuleViz client:visible lang="en" />

These rules ship in different combinations. DeepSeek-V4 pairs FULL with SWA.
Kimi-K3 pairs FULL with MAMBA for its KDA recurrent state. Inkling runs all
three. Encoding each combination as a specialized cache class produces a
combinatorial matrix. Earlier implementations followed that pattern, with
duplicated logic everywhere. Thus a unified prefix cache is becoming an urgent
task.

## Unified Radix Cache

### Design and mechanism

Unified Radix Cache adds only one thing to the radix tree: every node carries
one slot per component. FULL's slot holds the KV page numbers for the node's
tokens, present on every node of a cached path. SWA's slot holds window-slot
numbers, present only on nodes inside the trailing window; on older nodes it
is an empty tombstone. MAMBA's slot holds the location of a checkpoint, the
recurrent state after reading all tokens up to this node. It is present only
where a checkpoint was actually stored.

<TreeReplayViz client:visible lang="en" />

### The safe reuse boundary

During matching, the core walks the canonical FULL path and treats every
visited node as a candidate boundary. Each active component votes through its
validator, and the boundary advances only when all validators accept the
candidate. A rejection does not stop the traversal, because a component may
accept a deeper node. Take SWA on a long cached prefix: shallow nodes have
slid out of the trailing window, so their window slots are tombstones and SWA
rejects them, while the last few nodes still hold a complete window and SWA
accepts there. Stopping at the first rejection would throw that deeper
boundary away.

<BoundaryVoteViz client:visible lang="en" />

This is why three reuse rules do not need three trees. The tree walks by
tokens alone. Reaching a node means the prefix matched that far. Whether the
node's data is usable is each component's own question, and each component
answers by checking its own slots. Data there means usable; a tombstone or
nothing means not. For SWA the check also requires a complete trailing window,
as the example above showed.

## HiCache across memory tiers

Components decide what can be reused; HiCache decides where the reusable
payload lives. Unified Radix Cache carries the same component identity across
GPU L1, Host L2, and an external L3 tier. Moving data between tiers changes
neither its prefix identity nor its reuse rule.

<TierFlowViz client:visible lang="en" />

A node's slot stores page numbers inside a pool; the node's key is the token
sequence itself. When L1 fills up, the controller copies the pages down one
tier, frees the device pages, and records the new location on the node. The
node is not deleted, so the tree still knows the prefix exists and on which
tier. Matching reads only the tree. Only actual reuse reads the slot: pages
still in L1 are used in place, and pages on a lower tier get freshly allocated
device pages, copied in, with the new page numbers written back to the slot.
In DeepSeek-V4, FULL and SWA are components with independent index spaces: in
the blog's normalized six-page example, the same tokens sit in the FULL tail
pages F4 and F5 but in the SWA slots S0 and S1, translated by the allocator at
runtime. The C4 and C128 compressed-KV pools plus indexer buffers and
compressor states, five auxiliary pools in all, register as sidecars, three
following FULL and two following SWA. Components translate indices; sidecars
copy them.

### Multi-turn benchmark

Multi-turn workloads grow a reusable conversational prefix every round. The
question is whether lower tiers preserve it after GPU capacity runs out. Here
is the comparison across two hybrid models and three storage tiers.

We can see that on DeepSeek-V4-Flash, L3 keeps the hit rate near 98%, holds

versus 9.4K for L1 only. On Inkling-Small it finishes at 96.8% and 67.1K.

## Session-aware eviction

LRU records which entries were touched recently, but doesn't know any
session-level context. Under memory pressure it can evict an active session's
KV while keeping unrelated entries. Session-aware eviction adds the missing
signal. Applications attach a stable `session_id` to every request. Calling
`/close_session` removes a session's references without immediately deleting
its entries. When a session is closed, the cache evicts that session's entries
first instead of following plain LRU order.

<SessionEvictViz client:visible lang="en" />

### SWE-bench results

On SWE-bench agent trajectories with HiCache, the session-aware configuration
lowers TTFT by 11.0% and 2.9% on DeepSeek-V4-Pro (batch 128 and 256), and by
13.5% and 16.6% on Qwen3.5-397B-A17B (batch 32 and 64). Device hit ratios rise
from about 42% to 51% for DeepSeek-V4-Pro at batch 128, and from about 5% to
34% for Qwen at batch 32. The baseline is ordinary HiRadixCache with LRU. The
comparison enables both Unified Radix Cache and `--enable-session-radix-cache`,
so the deltas are not an isolated ablation of session awareness.

## Rust tree core

The tree core runs on the scheduler's CPU critical path: every request pays
for traversal, lock bookkeeping, LRU updates, etc. As an interpreted language,
Python resolves types and attributes at runtime: every visit pays for
interpreter dispatch, attribute lookups, and reference counting. Rust, in
contrast, is compiled: types and field offsets are fixed at compile time, so
the same step becomes a few instructions over compact structs. The
experimental prototype therefore rebuilds the same state machine in Rust,
opt-in and L1-only: Rust owns the radix topology, lock accounting, intrusive
LRU lists, and eviction walks, while Python keeps request-to-token mappings
and physical KV allocation, applying the deferred actions Rust returns.

<RustSplitViz client:visible lang="en" />

Against the Python tree over a 200-turn synthetic conversation, TTFT drops
most where tree overhead dominates: 38% on the SWA workload (42% over turns
176–200), 10% on full attention (18% over the last 25 turns), and 5% on
hybrid SSM (7%), where a larger GPU forward hides most of the change. The
follow-up RFC #32710 keeps orchestration and pool management in Python behind
a replaceable tree core.
