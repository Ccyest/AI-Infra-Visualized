## Background

Suppose we give a model a long document and ask it to write a summary. After reading the summary, we ask about one detail in the same document. The questions differ, but the document at the start of both requests is the same. If its KV is still cached, the model can reuse it and compute only the new question. It does not need to run prefill over the document again. KV here means the key and value tensors that attention uses to read earlier tokens.

Keeping that KV on the GPU would make the next request easy. The problem is that the GPU also needs memory for model weights and requests it is currently serving. As more users bring more documents, it cannot keep every old prefix. SGLang HiCache saves some of them in CPU memory or external storage. When the document is needed again, it loads the KV back onto the GPU. This works only for matching token prefixes and compatible model state; similar wording is not enough. The [HiCache lesson](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hicache/) explains the cache management. Here we look at the hardware that makes each storage tier useful, and the cost of moving between them.

HiCache calls GPU memory L1, CPU memory L2, and its storage backend L3. These names describe where HiCache keeps data; L1 does not mean the small hardware L1 cache inside a GPU core. On the accelerators discussed here, GPU memory is HBM. **HBM is also a kind of DRAM.** We will compare how HBM connects to the GPU with how ordinary server DRAM connects to the CPU.

## Storage at a glance

Before looking inside the hardware, it helps to separate four properties. **Capacity** is how much data it can hold; **bandwidth** is how many bytes it can move per second; **latency** is how long one access takes; **cost per byte** is how much we pay for the same amount of storage. Different devices make different tradeoffs:

<div className="storage-glossary" tabIndex={0} role="region" aria-label="Storage terminology comparison">

| Term (what it is) | Advantages | Limitations | HiCache tier |
| --- | --- | --- | --- |
| **SRAM** (GPU on-chip memory) | Low latency | Small capacity, costly per byte | No separate tier |
| **HBM** (high-bandwidth GPU memory) | High bandwidth | Limited capacity, expensive | **L1** |
| **CPU DRAM** (host memory) | Larger, cheaper than HBM | Must copy KV to the GPU | **L2** |
| **Remote DRAM** (other machines’ memory) | Pooled capacity, shared access | Network bandwidth and latency | **L3** |
| **SSD** (stores data in NAND flash) | Large, cheap per byte, persistent | Slower I/O, finite write endurance | **L3** |

</div>

## HBM: feeding the GPU

### Why bandwidth matters

Return to the document example. While generating an answer, full attention repeatedly reads the document’s KV. A longer document means more historical KV to read at each decode step. The GPU can do a great deal of arithmetic in parallel, but it needs the data to arrive fast enough. This is why active KV belongs in high-bandwidth GPU memory.

Bandwidth tells us how many bytes can move per second. Latency tells us how long one access takes. They are related, but they are not the same measurement. A memory system can serve many reads at once and deliver high total bandwidth, while a thread waiting for one particular read still has to wait for that read to finish. This distinction helps explain what HBM improves.

### How HBM moves more data

HBM stacks several DRAM dies vertically and connects them with through-silicon vias, or TSVs. The stacks sit beside the GPU die in the same package. Dense wiring inside the package provides a wide interface between the GPU and memory. Short connections help reduce the energy spent moving each bit, and multiple memory channels let the GPU transfer more data at once. HBM sits close to the GPU’s compute die; it is not memory built inside that die. [Micron’s HBM3E overview](https://www.micron.com/about/blog/applications/ai/microns-hbm3e-powering-the-future-of-ai-with-high-bandwidth-memory)

Like ordinary DRAM, HBM needs periodic refresh to retain data; its wide interface increases aggregate bandwidth without eliminating the wait for each access. [Micron’s HBM memory architecture](https://assets.micron.com/adobe/assets/urn%3Aaaid%3Aaem%3A275edf31-79e3-4b6c-8bbd-a233babe9281/original/as/micron-hbm2e-memory-wp.pdf)

The cost of this design is in the package as well as the memory chips. There is limited space beside the GPU, stacking makes manufacturing and cooling harder, and the dense connections require advanced packaging. Adding HBM capacity usually means choosing a different accelerator design, rather than plugging in another memory module. HBM also loses its contents without power, just like other DRAM.

### What stays in L1

HBM is therefore a good place for KV that attention is using now. GPU kernels read chunks of that data into on-chip caches and shared memory as they work, while the full KV pool stays in GPU memory. If the GPU uses GDDR instead of HBM, its GPU memory still serves as HiCache L1; the software tier does not require one particular memory technology.

The GPU’s on-chip caches and shared memory use SRAM. A typical SRAM cell holds a bit in a transistor circuit while power is supplied, without DRAM’s periodic refresh. This makes it useful for fast on-chip access, but each bit takes much more silicon area. It can hold the small working blocks a kernel needs, not the entire history of many conversations. HiCache therefore does not treat it as another storage tier. [CUDA memory spaces](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#device-memory-spaces)

Once the answer is finished, the document’s KV may sit unused until the next question. Keeping it in HBM saves a future load, but also takes space away from new requests. HiCache can keep a copy in a lower tier and reclaim the GPU space when needed. That leads to the next question: where can we keep more KV without paying for more GPU memory?

## CPU memory: keeping more KV

### Where the extra capacity comes from

A server usually has DRAM chips on DIMM memory modules, connected to the CPU’s memory controller. We call this Host memory. The motherboard can provide several memory channels and slots, so capacity can be increased within the server’s supported configurations. Compared with HBM beside a GPU, this usually gives us more affordable capacity. The tradeoff is that this memory connects to the CPU, not directly to the GPU’s memory interface.

Adding capacity does not necessarily add bandwidth. Filling another memory channel can increase parallel access, while putting more capacity on an already populated channel does not add another channel. The DIMMs and CPU controller also limit the supported speed. Most conventional servers use DDR memory; platforms such as Grace use LPDDR5X. For HiCache, both serve the Host-memory role.

### The GPU still has to receive it

Suppose the next question arrives after the document’s KV has left the GPU, but a copy remains in Host memory. In a conventional PCIe server, loading it means reading Host DRAM, sending the bytes over PCIe, and writing GPU memory. The transfer can only run as fast as the slowest part of that path. If several GPUs share memory channels or an upstream link, they also compete for that bandwidth.

The difference is large enough to matter. NVIDIA lists **3.35 TB/s** of HBM bandwidth for H100 SXM. PCIe Gen 5 x16 provides **64 GB/s in one direction**, or 128 GB/s when both directions are added together. Dividing a decimal 1 GB by those bandwidths gives about **0.30 ms** for an ideal HBM access and **15.6 ms** for an ideal one-way PCIe transfer. These are bandwidth-only calculations, not measured KV restore times. They illustrate why having enough CPU memory does not give the GPU the same access speed as HBM. [H100 specifications](https://www.nvidia.com/en-us/data-center/h100/) · [Hopper PCIe specifications](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)

The connection depends on the machine. Grace Hopper, for example, uses NVLink-C2C between its CPU and GPU. That changes the available bandwidth and supports coherent access to both memories. It still takes a link traversal to reach CPU memory, so sharing an address space does not make CPU memory as fast as local HBM. We will return to the different links below. [Grace Hopper architecture](https://developer.nvidia.com/blog/nvidia-grace-hopper-superchip-architecture-in-depth/)

### Why L2 is still useful

HiCache does not need to read the document from CPU memory at every decode step. It loads the cached KV back onto the GPU, then attention uses that GPU copy. **The cost to compare is one restore against another prefill over the document.** If restoring is cheaper, L2 saves time even though its path to the GPU is much slower than HBM access.

Where the Host buffer is allocated also matters. On a server with several CPU sockets, allocating it near the GPU’s socket avoids an extra trip across the CPU-to-CPU link. This is NUMA locality. The buffer can also use pinned memory, whose pages stay fixed for device transfers. Pinning helps the transfer path; it does not make the DRAM cells faster, and pinning too much memory leaves less flexibility for the rest of the system. [CUDA Host–device transfer guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

## L3: keeping a larger history

### Using memory on other machines

CPU memory is larger, but it is not unlimited either. If users keep returning to many different documents, we may want to preserve more history than one inference instance can hold. One option is to pool DRAM from other machines into a cache service. For example, the [HiCache multi-turn benchmark](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/) uses a 500 GiB Mooncake Store memory tier. It is L3 because it is the storage backend, even though the data still lives in DRAM.

A shared service can also make the document’s KV available to another inference instance. That instance no longer has to compute the prefix just because it did not handle the earlier request. The cost is a network read: looking up the data, reading remote memory, and transferring it through the NICs and network. RDMA can reduce CPU processing and extra copies along this path, but the bytes still have to cross the network.

This is why local L2 and remote DRAM L3 can perform very differently despite using the same type of memory cell. It also matters whether a backend is actually shared. Compatible instances need access to the same cache namespace and data format; a local file backend does not provide that simply by being called L3. [HiCache tier sharing](https://docs.sglang.io/docs/advanced_features/hicache_design#tier-sharing-scope)

### Using SSDs

Another option is to use SSDs for documents that are worth keeping but are read less often. An SSD stores data in NAND flash, with a controller managing reads, writes, and physical locations. NAND retains data without power and usually costs less per byte than DRAM. The tradeoff is a slower access mechanism, especially for writes and updates.

A NAND cell stores charge that changes the transistor’s threshold voltage. Reading the cell means identifying which voltage range it falls into. TLC distinguishes eight states to store three bits per cell; QLC distinguishes sixteen states to store four. More states give us more capacity per cell, but leave less room between adjacent states. Writing and distinguishing those states becomes more demanding, which affects speed, error correction, and endurance. [KIOXIA’s cell explanation](https://www.kioxia.com/en-jp/rd/technology/multi-level-cell.html) · [NAND endurance](https://americas.kioxia.com/content/dam/kioxia/en-us/business/memory/asset/KIOXIA-SSD-NAND-Endurance-Tech-Brief.pdf)

Updating data creates another cost. NAND reads and programs pages, but erases larger blocks containing many pages. To update page A, the SSD usually writes the new A elsewhere and marks the old A invalid. Later, it reclaims the old block. If that block still holds a valid page B, the controller must copy B out before erasing the block. The application only changed A, but the SSD also wrote B. These extra writes are called **write amplification**. They use bandwidth and device endurance, and background garbage collection can make some requests take longer. The NAND animation above steps through this A/B example. [KIOXIA on garbage collection](https://blog-us.kioxia.com/post/2025/06/20/how-fdp-can-reduce-garbage-collection-and-ultimately-waf-use-fdp-enabled-kioxia-xd8-series-data-center-ssds)

This is also why “NVMe SSD” is not enough to predict performance. NVMe describes the command interface, not the storage medium. A large sequential read, a small random read, and a sustained mix of reads and writes stress the same SSD differently. A remote SSD service adds network and service time on top of the device I/O.

For HiCache, writing every discarded prefix to SSD would spend bandwidth and endurance on data that might never be used again. Selective backup is useful when likely reuse justifies that cost. Flash retaining bytes across power loss is a separate issue from a KV service recovering after restart: the service also needs its metadata and compatible model state.

These tiers can hold copies of the same KV at the same time. Backing up the document to L2 does not require deleting its GPU copy immediately. Loading it from L3 does not require deleting the L3 copy either. We choose which copies to retain based on the available space and how likely the document is to be used again.

## Moving KV back to the GPU

We have chosen where to keep the document’s KV. Now the next question arrives, and we need that KV on the GPU again. To understand the cost, we need to separate two things: **which hardware links the bytes cross, and how the transfer is carried out.** PCIe and NVLink are links. DMA and RDMA describe ways to move data over hardware links. A single RDMA transfer can cross a network and then PCIe.

### Which devices does the link connect?

| Interconnect | What it connects | Advantage | Constraint |
| --- | --- | --- | --- |
| PCIe | CPUs, GPUs, NICs, and NVMe controllers through a PCIe topology | Widely available and supports several device types | Negotiated link width, generation, switches, and shared upstream links limit throughput |
| GPU NVLink / NVSwitch | GPUs within a supported NVLink fabric | High aggregate bandwidth for GPU peer traffic | Requires compatible GPUs and topology; a GPU–GPU link does not accelerate a CPU–GPU PCIe segment |
| NVLink-C2C | CPU and GPU chips in platforms such as Grace Hopper | High-bandwidth coherent access across CPU and GPU memory | Platform-specific; accessing Host memory still consumes link bandwidth and has a different cost from local HBM |

A fast link only helps the bytes that actually cross it. If two GPUs have NVLink between them, a Host-to-GPU copy may still use PCIe. Adding GPU-to-GPU bandwidth does not speed up that copy. On Grace Hopper, the CPU–GPU connection itself is NVLink-C2C, so it changes this part of the transfer. Before comparing bandwidth numbers, check which devices each link connects. [NVIDIA topology guidance](https://docs.nvidia.com/datacenter/dcgm/latest/learn/core-services/topology-and-links.html) · [Grace Hopper architecture](https://developer.nvidia.com/blog/nvidia-grace-hopper-superchip-architecture-in-depth/)

### DMA: letting hardware do the copy

To copy KV from CPU memory to GPU memory, the CPU does not need to load and store every byte itself. Software can submit a transfer and let a DMA engine do the copying. The bytes still cross the memory interfaces and interconnect, but CPU cores are free to do other work. If the source is ordinary pageable Host memory, the CUDA runtime may first copy it into a pinned buffer whose physical pages stay fixed during the transfer. Keeping KV in a reusable pinned pool can avoid that staging copy and support asynchronous transfers. Pinning has a cost, which is why a long-lived pool is preferable to repeatedly pinning small buffers. The GPU must still wait for the relevant transfer to finish before reading its result. [CUDA transfer guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

There is another cost when KV is scattered across many pages: submitting many small copies. HiCache also provides GPU-assisted transfer kernels. GPU threads gather the required KV and write it to the destination layout, handling the difference between Host and GPU layouts in the process. This can reduce the overhead of submitting individual copies, but it uses GPU execution resources that inference also needs. Whether it wins depends on the amount of data, the layout, and the concurrent compute workload. Neither a DMA copy nor a GPU kernel increases the link’s physical bandwidth. [HiCache transfer design](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)

### TCP and RDMA: receiving remote KV

If the document’s KV lives on another machine, we first need to receive it over the network. A conventional TCP socket path uses the operating system’s network stack and typically copies received data from socket buffers into the application buffer. TCP is widely supported and has mature deployment tools. At high throughput, however, protocol processing and those memory copies can consume substantial CPU time and memory bandwidth. Offloads and optimized APIs can reduce this work.

With RDMA, software registers a memory region with a compatible NIC, making it available for authorized device access. The NIC can then place incoming data into that region with less CPU involvement and fewer intermediate copies. This requires compatible hardware and network setup, such as InfiniBand or Ethernet with RoCE. Software still manages connections, transfer queues, and completion events. Most importantly for this example, **if RDMA puts the KV in Host memory, we still need the Host-to-GPU transfer.** RDMA alone does not tell us where the received bytes end up. [NVIDIA RDMA programming guide](https://networking-docs.nvidia.com/doca/archive/3-4-0/rdma-aware-networks-programming-guide)

### GPUDirect: skipping the Host buffer

If the GPU is going to consume the data, can the NIC put it straight into GPU memory? GPUDirect RDMA enables this on supported systems. It removes the Host staging buffer and the subsequent Host-to-GPU copy from that path. The network transfer and GPU-side PCIe traffic remain. It also requires a compatible GPU, NIC, driver, and PCIe topology, and the application must ensure that reception is complete and visible before a GPU kernel reads the data. [GPUDirect RDMA](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)

GPUDirect Storage addresses a similar problem for storage reads and writes. Applications integrate cuFile so that supported storage paths can transfer data between storage and GPU memory without a CPU-memory staging buffer. This saves Host memory traffic, but requires a compatible storage stack; fallback paths may still stage through Host memory. NAND still takes time to read, and if the CPU must first parse or transform the data, bypassing it may offer less benefit. [GPUDirect Storage design](https://docs.nvidia.com/gpudirect-storage/design-guide/index.html)

### What HiCache actually skips

In the Host-staged HiCache path discussed here, L3 first fills the Host KV pool, then HiCache copies the data to the GPU. A zero-copy backend integration lets the storage client fill this pool directly, instead of filling a separate application buffer and copying it into the pool. It removes that extra Host copy; the Host-to-GPU transfer remains. The `direct` I/O backend name can also be misleading: it means standard CUDA copies between Host and GPU, not GPUDirect Storage. The `kernel` backend uses the GPU-assisted transfer kernels described above. [HiCache I/O backends](https://docs.sglang.io/docs/advanced_features/hicache_design)

These distinctions make it easier to choose an optimization. If the extra Host copy is expensive, writing directly into the KV pool can help. If Host-to-GPU bandwidth is already full, a faster network alone cannot fix it. Sending data directly to GPU memory can remove Host traffic, but the cache backend must support that path and supply the layout and synchronization the GPU needs.

## Following one restore

Now suppose only L3 still holds the document’s KV. In the Host-staged path, HiCache first reads it into the Host pool, then copies it into the GPU KV pool. Attention can use each required part only after it arrives. The animation divides the document’s KV into four pages so that we can follow when each copy appears. Switching the hit location to L1 or L2 removes the transfers that are no longer needed.

<TransferViz client:visible lang="en" />

This also explains why HiCache uses different layouts on the two sides. The GPU runs the model one layer at a time, so grouping KV by model layer helps it read the data for that layer. A storage request, however, fetches the cached data for a page of tokens across layers. Putting that page together in Host memory lets the backend read or write a larger contiguous block instead of many scattered pieces.

A HiCache page here means a group of tokens. It is different from an operating-system memory page or a physical NAND page. Combining transfers reduces the number of I/O submissions and spreads their fixed cost over more bytes. The amount of KV to move stays the same. [HiCache layout and transfer design](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)

We can also start useful work before the entire restore finishes. Once the first model layer’s KV reaches the GPU, the GPU can compute that layer while later layers’ KV is still moving. Earlier still, L3 prefetch can read data while a request waits to be scheduled. Both reduce how long the request waits for I/O. They cannot hide every transfer: if a layer’s KV arrives after the GPU needs it, computation still pauses.

## Is restoring faster than recomputing?

Finding the document in L3 is only the first step. We still need to compare the wait for its KV with the prefill work that reuse would save. An SSD read can be worthwhile if recomputing a long prefix takes even longer. A cache hit can also be slower than recomputation when the transfer is expensive and the prefix is cheap to compute.

Consider a simplified example with decimal 1 GB of KV. At an effective L3-to-Host bandwidth of 10 GB/s, the first transfer takes 100 ms. At an effective Host-to-GPU bandwidth of 50 GB/s, the second takes 20 ms. If they run one after the other, restoring takes 120 ms. If prefill would take 150 ms, reuse saves 30 ms. But if prefill only takes 50 ms, waiting 120 ms would be worse. Prefetch changes the comparison: completing 80 ms of the L3 read before scheduling leaves 40 ms to wait. These numbers are teaching assumptions, not hardware specifications or HiCache benchmark results.

<CostViz client:visible lang="en" />

Try reducing the recomputation time in the calculator, or increasing the amount of KV to restore. The comparison can reverse without changing the storage device. A real deployment also needs to account for lookup time, queueing, transfer startup, and overlap with computation. KV size and prefill time depend on the model and workload, so they should be measured together rather than inferred from peak device bandwidth.

For our document example, the useful storage choice depends on what happens after this request:

- **The same instance reads it repeatedly:** keeping an L2 copy can avoid repeated L3 reads, provided Host capacity and Host-to-GPU bandwidth are sufficient.
- **Several instances need it:** a shared L3 can make the cached prefix available across instances. This requires a backend and configuration that support sharing.
- **It is part of a large, less frequently read history:** SSD capacity can be useful if restoring still saves enough prefill work to justify the backup and read costs.
- **Host memory is scarce:** buffer-only mode releases Host slots after staging instead of retaining an L2 copy. It saves Host capacity, but the next request cannot hit that L2 copy and may need L3 again. The Host staging step still exists.

After the restore, the GPU uses the document’s KV from its own memory and computes the new question. The time saved comes from avoiding the document’s prefill. Keeping more history gives HiCache more opportunities to do that; choosing which copies to keep and when to load them determines whether those opportunities actually save time.
