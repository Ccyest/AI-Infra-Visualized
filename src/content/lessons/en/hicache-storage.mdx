## Background

Suppose we give a model a long document and ask it to write a summary. After reading the summary, we ask about one detail in the same document. The questions differ, but the document at the start of both requests is the same. If its KV is still cached, the model can reuse it and compute only the new question. It does not need to run prefill over the document again. KV here means the key and value tensors that attention uses to read earlier tokens.

Keeping that KV on the GPU would make the next request easy. The problem is that the GPU also needs memory for model weights and requests it is currently serving. As more users bring more documents, it cannot keep every old prefix. SGLang HiCache saves some of them in CPU memory or external storage. When the document is needed again, it loads the KV back onto the GPU. This works only for matching token prefixes and compatible model state; similar wording is not enough. The [HiCache lesson](https://yichizhang.dev/AI-Infra-Visualized/en/lessons/hicache/) explains the cache management. Here we look at the hardware that makes each storage tier useful, and the cost of moving between them.

HiCache calls GPU memory L1, CPU memory L2, and its storage backend L3. These names describe where HiCache keeps data; L1 does not mean the small hardware L1 cache inside a GPU core. On the accelerators discussed here, GPU memory is HBM. **HBM is also a kind of DRAM.** We will compare how HBM connects to the GPU with how ordinary server DRAM connects to the CPU.

## Storage at a glance

Before looking inside the hardware, it helps to separate four properties. **Capacity** is how much data it can hold; **bandwidth** is how many bytes it can move per second; **latency** is how long one access takes; **cost per byte** is how much we pay for the same amount of storage. Different devices make different tradeoffs:

<div className="storage-glossary" tabIndex={0} role="region" aria-label="Storage terminology comparison">

| Term and meaning | Main advantages | Main limitations | Use in HiCache |
| --- | --- | --- | --- |
| **SRAM** (Static Random-Access Memory): small memories inside the GPU chip | Low latency and high on-chip bandwidth | Large silicon area per bit, so capacity is small and costly | Hardware caches and kernel working data; not a separate HiCache tier |
| **HBM** (High Bandwidth Memory): stacked DRAM beside the GPU chip | High aggregate bandwidth for reading large amounts of KV | Expensive packaging and limited room for capacity; cannot expand by adding DIMMs | **L1**: KV being used by the GPU and prefixes retained in GPU memory |
| **CPU DRAM**: DRAM means Dynamic Random-Access Memory; CPU memory commonly uses DDR or LPDDR | Usually offers more capacity at a lower cost per byte than HBM | GPU reads or copies must cross the CPU–GPU link; CPU memory bandwidth is not the same as transfer bandwidth to the GPU | **L2**: reusable local KV copies and transfer buffers |
| **Remote DRAM**: memory on other machines, accessed through a cache service | Pools capacity and can share KV across inference instances | Adds network and service latency; limited by NICs and network bandwidth | One option for **L3**, such as a distributed memory cache |
| **SSD / NAND flash**: an SSD is a solid-state drive; NAND flash is the medium it uses to store data | Large capacity, usually cheaper per byte than DRAM, and retains data without power | Higher access latency than memory, plus extra work during updates and finite write endurance | Another option for **L3**, for retaining a larger history |

</div>

## HBM: feeding the GPU

### Why bandwidth matters

Return to the document example. While generating an answer, full attention repeatedly reads the document’s KV. A longer document means more historical KV to read at each decode step. The GPU can do a great deal of arithmetic in parallel, but it needs the data to arrive fast enough. This is why active KV belongs in high-bandwidth GPU memory.

### How HBM moves more data

HBM stacks several DRAM dies vertically and connects them with through-silicon vias, or TSVs. The stacks sit beside the GPU die in the same package. Dense wiring inside the package provides a wide interface between the GPU and memory. Short connections help reduce the energy spent moving each bit, and multiple memory channels let the GPU transfer more data at once. HBM sits close to the GPU’s compute die; it is not memory built inside that die. [Micron’s HBM3E overview](https://www.micron.com/about/blog/applications/ai/microns-hbm3e-powering-the-future-of-ai-with-high-bandwidth-memory)

<HbmStackViz client:visible lang="en" />

Inside each die, a typical DRAM cell stores one bit as charge in a capacitor, with a transistor controlling access. Charge leaks away, so the memory must refresh it regularly. Cells are arranged in rows within banks, which are groups that can handle some operations independently. To read a row, the memory activates it and senses the stored charge; switching rows in the same bank may first require closing the old row, a step called precharge. HBM still does this work. Its wide interface helps move many bytes in parallel, but does not remove the time needed to access the cells. [Micron’s HBM memory architecture](https://assets.micron.com/adobe/assets/urn%3Aaaid%3Aaem%3A275edf31-79e3-4b6c-8bbd-a233babe9281/original/as/micron-hbm2e-memory-wp.pdf)

The cost of this design is in the package as well as the memory chips. There is limited space beside the GPU, stacking makes manufacturing and cooling harder, and the dense connections require advanced packaging. Adding HBM capacity usually means choosing a different accelerator design, rather than plugging in another memory module. HBM also loses its contents without power, just like other DRAM.

### What stays in L1

HBM is therefore a good place for KV that attention is using now. GPU kernels read chunks of that data into on-chip caches and shared memory as they work, while the full KV pool stays in GPU memory. If the GPU uses GDDR instead of HBM, its GPU memory still serves as HiCache L1; the software tier does not require one particular memory technology.

The GPU’s on-chip caches and shared memory use SRAM. A typical SRAM cell holds a bit in a transistor circuit while power is supplied, without DRAM’s periodic refresh. This makes it useful for fast on-chip access, but each bit takes much more silicon area. It can hold the small working blocks a kernel needs, not the entire history of many conversations. HiCache therefore does not treat it as another storage tier. [CUDA memory spaces](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#device-memory-spaces)

Once the answer is finished, the document’s KV may sit unused until the next question. Keeping it in HBM saves a future load, but also takes space away from new requests. HiCache can keep a copy in a lower tier and reclaim the GPU space when needed. That leads to the next question: where can we keep more KV without paying for more GPU memory?

## CPU memory: keeping more KV

### Where the extra capacity comes from

A server usually has DRAM chips on DIMM memory modules, connected to the CPU’s memory controller. We call this Host memory. The motherboard can provide several memory channels and slots, so capacity can be increased within the server’s supported configurations. Compared with HBM beside a GPU, this usually gives us more affordable capacity. The tradeoff is that this memory connects to the CPU, not directly to the GPU’s memory interface.

DGX H200 uses DDR5 DIMMs. Vera Rubin uses LPDDR5X on replaceable SOCAMM modules, with NVLink-C2C connecting its CPUs and GPUs. The modules and links change, but Host memory still sits on the CPU side. The diagram compares one DGX H200 server with one Vera Rubin NVL72 rack; the expanded view shows their local connections. [DGX H200 architecture](https://docs.nvidia.com/dgx/dgxh100-user-guide/introduction-to-dgxh100.html) · [Vera memory design](https://www.nvidia.com/en-us/data-center/vera-cpu/) · [Vera Rubin specifications](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/)

### The GPU still has to receive it

Suppose the next question arrives after the document’s KV has left the GPU, but a copy remains in Host memory. In a conventional PCIe server, loading it means reading Host DRAM, sending the bytes over PCIe, and writing GPU memory. The transfer can only run as fast as the slowest part of that path. If several GPUs share memory channels or an upstream link, they also compete for that bandwidth.

Let’s put numbers to this difference. 
Suppose the GPU needs to read 1 GB of KV data, using decimal units throughout. The ideal time is data size ÷ bandwidth. If the data is already in H100 SXM’s HBM, its listed bandwidth of 3.35 TB/s = 3,350 GB/s gives 1 ÷ 3,350 seconds ≈ 0.30 ms to read it. If the same 1 GB is stored in CPU memory and must first be copied to the GPU over PCIe Gen 5 x16, the listed one-way bandwidth of 64 GB/s gives 1 ÷ 64 seconds ≈ 15.6 ms for that transfer alone. The advertised 128 GB/s adds both directions together and does not apply to this one-way copy. These estimates assume full bandwidth utilization and ignore other overheads; they are not measured KV restore times. CPU memory can provide room for more KV data, but bringing that data back to the GPU still takes time. H100 specifications · Hopper PCIe specifications

### Why L2 is still useful

HiCache does not need to read the document from CPU memory at every decode step. It loads the cached KV back onto the GPU, then attention uses that GPU copy. **The cost to compare is one restore against another prefill over the document.** If restoring is cheaper, L2 saves time even though its path to the GPU is much slower than HBM access.

Where the Host buffer is allocated also matters. On a server with several CPU sockets, allocating it near the GPU’s socket avoids an extra trip across the CPU-to-CPU link. This is NUMA locality. The buffer can also use pinned memory, whose pages stay fixed for device transfers. Pinning helps the transfer path; it does not make the DRAM cells faster, and pinning too much memory leaves less flexibility for the rest of the system. [CUDA Host–device transfer guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

## L3: keeping a larger history

### Using DRAM on other machines

Remote DRAM gives us access to memory on other machines, so we can keep more KV than one machine can hold. DRAM itself supports fast reads and writes. A shared cache service also lets several inference instances reuse the same KV instead of each computing and storing a separate copy.

The tradeoff is the extra network access. Reading remote DRAM means locating the data and transferring it back to the local machine. This adds waiting time and can be limited by network bandwidth, even though the memory chips are fast. DRAM also usually costs more per GB than SSDs and loses its contents without power.

In HiCache, a remote DRAM service such as [Mooncake Store](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/) can serve as L3. Software saves reusable KV there. On a later hit, it reads the KV into local Host memory and then copies it to the GPU. Sharing requires the instances to access the same cache and use compatible models and KV formats; calling a backend L3 does not automatically make it shared. [HiCache tier sharing](https://docs.sglang.io/docs/advanced_features/hicache_design#tier-sharing-scope)

### Using SSDs

SSDs are another option for documents that are worth keeping but are read less often. They offer large capacity at a lower cost per GB than DRAM and retain data without power. When there is too much KV to keep affordably in GPU or CPU memory, SSDs can hold history that may be useful again later.

The tradeoff is slower reads and writes than DRAM, and writes consume the device’s finite endurance. SSDs therefore suit historical KV that is used less often. KV that attention is actively reading should still stay in GPU memory. If the SSD is on another machine, reading it also takes a network transfer.

In HiCache, SSDs can provide the storage for L3. Software writes KV worth keeping to the backend and, on a later hit, restores it through Host memory to the GPU. There are two decisions: when writing, favor KV likely to be reused; when reading, compare the restore time with recomputation. Writing KV that is never reused wastes resources, and waiting for an SSD read may not pay off when recomputation is cheap.

These tiers can hold copies of the same KV at the same time. Backing up the document to L2 does not require deleting its GPU copy immediately. Loading it from L3 does not require deleting the L3 copy either. We choose which copies to retain based on the available space and how likely the document is to be used again.

## Moving KV back to the GPU

Finding cached KV does not mean the GPU can use it immediately. The data may still be in CPU memory or on another machine. Software has to bring it back, and the request may wait while that happens. To reduce the wait, we need to know what takes the time: the transfer itself, CPU work involved in moving the data, or extra copies between buffers. The techniques below target different parts of this cost.

### Start with the path the data takes

| Transfer | Common connection | What it helps with |
| --- | --- | --- |
| Host memory → GPU | PCIe; NVLink-C2C on platforms such as Grace Hopper | Moving CPU-side data to the GPU |
| GPU → GPU | NVLink / NVSwitch on supported systems | Exchanging data between GPUs |
| Another machine → this machine | NICs and a network | Fetching remote KV; a Host-to-GPU transfer may still follow |

This matters because a faster connection only helps transfers that use it. If restoring KV is limited by Host-to-GPU PCIe bandwidth, faster GPU-to-GPU NVLink will not fix it. NVLink-C2C changes the CPU-to-GPU connection itself, but requires a platform that provides it. Software can avoid unnecessary transfers and use bandwidth more efficiently; it cannot raise the link’s physical limit. [NVIDIA topology guidance](https://docs.nvidia.com/datacenter/dcgm/latest/learn/core-services/topology-and-links.html)

### Freeing the CPU: DMA and pinned memory

The CPU also has requests to schedule and other work to do. Making its cores copy every byte would consume time that could be spent on that work. With DMA, software submits a transfer task and a hardware engine moves the data. The CPU can do other work while the transfer runs. DMA reduces CPU involvement; the bytes still have to cross the link, and the GPU must wait for the transfer to finish before using them.

There can still be an extra copy before DMA starts. With ordinary Host memory, CUDA may first copy the data into a pinned buffer: memory whose pages are kept fixed for device access. Keeping a reusable pinned pool avoids repeatedly preparing that buffer and, when the data is already in it, avoids the staging copy. It also supports asynchronous transfer submission. Pinning consumes system resources, so software normally reuses a limited pool rather than pinning all memory. [CUDA transfer guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

Scattered KV introduces another cost: submitting a separate transfer for every small piece. HiCache can instead use GPU transfer kernels to gather those pieces and put them into the layout needed at the destination. This reduces individual copy submissions, but the kernels use GPU resources that inference also needs. Software must compare that saving with the effect on concurrent computation. [HiCache transfer design](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)

### Reducing network processing: TCP and RDMA

For remote KV, TCP sockets are a common starting point: widely supported and familiar to deploy. In a conventional receive path, the operating system handles network processing and the data is copied from its receive buffer into the application’s buffer. When many requests fetch KV at once, this processing and copying can consume substantial CPU time and memory bandwidth.

RDMA is useful when that CPU work and copying become expensive. Software registers a destination buffer with a compatible NIC, allowing the NIC to place incoming data directly into it. This reduces CPU processing and intermediate copies, but requires suitable NICs, network configuration, and backend support. Software still checks when the transfer has completed. If the destination is Host memory, the KV still needs a separate transfer to the GPU. [NVIDIA RDMA programming guide](https://networking-docs.nvidia.com/doca/archive/3-4-0/rdma-aware-networks-programming-guide)

### Skipping a Host-memory stop: GPUDirect

If only the GPU needs the incoming data, staging it in Host memory creates an extra step. On supported systems, GPUDirect RDMA lets the NIC write directly into GPU memory. This removes the Host buffer and the later Host-to-GPU copy. The network transfer still takes time, and the GPU, NIC, drivers, and their connections must support the path. Software must also ensure the data is ready before a GPU kernel reads it. [GPUDirect RDMA](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)

GPUDirect Storage applies the same idea to storage: avoid reading data into Host memory only to copy it to the GPU. Software integrates the cuFile interface and uses a compatible storage path to transfer data directly into GPU memory. This can reduce Host memory traffic, but does not make the SSD itself faster. Unsupported paths may still use Host staging, and data that first needs CPU processing may still need to go through Host memory. [GPUDirect Storage design](https://docs.nvidia.com/gpudirect-storage/design-guide/index.html)

### Applying this to HiCache

The HiCache path discussed here restores KV from L3 into the Host KV pool, then copies it to the GPU. A backend with zero-copy integration can write straight into that pool instead of first filling another application buffer and then copying into the pool. This removes one extra copy inside Host memory. It does not remove the Host-to-GPU transfer or turn the path into GPUDirect. [HiCache data paths](https://docs.sglang.io/docs/advanced_features/hicache_design)

Choose an optimization based on where the request is waiting. If CPU receive processing is costly, investigate RDMA. If extra buffer copies dominate, investigate pinned pools or direct writes into the KV pool. If Host-to-GPU bandwidth is already saturated, removing CPU work alone will not solve it: reducing the bytes transferred or using a faster connection matters more. Compare the end-to-end restore time with recomputation, rather than choosing a technique by name.

## Following one restore

Now suppose only L3 still holds the document’s KV. In the Host-staged path, HiCache first reads it into the Host pool, then copies it into the GPU KV pool. Attention can use each required part only after it arrives. The animation divides the document’s KV into four pages so that we can follow when each copy appears. Switching the hit location to L1 or L2 removes the transfers that are no longer needed.

<TransferViz client:visible lang="en" />

This also explains why HiCache uses different layouts on the two sides. The GPU runs the model one layer at a time, so grouping KV by model layer helps it read the data for that layer. A storage request, however, fetches the cached data for a page of tokens across layers. Putting that page together in Host memory lets the backend read or write a larger contiguous block instead of many scattered pieces.

A HiCache page here means a group of tokens. It is different from an operating-system memory page or a physical NAND page. Combining transfers reduces the number of I/O submissions and spreads their fixed cost over more bytes. The amount of KV to move stays the same. [HiCache layout and transfer design](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)

We can also start useful work before the entire restore finishes. Once the first model layer’s KV reaches the GPU, the GPU can compute that layer while later layers’ KV is still moving. Earlier still, L3 prefetch can read data while a request waits to be scheduled. Both reduce how long the request waits for I/O. They cannot hide every transfer: if a layer’s KV arrives after the GPU needs it, computation still pauses.

## Is restoring faster than recomputing?

Finding the document in L3 is only the first step. We still need to compare the wait for its KV with the prefill work that reuse would save. An SSD read can be worthwhile if recomputing a long prefix takes even longer. A cache hit can also be slower than recomputation when the transfer is expensive and the prefix is cheap to compute.

Consider a simplified example with decimal 1 GB of KV. At an effective L3-to-Host bandwidth of 10 GB/s, the first transfer takes 100 ms. At an effective Host-to-GPU bandwidth of 50 GB/s, the second takes 20 ms. If they run one after the other, restoring takes 120 ms. If prefill would take 150 ms, reuse saves 30 ms. But if prefill only takes 50 ms, waiting 120 ms would be worse. Prefetch changes the comparison: completing 80 ms of the L3 read before scheduling leaves 40 ms to wait. These numbers are teaching assumptions, not hardware specifications or HiCache benchmark results.

<CostViz client:visible lang="en" />

Try reducing the recomputation time in the calculator, or increasing the amount of KV to restore. The comparison can reverse without changing the storage device. A real deployment also needs to account for lookup time, queueing, transfer startup, and overlap with computation. KV size and prefill time depend on the model and workload, so they should be measured together rather than inferred from peak device bandwidth.

For our document example, the useful storage choice depends on what happens after this request:

- **The same instance reads it repeatedly:** keeping an L2 copy can avoid repeated L3 reads, provided Host capacity and Host-to-GPU bandwidth are sufficient.
- **Several instances need it:** a shared L3 can make the cached prefix available across instances. This requires a backend and configuration that support sharing.
- **It is part of a large, less frequently read history:** SSD capacity can be useful if restoring still saves enough prefill work to justify the backup and read costs.
- **Host memory is scarce:** buffer-only mode releases Host slots after staging instead of retaining an L2 copy. It saves Host capacity, but the next request cannot hit that L2 copy and may need L3 again. The Host staging step still exists.

After the restore, the GPU uses the document’s KV from its own memory and computes the new question. The time saved comes from avoiding the document’s prefill. Keeping more history gives HiCache more opportunities to do that; choosing which copies to keep and when to load them determines whether those opportunities actually save time.
