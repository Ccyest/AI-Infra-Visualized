> **一句话**:投机解码 = 小模型多写、大模型批改,一次 forward 验证一整块。
> 小 batch 时验证近乎免费;batch 一大,每个 verify token 都要花真金白银——
> DSpark 用置信度决定"每个请求验几个才划算",再把参差的验证请求紧凑打包。

## 为什么"批改"比"亲笔写"便宜

Decode 是 memory-bound 的:大模型每次 forward 的时间大头在搬权重,算 1 个
token 和验证 K 个 token 花的时间(小 batch 下)差不太多。于是让小模型
(drafter)先写 K 个草稿,大模型一次 forward 全部批改:接受的前缀照单全收,
批改那次 forward 还顺带产出 1 个 bonus token。

DSpark 的 drafter 是 **semi-autoregressive block drafter**:小模型自己也一次
forward 起草一整块,不用逐 token 磨——起草快,接受率还高。看赛跑:

<SpecRaceViz client:visible />

被拒的草稿(斜纹格)浪费的只是小模型的算力,便宜;省下的是大模型的
forward 次数,昂贵。这笔买卖,小 batch 下稳赚。

## 大 batch 的反转:验证不再免费

batch 变大后 GPU 不再闲,verify token 挤占的是别的请求的算力。DSpark 给
"第 M 个 verify token 在负载 bs 下的边际成本"建了个加性成本模型
`T(bs, K) = bias + α(bs) + θ(M)`,用一次性的服务器画像把 θ 按负载测成表——
真实曲线是带平台和陡坡的"台阶",不是平滑曲线。

另一头,drafter 训练了一个 **confidence head**,对每个草稿位置给出存活概率。
调度器逐请求裁剪:期望收益盖不住边际成本的位置,直接不送去验证。切换负载
档位,看窗口如何收缩——以及不同请求收缩得多不均匀:

<TrimViz client:visible />

数学推理的草稿容易被接受,窗口保得住;自由写作发散,batch 一大就只值得验
两三个。这正是混合流量下的实测形态:gsm8k 拿到 5.24 的平均窗口,诗歌只拿
2.91,而利用率始终贴着接受上限的 0.88–0.97。

## 工程底座:ragged 打包 + 状态回放

**Ragged verification**:裁剪完,每个请求的验证长度参差不齐,而 CUDA graph
只认固定形状。与其 padding 到最大块长,不如首尾相接打包再取整到预捕获的
档位:

<PackViz client:visible />

**ReplaySSM**(K3 特供):KDA 递归状态是原地覆写的,投机被拒时要能回滚。
与其整块快照(512 KB),不如只存每步草稿的原始输入(16 KB,省 32×),
接受后用 fold kernel 重放一遍——输出与快照方案逐位一致,省下的 scratch
显存直接换成了并发度。配合 overlap scheduler 的异步 future + 设备端
barrier,迭代之间零气泡,执行紧凑约 1.5×。

## 数字速览

| 场景 | 结果 |
| --- | --- |
| K3,BS=1 解码 | 113 → **423 tok/s**(~3.7×,含起草与验证开销) |
| chat 负载,batch 256 | 相对 verify-all 投机基线再 **+68%** 吞吐(平均接受 2.7 → 2.2——故意少验,反而更快) |
| DeepSeek-V4-Flash,H200 DP4 | 全并发扫描下吞吐/延迟前沿全面领先 MTP 与非投机基线 |
