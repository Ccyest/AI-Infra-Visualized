## Background

先讲投机解码的基本思路。解码是 memory-bound 的：target 模型的一次 forward 大部分时间在搬权重，所以小批次下验证好几个 token 的开销和生成一个差不多。于是让一个小 drafter 先写出 K 个 token，target 用一次 forward 全部检查一遍。通过的前缀被提交，verify forward 还顺带产出一个 bonus token。被拒的草稿只浪费 drafter 的便宜算力：

<SpecRaceViz client:visible />

这笔交易随负载变亏。batch 为 B、每请求 K 个投机 token 时，target 每步要验证 B×K 个 token。小批次下，这些多出来的 token 几乎搭权重搬运的顺风车。批次填满 GPU 后，每个 verify token 都开始消耗真实的步时，过了某个点，验证的开销就超过了它省下的。下图给同样三种选择在不同负载下算账：

<CostViz client:visible />

本文余下的部分分三块：解这笔交易的两代算法，SGLang 为 serve 它们做的工程，以及这套栈对 DeepSeek-V4 意味着什么。

## 从 DFlash 到 DSpark

### DFlash: parallel drafting with KV injection

大多数投机方案，包括 EAGLE 系列和 DeepSeek-V4 这类模型自带的 MTP head，起草是自回归的：小模型逐 token 生成，草稿越长起草开销越大，为了压延迟只能把 drafter 做得很浅。

Z Lab 开发的 DFlash 用一个轻量的块扩散(block diffusion)模型换掉自回归 drafter，一次 forward 并行产出整块草稿。做到这一点不只是换个 drafter 那么简单。从头训练的小扩散模型接受率很低，拿现成的大扩散 LLM 起草又太贵。DFlash 的答案是 KV injection：最懂 context 的是 target 模型本身，所以把 target 的 hidden states 抽出来，注入 draft 模型每一层的 KV cache。EAGLE 类方法只在 drafter 的输入端喂一次 target 特征，drafter 一深信号就衰减；逐层注入让 context 信号一直在场，drafter 可以完全不建模 context，把全部容量花在预测这一块上：

<DFlashViz client:visible />

两个部件的贡献是分开的，论文的消融把这一点摆得很清楚。只用扩散、不用注入，端到端就已经比 EAGLE-3 快，哪怕接受长度更低。只用注入、不用扩散，接受长度反超 EAGLE-3。两个一起用，接受长度保持在 EAGLE-3 的水平，起草却快一个量级：GSM8K 上接受 4.2 个、端到端 3.3×，对 EAGLE-3 的 4.2 个、2.1×。在 Qwen3.5-397B-A17B 上，联合发布的 drafter 在 HumanEval 并发 1 下达到非投机基线的 4.3×、MTP 的 1.5×：

### DSpark：sequential head 加验证预算

纯并行的块留下了两件事没解决。第一，块内各位置的起草互相独立，没有块内依赖，质量向块尾衰减；DSpark 论文称之为 suffix decay。第二，验证侧原封未动：每个请求照旧整块 verify，高并发下就是 Background 里那笔 B×K 的账。

来自 DeepSeek 的 DSpark 用 draft 侧的三件东西从两端一起下手。block drafter 仍然一次 forward 产出 gamma 个 token 的块，但一个轻量的 sequential head(Markov 或 RNN)让每一位以前一位为条件，这就是「半自回归」的含义，也正是对付 suffix decay 的那一手。

confidence head 给每个草稿打「能通过验证」的分数。这个分数来源很具体：结构上它只是搭在 drafter hidden state 上的一个线性层加 sigmoid。训练标签也是算出来的：drafter 在这一位的输出分布和 target 的分布差多远，接受率就有多低，头学的就是预测这个差距。所以分数与请求属于什么主题无关，只反映这一位的下文好不好猜：公式和代码把下一个 token 锁得很死，分就高；自由发挥的文本选择空间大，分就低。整块连乘是块的存活率。Sequential Temperature Scaling(STS)再做一次保序的温度校准，因为原始分系统性偏自信，而预算要对着真实接受率做。

有了这些存活分，验证长度才能按请求来调度：沿着块的存活率曲线往下走，走到「期望多接受的 token 盖不住多验证一个 token 的边际成本」就停。下图跟着一个请求走完一次 draft：

<BlockDraftViz client:visible />

在 Qwen3-4B、8B、14B 三个 target 上，论文报告宏平均接受长度比 DFlash 分别高 16.3%、18.4%、18.3%。剩下的是 serving 问题：得有人给边际成本定价、每步切好预算，还要让一批验证长度参差不齐的请求在真实 GPU 上跑得快。这就是 SGLang 的部分。

## SGLang 怎么把 DSpark serve 起来

SGLang 在 [#30261](https://github.com/sgl-project/sglang/pull/30261)(2026 年 7 月合入)完成集成，drafter 直接搭在 DFlash 的 draft 模型之上，稠密与稀疏 target 都支持，例如 Qwen3 和 DeepSeek-V4。在 DeepSeek-V4-Flash 的完整并发扫掠中，这套集成保持最优的吞吐/延迟频谱，全程领先 MTP 和非投机基线：

<FrontierViz client:visible />

本节余下的部分逐个讲把论文的调度变成真实墙钟时间的工程。

### Confidence scheduler 与 verify 模式

一句话本质：这个优化把「验证多少个 token」从全局常数变成每个请求、每一步的单独决策。

SGLang 的 confidence scheduler 每步给批次里的每个请求执行上一节的预算规则：沿存活率曲线往下走，走到期望收益盖不住边际成本就停。边际成本来自实测：SGLang 事先在这台 server 上离线量好「每多验一个 token 步时多花多少」，存成成本表，scheduler 在线查表定价。效果是可预测的请求保住长窗口，发散的请求被裁到两三个 token；负载升高，所有窗口一起收紧：

<TrimViz client:visible />

verify 有三种模式，各管一件事：static 整块全验，是基线；compact 只验 scheduler 给的窗口，是生产路径；cap-accept 全验但只提交到窗口，产出和 compact 一致，专门用来量「裁剪丢掉了多少本可接受的 token」：

### Ragged verify under full CUDA graphs

一句话本质：这个优化保证裁掉的预算真的变成省下的时间。验证长度参差不齐的批次直接进 CUDA graph，不靠 padding 补齐。

CUDA graph 要求固定的输入形状，而裁剪后每个请求的验证长度都不一样；把大家 pad 回块宽，等于把裁掉的又算了回来。SGLang 的做法是把所有 verify token 首尾相接打包进一个紧凑 buffer，graph 按打包后的总 token 数选档位(向上取整到最近的已捕获档位)。预算一收紧，总数落到更小的档位，回放的就是 attention 和 MLP 行数真正更少的 graph。DP attention 下各 rank 共用最大档位、一起降档；打包后的 buffer 是 cu_seqlens 式变长输入，attention 直接复用后端现成的 kernel(DeepSeek-V4 上就是 flash_mla)，没有新 kernel：

### 调度收益

动态预算到底买到了多少？原文把 compact 和 no-trim 对比，后者是把 static 的整块调度跑在同一条 ragged 路径上，比较对象是两个接受率不同的示例负载。收益主要是高批次效应。batch 1 时，target verify 几乎不因多验几个 token 变慢，裁剪省不了什么，两臂打平。并发上去、吞吐开始进入平台期后，裁剪缩短了每一步，compact 拉开领先。在接受率更低的负载上，差距更大、拉开得更早，因为更低的接受率留下了更多可裁的尾巴。

这些数字背后的 scheduler 是第一版朴素实现，原文也这么定位它：证明机制端到端可行。两个示例负载除接受率外还有细微的设置差异，所以结论是跨负载的趋势，而不是面板间的绝对数字。预算的质量也取决于背后的成本表；当前的拟合是初版，可能还没有完全考虑 context 长度对步时的影响。

同质负载的扫掠还会掩盖 confidence scheduling 的真正意义：同一批次里，一个请求比另一个可预测得多时，两者不该拿到同样的验证窗口。在 gsm8k、arena-hard、poetry 的混合流量上，窗口随接受难度收缩，从 5.24 到 3.78 再到 2.91 个 token，对接受上限的利用率保持在 0.88–0.97。逐步分布说明同一件事：约 55% 的 gsm8k 步用满 6 的窗口，约 80% 的 poetry 步只用 3 个以内：

### Zero-overhead scheduling 与 kernel

把调度变成墙钟时间靠两类工程：压低每一步的成本，以及把 scheduler 藏到 forward 背后。两者合起来，在 DeepSeek-V4-Pro(TP8，B300)上 batch 1、接受长度约 5 时达到 383.7 tok/s。

kernel 侧，SGLang 把 verify 周围成簇的小算子重写成融合的 Triton kernel：compact scatter、SWA page-index、验证长度的 top-k 调度、ragged 窗口打包。block drafter 的采样路径折叠进融合 kernel，矩阵乘做了 shard。在一个示例 profile 里，target verify 之外的部分缩短了 1.7 ms，而 verify 本身是 7.3 ms。

调度侧，DSpark 几乎不加特判就接入了 SGLang 的 zero-overhead(overlap)scheduler。spec-v2 运行时是随 DFlash 集成一起上线的，当时它的 overlap scheduling 在初版实现之上又多拿了 33% 的吞吐。它在独立 stream 上把下一步的调度和当前 forward 重叠，DSpark 作为一等 worker 加入：forward 输出以 async future 返回，跨迭代的顺序靠运行时的 device 侧 barrier，页表在 device 上，每步不需要 host 同步。confidence relay 走同一条通道，读两步之前的值。解码循环于是完全没有逐步气泡，比关掉 overlap scheduler 紧约 1.5×：

## 用 SGLang serve DeepSeek-V4

DeepSeek-V4 有两个尺寸，1.6T 的 Pro 和 284B 的 Flash。每一层都把滑动窗口注意力和压缩注意力混着用，撑起 1M token 的上下文；checkpoint 还自带一个原生训练的单层 MTP head。SGLang 从 Day 0 起就支持这个家族，前缀缓存、kernel、并行方式都为混合注意力路径专门做过；那一侧的细节见文末的 Day-0 blog。

本文讲的一切都架在这之上，是 serving 时的一个选择。投机解码不碰 target 模型的架构，也不改输出分布：drafter 是单独训练的伴随模型，关掉投机就等于加载裸的 checkpoint。同一个 V4 target 上，`--speculative-algorithm` 选的就是 drafter 的代际：EAGLE 跑 checkpoint 里自带的 MTP head，DFLASH 跑块扩散 drafter，DSPARK 跑 DeepSeek 以伴随 checkpoint 形式发布的置信度调度 drafter(DeepSeek-V4-Flash-DSpark、DeepSeek-V4-Pro-DSpark)。DSpark 论文报告，在 DeepSeek 自己的 V4 服务系统里、真实用户流量下，DSpark 在同等吞吐水平上把单用户生成速度比 MTP 基线提高 60–85%。完整的启动配方和复现命令都在文末的原文链接里。
