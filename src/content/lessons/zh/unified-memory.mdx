## 背景

模型读完一篇文档后，会保存一些数据，供接下来生成答案时使用。混合模型包含不同类型的层，它们保存历史的方式也不同：

- **全注意力层为每个 token 保存 key 和 value，简称 KV。** 读入的 token 越多，KV 就越多。生成答案时，注意力会读取这些 KV，回看文档内容。
- **循环层不断更新一块大小固定的状态。** 每读入一个新 token，状态里的内容会变化，但这块状态不会变大。每个活跃请求都需要自己的工作状态。如果要保存一个 checkpoint 供以后复用，还需要另占一个状态槽位。

下图只看一个请求。上下文变长时，KV 不断累积，循环状态则在原来的空间里更新。混合模型继续生成时，两者都需要。

<StateGrowthViz client:visible />

这就带来了容量分配问题。大量短请求需要很多状态槽位，但每个请求的 KV 很少；少量长请求需要的工作状态较少，KV 却很多。如果 SGLang 在启动时就给两类数据各划一块固定大小的显存，一边可能已经放满，另一边却还有空位。

## Unified Memory

### 共用空闲空间

SGLang 的 Unified Memory 让两类数据使用**同一块 GPU 显存**。循环状态从一端向中间增长，KV 从另一端向中间增长。中间的空闲空间，哪一边需要就分给哪一边。整块显存的大小不变，两类数据能用到的容量随需求调整。

假设总容量是 24 个单位，每个请求需要 2 单位循环状态和 1 单位 KV。如果固定给状态 8 单位、给 KV 16 单位，只能放下四个请求：状态池已经满了，KV 池却还有 12 单位空闲。改成共享池后，图中的七个请求总共只用 21 单位，可以全部放下。

<CapacityViz client:visible />

长上下文可能遇到相反的情况：KV 放不下了，状态池却还有空位。可以切到“长上下文”查看。共享池解决的是固定分界带来的容量浪费；如果两类数据加起来已经放满整个缓冲区，请求仍然需要等待，或者先驱逐一部分缓存。

这里的 Unified Memory，指的是同一张 GPU 上几类缓存共用容量，不涉及把数据搬到 CPU。[HiCache](../hicache/)负责另一件事：把缓存历史保存在 CPU 内存或外部存储里，需要时再加载回来。

### 把数据放成可以搬移的块

要把一类数据腾出的空间交给另一类使用，数据布局也得配合。模型有很多层。如果每层各有一个 KV 缓冲区，同一页 token 的数据就会散落在这些缓冲区里。释放这一页，只会在各层分别留下一个小空隙。

SGLang 把一页 KV 在相关层中的数据连续放在一起，组成一个 **page envelope**。下图用三层、两页来表示。两种布局里的第 1 页包含相同的数据，改变的只是这些数据在显存中的位置。

<PageLayoutViz client:visible />

循环状态也按块存放，一个块包含各个循环层所需的状态。KV 页和状态块保留各自的大小，但都从同一个缓冲区取空间。因此，释放一个较大的状态块，就可能放下好几个较小的 KV 页。

### 把内部空洞变成可用空间

释放的块可能夹在两个仍在使用的块之间。图中，状态块 A、B、C 占据左端。释放 B 后，虽然出现了一个空洞，C 却把它和中间的共享空闲区隔开了。SGLang 把 C 搬到 B 原来的位置，C 腾出的空间就能接入共享空闲区，用来分配新的 KV 页。

C 搬走后，请求还得找得到它。SGLang 给 C 一个不变的**虚拟编号**，再用一张表记录它当前的位置。请求仍然引用 C，表里的记录从“C 在位置 8”改成“C 在位置 4”。这样，搬移数据时不用逐个修改所有引用它的请求。

<CompactionViz client:visible />

这个过程叫作**压实（compaction）**。SGLang 可以先留下空洞，等某次分配需要这段空间时再压实。搬移必须等到安全的时候才能进行，之后 GPU 的读写也要使用更新后的位置。如果 GPU 计算或网络传输仍在使用这块数据，就不能在操作中途把它搬走。

[共享池初版](https://github.com/sgl-project/sglang/pull/29678)引入了这套分配和位置映射机制。[后续扩展](https://github.com/sgl-project/sglang/pull/35177)让三类数据都能共用缓冲区：全注意力 KV、滑动窗口 KV 和循环状态。滑动窗口层只需要最近一段 token，其容量需求也可能与另外两类不同。

## 留下更多可复用的前缀

请求完成后，SGLang 可以保留文档的 KV，以及文档末尾的循环状态 checkpoint。另一个请求如果以完全相同的 token 前缀开头，就能复用这些历史，只计算新加的后缀。驱逐这段缓存能立即腾出空间，但后续请求可能就得重新计算它。

共用显存以后，驱逐决策也要把所有能回收的容量算进去。假设一次新分配需要 6 单位 KV 空间。删掉一段缓存前缀，会释放 1 单位 KV 和 2 单位状态 checkpoint。删掉两段，再进行必要的压实，就已经有了 6 单位可用空间。如果只数释放了多少 KV，就只会算到 2 单位，进而继续删掉本来可以留下的前缀。

<EvictionViz client:visible />

SGLang 的[驱逐优化](https://github.com/sgl-project/sglang/pull/33091)会在每次驱逐后，检查共享分配器能否满足当前分配。能满足就停止。这个检查也会计入另一类数据腾出且可以回收的空间，因此能留下更多有用的缓存前缀。

## 实验结果

下面的实验先缓存 28 段不同的前缀，再发送一个无关的长请求制造显存压力，最后重新请求原来的前缀。前缀还在，就能省下重复处理输入的计算；前缀被驱逐了，就需要重算。

**两组都已经启用 Unified Memory。** 比较的是为新分配腾空间时，驱逐在什么时候停止。采用改进后的规则，更多前缀得以保留，28 个返回的请求也更早完成。

<BenchmarkViz client:visible />

实验把池限制为 8,192 个全注意力 token 和 32 个循环状态槽位，prefill chunk 为 8,192 tokens。把 chunk 缩小到 2,048 tokens 后，两组都保留了 28 段前缀中的 17 段。收益取决于释放的状态容量能否补足当前 KV 分配的缺口；这项实验没有观察到整体吞吐的稳定提升。

共享容量本身也有开销：SGLang 要维护位置映射，有时还要复制数据块。[三个子池的评测](https://github.com/sgl-project/sglang/pull/35177)在相同注意力后端下比较固定池与共享池，各模型的 token 间延迟中位数变化为 −0.81% 到 +1.32%。它的收益在于需求变化时能用好已有显存，并不会让每一次 GPU 计算都更快。
