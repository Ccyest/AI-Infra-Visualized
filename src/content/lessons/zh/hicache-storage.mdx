## 背景

假设我们给模型一份很长的文档，让它写一段摘要。看完摘要后，又针对文档中的某个细节提问。两次的问题不同，但两次问题共享文档作为上下文。如果文档对应的 KV 还在，模型就能直接复用，只计算后面的新问题，这就是RadixAttention。

把这份 KV 一直留在 GPU 上，下次用起来最方便。问题是，模型权重和正在处理的请求也要用显存。用户和文档越来越多，GPU 不可能把所有历史前缀都留下。SGLang HiCache 因此把一部分 KV 存到 CPU 内存或外部存储，下次用到这份文档时，再搬回 GPU。[前一篇 HiCache 文章](https://yichizhang.dev/AI-Infra-Visualized/lessons/hicache/)讲了缓存怎么管理，这篇继续解释硬件/通信细节。

HiCache 把 GPU 显存叫作 L1，CPU 内存叫作 L2，存储后端叫作 L3。这几个名字表示 KV 存在哪里。本文讨论的加速卡使用 HBM 显存（高带宽内存，本身也是DRAM的一种），下面要比较的是：它怎样连接 GPU，以及服务器里的普通 DRAM 怎样连接 CPU。

## 先认识几种存储

深入硬件之前，先分清几个指标：**容量**是能存多少数据，**带宽**是每秒能搬多少数据，**延迟**是一次访问要等多久，**单位容量成本**是存同样多的数据要花多少钱。几种常见存储的取舍如下：

<div className="storage-glossary" tabIndex={0} role="region" aria-label="存储术语对照表">

| 名词与含义 | 主要优势 | 主要局限 | 在 HiCache 中的用途 |
| --- | --- | --- | --- |
| **SRAM**（静态随机存取存储器）：GPU 芯片内部的小容量内存 | 访问延迟低，片上带宽高 | 每 bit 占用的芯片面积大，容量小、单位容量成本高 | 硬件 cache 和 kernel 工作数据，不单独算 HiCache 一层 |
| **HBM**（High Bandwidth Memory，高带宽内存）：堆叠在 GPU 芯片旁的 DRAM | 总带宽高，适合 GPU 大量读取 KV | 封装贵，容量受限，不能靠加内存条扩容 | **L1**：GPU 正在使用的 KV 和留在显存中的前缀 |
| **CPU DRAM**：DRAM 指动态随机存取存储器，CPU 内存常采用 DDR 或 LPDDR | 相比 HBM，通常容量更大、单位容量成本更低 | GPU 使用前要经过 CPU–GPU 链路，不能直接获得 CPU 的内存带宽 | **L2**：本地可复用的 KV 副本和传输缓冲 |
| **远端 DRAM**：其他机器上的内存，通过缓存服务访问 | 可以汇集更多容量，也可供多个推理实例共享 | 多了网络和服务开销，吞吐还受网卡、网络限制 | **L3** 的一种选择，例如分布式内存缓存 |
| **SSD / NAND flash**：SSD 是固态硬盘，NAND flash 是其中保存数据的闪存介质 | 容量大，单位容量成本通常低于 DRAM，断电后仍能保存 | 访问延迟比内存高，更新有额外开销，写入寿命有限 | **L3** 的另一种选择，用于保留更大的历史 |

</div>

## HBM：让 GPU 快速读 KV

### 为什么需要高带宽

模型生成答案时，full attention 会反复读取文档对应的 KV。文档越长，每一步 decode 需要读取的历史 KV 通常就越多。GPU 有很多计算单元可以同时工作，但前提是数据能及时送到。因此，正在使用的 KV 需要放在高带宽的 GPU 显存里。

### HBM 怎样提高带宽

HBM 把多层 DRAM 芯片垂直堆起来，用穿硅通孔，也就是 TSV，把各层连起来。然后把这些堆栈放在 GPU 芯片旁边，一起封装。封装内部可以布置密集的连线，让 GPU 和内存之间同时传输更多 bit。连线短，也有利于降低每 bit 的传输能耗。多个内存通道一起工作，就能提供很高的总带宽。HBM 离 GPU 的计算芯片很近，但没有做进那块计算芯片内部。[Micron 的 HBM3E 介绍](https://www.micron.com/about/blog/applications/ai/microns-hbm3e-powering-the-future-of-ai-with-high-bandwidth-memory)

<HbmStackViz client:visible />

HBM 和普通 DRAM 都需要定期刷新来保持数据；高带宽意味着能同时搬更多数据，并不代表每次访问都没有等待。Micron 的 HBM 存储结构说明

这样的设计也有代价。GPU 周围能放堆栈的位置有限，多层堆叠增加了制造和散热难度，密集的连线又需要昂贵的先进封装。想增加 HBM 容量，通常要换用另一种加速卡设计，不能像服务器内存那样再插一根内存条。它和其他 DRAM 一样，断电后也会丢失数据。

### L1 的存储内容

因此，HBM 适合存放 attention 现在要读的 KV。GPU kernel 执行时，会把其中的小块数据读入片上 cache 和 shared memory，完整的 KV 池仍然放在显存里。如果一张 GPU 用的是 GDDR，它的显存同样可以承担 HiCache L1，软件分层并不要求显存必须是 HBM。

GPU 的片上 cache 和 shared memory 使用 SRAM。典型 SRAM 用晶体管电路在通电时保持一个 bit，不需要像 DRAM 那样定期刷新，适合快速的片上访问。但每个 bit 占用的硅面积大得多，做不了很大的容量。所以它适合放 kernel 正在处理的小块数据，不适合存很多轮对话的完整历史，HiCache 也没有把它单独当作一层。[CUDA 内存空间对比](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#device-memory-spaces)

答案生成完以后，文档的 KV 可能要等一会儿才会再次用到。继续留在 HBM 里，下次就不用搬；但它也占着本来可以交给新请求的显存。HiCache 可以在下层保留副本，需要腾空间时再回收 GPU 上的这一份。

## CPU 内存：保存更多 KV

### 容量从哪里来

普通服务器把 DRAM 芯片放在 DIMM 内存条上，连接 CPU 的内存控制器。这就是本文说的 Host 内存。相比 GPU 旁边的 HBM，这种方式通常能以更低的单位容量成本保存更多 KV。但这些内存连着 CPU，GPU 要用里面的数据，还得再搬一趟。

H200 时代的 DGX 服务器使用 DDR5 DIMM；Vera Rubin 则把 LPDDR5X 放在可更换的 SOCAMM 内存模块上，并用 NVLink-C2C 连接 CPU 和 GPU。变的是内存模块和连接方式，Host 内存仍然在 CPU 这一侧。下面分别画出一台 DGX H200 和一个 Vera Rubin NVL72 机架，展开后可以看到局部连接。[DGX H200 架构](https://docs.nvidia.com/dgx/dgxh100-user-guide/introduction-to-dgxh100.html) · [Vera 内存设计](https://www.nvidia.com/en-us/data-center/vera-cpu/) · [Vera Rubin 规格](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/)

### GPU 还要等数据搬过来

假设新问题来了，文档的 KV 已经不在 GPU 上，但 CPU 内存里还有一份。在传统 PCIe 服务器中，恢复它需要先读 Host DRAM，再经过 PCIe，最后写入 GPU 显存。

在这里我们可以算一笔账：假设 GPU 要读取 1 GB 的 KV 数据。
理想情况下，所需时间 = 数据量 ÷ 带宽。
如果这份数据已经在 H100 SXM 的 HBM 中，按标称带宽 3.35 TB/s，
也就是 3,350 GB/s 计算，读完需要 1 ÷ 3,350 秒 ≈ 0.30 毫秒。
如果同样的 1 GB 数据放在 CPU 内存中，需要先经过 PCIe Gen 5 x16 搬到 GPU，
那么按单向 64 GB/s 计算，仅这一步搬运就需要 1 ÷ 64 秒 ≈ 15.6 毫秒。
规格中的 128 GB/s 是两个方向相加，不能用来计算这次单向搬运。
这些估算假设带宽完全跑满，并忽略其他开销，不是 KV 恢复的实测时间。CPU 内存可以装下更多 KV，
但把这些数据搬回 GPU，仍然需要时间。【refer：H100 规格 · Hopper 的 PCIe 规格】

### 为什么 L2 仍然有用

那么提到上面的开销，为什么L2 Cache仍然是值得的呢？因为HiCache 并不需要让每一步 decode 都去 CPU 内存读取这份文档。它先把缓存的 KV 搬回 GPU，之后 attention 使用 GPU 上的副本。**这里要比较的是“搬回来一次”和“把文档重新 prefill 一次”的成本。** 只要前者更低，L2 就能节省时间，并不需要它达到 HBM 的访问速度。

同样是 Host 内存，分配位置也会影响速度。多路 CPU 服务器中，如果内存分配在 GPU 所连接的 CPU 附近，就能少经过一段 CPU 之间的互连，这就是 NUMA 亲和性。传输缓冲区还可以使用 pinned memory，把内存页固定下来供设备搬运。它改善的是搬运过程，没有让 DRAM 单元本身变快；固定太多内存，也会挤占系统其他用途的空间。[CUDA 的 Host–Device 搬运建议](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

## L3：保存更大的历史

### 使用其他机器的DRAM

远端 DRAM 的优势是能借用其他机器的内存，保存本机放不下的 KV。DRAM 本身读写快；把这些内存组成共享缓存服务后，多个推理实例还可以复用同一份 KV，减少各自重复计算和保存副本的开销。

代价是读取时要多走一趟网络。软件需要找到数据，再把它从远端搬回本机，这会增加等待，也可能受网络带宽限制。因此，即使用的都是 DRAM，远端 L3 也不能当成本地 L2 来用。另外，DRAM 每 GB 通常比 SSD 贵，断电后也会丢失数据。

在 HiCache 中，[Mooncake Store](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/) 这样的远端 DRAM 服务可以作为 L3。软件把以后可能复用的 KV 存进去，下次命中时，先通过网络读回本机 Host 内存，再搬到 GPU。要让多个实例共享，它们还需要访问同一份缓存，并使用兼容的模型和 KV 数据格式；不是把后端叫作 L3，就能自动共享。[HiCache 各层的共享范围](https://docs.sglang.io/docs/advanced_features/hicache_design#tier-sharing-scope)

### 使用 SSD

对于值得保留、但没有那么频繁使用的文档，另一种选择是 SSD。SSD 的优势是容量大、每 GB 比内存便宜，断电后也能保存数据。如果有很多暂时用不到、以后可能再次使用的 KV，把它们全部留在 GPU 显存或 CPU 内存里太贵，就可以考虑存到 SSD。

代价是读写比内存慢，而且写入会消耗使用寿命。所以，SSD 适合保存不常用的历史 KV；正在参与计算、需要反复读取的 KV，仍然应该放在 GPU 显存里。如果 SSD 在另一台机器上，读取时还要加上网络传输的时间。

在 HiCache 中，SSD 可以作为 L3 的存储介质。软件把值得保留的 KV 写进去，下次命中时，再经由 Host 内存搬回 GPU。这里有两个取舍：写入时，优先保留以后可能复用的 KV；读取时，判断搬回来是否比重新计算更快。如果一份 KV 再也用不到，写入就是浪费；如果重算很快，等 SSD 读回来也未必划算。

同一份 KV 可以同时在几层里保留副本。把文档备份到 L2，不需要立即删除 GPU 上的那份；从 L3 读回来，也不需要删除 L3 中的副本。要留下哪几份，取决于各层还有多少空间，以及这份文档之后多大概率还会用到。

## KV 怎样搬回 GPU

KV 存在哪里，决定了它要走哪条路。硬件连接和传输方式可以配合使用：例如先经网络读回远端 KV，再通过 PCIe 搬到 GPU。

<div className="storage-glossary" tabIndex={0} role="region" aria-label="传输方式对照表">

| 连接或传输方式 | 主要优势 | 主要局限 | 使用场景 |
| --- | --- | --- | --- |
| **[PCIe](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)**：常见的 Host 与 GPU 连接 | 服务器和 GPU 普遍支持 | 搬运需要时间，大量 KV 可能受带宽限制 | 把本机 CPU 内存中的 KV 搬回 GPU |
| **[NVLink-C2C](https://www.nvidia.com/en-us/data-center/nvlink-c2c/)**：CPU 与 GPU 芯片之间的连接 | 带宽高，适合大量搬运 CPU 一侧的数据 | 需要机器本身支持；Host 内存仍不是 GPU 显存 | Grace Hopper、Vera Rubin 等平台上的 Host 与 GPU 传输 |
| **[GPU NVLink / NVSwitch](https://www.nvidia.com/en-us/data-center/nvlink/)**：GPU 之间的连接 | GPU 之间传输带宽高 | 需要兼容的 GPU 和连接；不能加速 Host → GPU 的 PCIe 搬运 | 在相连的 GPU 之间交换 KV 或其他数据 |
| **TCP**：常规网络传输 | 普遍可用，开发和部署方便 | 网络收发和数据复制可能占用较多 CPU 时间 | 从远端读取 KV，优先考虑兼容性和部署方便时 |
| **[RDMA](https://networking-docs.nvidia.com/doca/archive/3-4-0/rdma-aware-networks-programming-guide)**：减少 CPU 参与的网络传输 | 减少 CPU 处理和中间复制 | 需要配套网卡、网络和后端支持；读进 Host 的 KV 仍要再搬到 GPU | 大量读取远端 KV，CPU 忙于网络收发时 |
| **[GPUDirect RDMA](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)**：网络数据直接进入 GPU 显存 | 省掉 Host 内存中转和后续的 Host → GPU 拷贝 | 需要硬件、连接和软件支持；仍要花时间经过网络 | 后端支持时，把远端 KV 直接送到 GPU |
| **[GPUDirect Storage](https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html)**：存储数据直接进入 GPU 显存 | 省掉经过 Host 内存的中转复制 | 需要存储路径和软件支持；没有让 SSD 本身变快 | 后端支持时，把存储中的 KV 直接读到 GPU |

</div>

## 走一遍文档 KV 的恢复过程

现在假设这份文档的 KV 只剩 L3 中的一份。沿着 Host 中转的路径，HiCache 先把它读进 Host 池，再复制到 GPU KV 池。Attention 要使用哪部分 KV，就必须等那部分到达。下面把文档的 KV 分成四页，逐步展示每份副本什么时候出现。把命中位置切到 L1 或 L2，也能看到哪些搬运因此省掉了。

<TransferViz client:visible />

沿着这个过程，也就能理解 HiCache 为什么调整布局。GPU 逐层执行模型，把同一个模型层的 KV 放在一起，方便这一层计算时读取。但存储请求取回的是一页 token 的缓存，里面包含多个模型层的数据。如果在 Host 内存中把这一页的数据放到一起，后端就能读写连续的大块数据，不必对着许多分散的小块逐次提交 I/O。

这里 HiCache 的一页指一组 token，与操作系统内存页、NAND 物理页不是同一个概念。合并小块传输，减少的是 I/O 提交次数，让一次提交的固定开销分摊到更多字节上。真正需要搬运的 KV 总量并没有变。[HiCache 的布局与搬运设计](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)

搬运还没全部结束时，也可以先做一部分计算。第一个模型层的 KV 到达 GPU 后，GPU 就能计算这一层，同时继续搬后续层的 KV。更早一些，L3 预取还可以利用请求等待调度的时间，提前读取文档缓存。这两种做法都能减少请求等待 I/O 的时间。但如果某一层的 KV 到得太晚，GPU 算到这里时仍然要停下来等。

## 搬回来到底值不值

在 L3 找到文档，只是第一步。接下来还要比较：等 KV 搬回来需要多久，重新对文档做 prefill 又需要多久。SSD 读取虽然慢，但只要重算更慢，复用仍然划算。反过来，如果传输很贵、前缀却很容易算，即使命中了缓存，等它搬回来也可能更慢。

看一个简化例子。假设需要恢复十进制 1 GB 的 KV，L3 → Host 的有效带宽是 10 GB/s，这段要花 100 ms；Host → GPU 是 50 GB/s，再花 20 ms。两段依次执行，一共是 120 ms。如果重新 prefill 要 150 ms，复用就省了 30 ms；如果重算只要 50 ms，等 120 ms 反而更慢。预取又会改变这个比较：如果调度前已经提前完成了 80 ms 的 L3 读取，剩下就只要等 40 ms。这些数字是教学假设，不是器件规格，也不是 HiCache 实测结果。

<CostViz client:visible />

可以在计算器里调低重算时间，或者增大要搬的 KV，看看结果什么时候反过来。存储设备没换，复用也可能从划算变成不划算。真实部署还要算上查询、排队、传输启动，以及搬运和计算重叠的影响。KV 大小与 prefill 时间都取决于模型和实际负载，需要一起测，不能只看器件标称带宽。

回到这份文档，下一次怎样使用它，会影响我们该保留哪份副本：

- **同一个实例频繁使用：** Host 容量和 Host → GPU 带宽够用时，保留 L2 副本可以减少反复读取 L3。
- **多个实例都要使用：** 共享 L3 可以让其他实例也读到这段前缀，前提是后端和配置支持共享。
- **历史很多，使用频率较低：** 如果恢复仍能省掉足够多的 prefill，SSD 的容量就有用。但收益要覆盖备份和再次读取的成本。
- **Host 内存紧张：** buffer-only 模式在中转完成后释放 Host 槽位，不长期保留 L2 副本。这样省了 Host 容量，但下次就不能命中这份 L2，可能还得再读 L3。Host 中转这一步仍然存在。

恢复完成后，GPU 使用自己显存里的文档 KV，继续计算新的问题。省下来的时间来自没有再算一遍文档的 prefill。多存一些历史，给了 HiCache 更多这样的机会；该保留哪份副本、什么时候搬回来，则决定了这些机会能不能真的变成更短的等待。
