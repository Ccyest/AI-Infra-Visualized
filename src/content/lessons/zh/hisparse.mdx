## 背景

### 稀疏注意力

模型生成一个 token 时，注意力要反复回看上下文。为此，人们发明了 KV cache，里面存着每一层、每个历史 token 的 key 和 value。Full Attention 会把所有 KV 全部读一遍。上下文有 32K 个 token，每一步就要读 32K 条，所以每步的开销随上下文变长而增加。

而稀疏注意力，是基于 Attention 原理的一个优化算法方案，它只读上下文的一部分。DeepSeek-V3.2 和 GLM-5.1 用的设计叫 DeepSeek Sparse Attention（DSA）。它分两步。第一步，一个叫 indexer 的小模块给每个历史 token 打分，分数只对当前这一步有效。Indexer 有自己的一套精简 key，所以给整段上下文打分很便宜。第二步，模型留下分数最高的 k 个 token，只在这些 token 上做注意力。k 是固定的。本文涉及的配置里 k 是 2048，上下文多长都不变。

<SparseAttnViz client:visible />

图中就是稀疏注意力的演示，每一轮 indexer 都会打分，打分之后，选取得分最高的 top-k，只对 top-k 进行注意力计算。因此每一步注意力的开销固定，不会随着上下文增长而增长。

### Indexer 怎样打分

每个注意力层有自己的 indexer。Indexer 有三个自己的小权重矩阵：算 key 的 $W_K$、算 query 的 $W_Q$、算 head 权重的 $W_w$。某一层第一次处理一个 token 时，用这个 token 在该层的隐状态乘 $W_K$。结果是一个小向量，叫 index key，存在 GPU 上。

在每个解码步，indexer 算 query 的方式和注意力一样。它用当前 token 的隐状态乘 $W_Q$。输出被切成等长的几段，每个 head 一段，每段就是一个 query 向量。$W_w$ 把同一个隐状态变成每个 head 一个权重。对每个历史 token，indexer 用每个 query 和这个 token 的 index key 做点积。负的结果清零。其余的乘上各 head 的权重再相加。这个和就是这个 token 的分数。分数最高的 k 个 token 进入注意力计算。

这一步的开头和注意力一样：query 和 key 做点积。之后就轻得多。Indexer 没有 value，也不做 softmax，因为它只需要给每个 token 一个分数。它的 key 也很小。$W_K$ 不是方阵。在 DeepSeek-V3.2 里，它的输入是 7168 维的隐状态，输出是 128 维的 key，所有 head 共用这一个 key。每段 query 也是 128 维，所以点积对得上。

<IndexerViz client:visible />

存下来的 index key 不会再变。每一步新算的只有 query 和权重。所以同一个 token 可能这一步分数高，下一步分数低。

### 显存限制

稀疏注意力减少了每一步的计算量。它没有减少显存占用。任何一个 token 之后都可能被选中，所以整段上下文的 KV 都要留在 GPU 显存里。

于是 GPU 显存决定了能同时解码多少个请求。显存一满，再增加并发也不会提高吞吐。下面的 benchmark 里也可以看出，baseline 在 32 并发时就不再增长。

## HiSparse

### 设计与机制

SGLang 的 HiSparse 为了解决这个问题应运而生。HiSparse 把 KV cache 存在两个地方。CPU 内存保存每个请求的完整 KV。GPU 显存为每个请求保留一个小缓冲区，叫 hot device buffer，槽位数固定。Indexer 的 key 也留在 GPU 上，因为 indexer 仍然要给整段上下文打分。

每个解码步执行五个动作：

1. 打分。Indexer 给每个历史 token 打分，留下分数最高的 k 个。
2. 查 buffer。HiSparse 检查这 k 个 token 里哪些已经在 buffer 里。
3. 拷入。不在 buffer 里的 token，它的 KV 从 CPU 内存拷进 buffer。Buffer 满了就替换最久没用过的 token。
4. 注意力。模型从 buffer 里读 top-k 的 KV，生成下一个 token。
5. 追加。新 token 的 KV 拷到 CPU 内存，它的 index key 加入 GPU 上的 index key。

Buffer 的槽位数比 k 多，所以它还留着最近几步选中过的 token。因为 Indexer 以及模型上下文的特性，相邻两步选中的 token 大部分相同。因此多数查找都能命中 buffer，每一步只需要搬少量 KV，而非全部 top-k。

<HiSparseFlowViz client:visible />

一个解码步不会改写之前存下的任何内容。一个 token 的 KV 和 index key 都只算一次。每一步只为新 token 各追加一份。

有了 HiSparse，一个请求在 GPU 上只占固定数量的 KV 槽位，上下文多长都一样。同一块 GPU 能容纳的请求多了很多，decode batch 也随之变大。

### Swap-in kernel

Swap-in 在每个解码步都要执行，所以它的延迟很关键。SGLang 把它实现成一个 CUDA kernel。这个 kernel 做三件事。它找出 top-k 里不在 buffer 中的 token。它按 LRU（最近最少使用）策略选出要腾出的槽位。它更新页表，并把缺失的 KV 从 CPU 内存拷到 GPU。

每次缺失都要从 CPU 内存拷一次，所以缺失越少，swap-in 越快。有两个选择可以减少缺失：更大的 buffer 和更好的驱逐策略。下图在 DeepSeek-V3.2 上比较了它们。Buffer 从 2048 槽加到 4096 槽，缺失数少了一大截。同样是 4096 槽，LRU 的缺失数低于 FIFO 和随机驱逐。

### Prefill-decode 分离

SGLang 可以把 prefill 和 decode 放在不同的实例上。HiSparse 作用在 decode 实例。Prefill 实例把 KV 直接发进 decode 实例的 CPU 内存。Decode 侧的 GPU 从头到尾不用装下完整 KV，传输期间也不用。Prefill 实例不需要任何改动。

## 结果

第二组 benchmark 在 GLM-5.1-FP8 上遍历不同的输入和输出长度。六组配置下，HiSparse 的生成吞吐是 1,720 到 2,320 tokens/s。Baseline 是 352 到 752 tokens/s。上下文越长差距越大。最短的一组配置是 3.1 倍，输入 40K、输出 20K 时超过 5 倍。

<SweepBenchViz client:visible />

HiSparse 是为高并发设计的。低并发时它比 baseline 慢，因为多出来的拷贝开销超过了省下的显存带来的收益。上面的并发图里，32 并发及以下就是这种情况。HiSparse 目前仍是实验性功能。它最初支持的是 DSA 模型家族，即 DeepSeek-V3.2 和 GLM-5.1。当前支持的模型和参数见 [HiSparse guide](https://docs.sglang.io/docs/advanced_features/hisparse_guide)。
