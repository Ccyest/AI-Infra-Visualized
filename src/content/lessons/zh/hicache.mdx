## 背景

模型为读入的 token 计算 key 和 value，简称 KV。生成时，attention 通过这些 KV 读取前文。当另一个请求以相同的 token 前缀开头，SGLang 就能复用对应的 KV，只计算新增的后缀。这减少了 prefill 工作，也缩短了首 token 延迟，即 TTFT。

GPU 显存容量限制了这种复用。对话每一轮都在增长，更多客户端又带来更多历史。缓存满了以后，某段前缀可能刚被驱逐，下一个请求就需要它。SGLang 的 HiCache 用容量更大的存储层保留这些前缀。要让新增容量产生收益，恢复前缀必须比重新计算更划算，而且恢复的状态必须足以让模型从这个前缀继续执行。

HiCache 先接入 CPU 内存，再扩展到外部存储。后续工作把恢复范围扩展到混合模型和 draft 状态，并提出了让 host 内存只作传输缓冲的方案。时间线展示这些变化的背景，后文则沿着它们解决的工程问题展开。

## HiCache

### 设计与机制

把所有可复用前缀都留在 GPU 上，会挤占活跃请求所需的显存。因此，HiCache 把前缀的保存位置与模型的使用位置分开：GPU HBM 是 L1，CPU DRAM 是 L2，外部存储是 L3。Attention 仍由 GPU 执行，较低层保留原本会被丢弃的数据，cache controller 负责备份和加载。

<StorageLocationViz client:visible />

假设两次请求都以同一份文档开头，只是后面的问题不同。SGLang 可以复用文档对应的 KV，只计算新问题。HiRadixTree 负责匹配相同的前缀，并记录本地缓存的位置；HiCache 负责在需要时把下层缓存搬回 GPU。

<CacheReuseViz client:visible />

L1 命中直接复用；L2 命中先搬回 L1；L3 命中先取到 L2，再搬回 L1。只有三层都找不到的部分才需要重新计算。HiCache 的收益就在这里：即使 GPU 清掉了某段缓存，只要下层还保留着，就有机会省掉重算。这要求两次请求的前缀 token 一致，仅仅意思相近不能复用。

### 工程问题纵览

分层设计提供了保留和恢复前缀的路径。要让这条路径真正有用，实现中还需要解决几类问题：

- **内存布局：** GPU 计算按模型层排列数据，存储 I/O 则按照page排列数据，怎样让不同的排列顺序之间仍然高效搬运？
- **重叠搬运与计算操作：** 哪些传输可以与 GPU 计算重叠，让GPU不空等？
- **缓存策略：** 预取和备份都消耗时间、带宽与容量，什么时候值得等待，什么时候值得多存一份？
- **混合模型与 draft 状态：** token 匹配到了，所需历史状态却可能不完整，哪些数据必须随前缀一起恢复？
- **Host 内存：** 每个实例都有私有 L2 池，L3 已经保留历史时，host 还需要长期保存多少数据？
- **存储后端：** 不同系统的 I/O 实现各异，怎样共用 HiCache 的调度与恢复机制？




















### 内存布局

这项优化解决 GPU 计算与存储 I/O 所需的 KV 排列顺序不同的问题。GPU 每次计算一个模型层，为了便于读取，就会把一层的KV放一起。而L3外部存储则按页读写（如第一页包含token 1-4，第二页包含 5-8）

因此，如果在Host段仍然不改变排列方式的话，如图所示，在搬运过程中就会有多次小的搬运开销。相反，如果Host段使用按页排列，则可以一次搬运一整页到L3外部存储，减少了搬运次数与开销。

**因此，HiCache 让 Host 按页排列，作为中转站。** HiCache 让 Host 在搬运时转换布局。如图所示。图中高亮第 1 页：Before 里，它分散在 Host 的多个区域；After 里，它集中成一块。Host → 存储备份时，可以直接读取这一整块；存储 → Host 恢复时，可以直接写入这一整块，减少开销。



<LayoutViz client:visible />

**GPU ↔ Host** 这一段，SGLang自己研发的GPU 辅助的 I/O kernel 让传输吞吐最高达到标准 `cudaMemcpyAsync` 路径的 **3 倍**。**Host ↔ 存储** 这一段，按页排列让存储能读写连续的大块数据；zero-copy 让存储客户端直接访问 Host 池里的这些数据。按页排列与 zero-copy 配合，让 Host–存储吞吐最高达到 **2 倍**。

### 重叠搬运与计算操作

前文讲了搬运如何加速，这项优化则是把 **Host → GPU 搬运缓存 KV** 与 **GPU 计算新 token** 重叠起来。在搬运过程中，我们不想要GPU空等，理想状态是每搬运一点GPU就算一点。因此，需要 HiCache 在第一个模型层的 KV 到齐后就开始计算，同时继续搬运后续模型层的 KV。

以三层模型为例：先把文档在第 0 层的 KV 从 Host 搬到 GPU。GPU 随即对新问题执行第 0 层计算，并通过这份缓存 KV 读取文档内容。与此同时，传输流搬运文档在第 1、2 层的 KV。

能这样重叠，是因为每个模型层使用自己的 KV。第 0 层计算时，不需要等第 1 层的 KV。计算走到第 1 层时，再检查第 1 层是否搬完：搬完就直接计算，没搬完才等这一层。L2 命中可以直接开始这个 Host → GPU 过程；L3 命中则先把 KV 从存储读到 Host，再进行同样的重叠操作。

### 缓存策略

HiCache 还要决定什么时候值得搬运。读取时，等待缓存命中可能推迟请求；写入时，保存一段再也不会复用的数据又会浪费带宽和容量。预取与备份策略分别控制这两类成本。

#### 预取

存储延迟比 CPU–GPU 延迟更高，也更难预测。如果等 GPU 准备好才开始读取 L3，请求就必须直接承担这段等待。HiCache 因此在请求等待调度时，提前把存储中命中的页预取到 CPU 内存。

请求准备执行后，策略决定还要等多久。Best-effort 可以停止预取，复用已就绪的前缀，重新计算缺失部分。等待完成的策略倾向于保留更多复用机会，timeout 则为额外等待设置上限。

<PrefetchViz client:visible />

收益在于更早启动存储 I/O，并能控制剩余等待。读取在调度前完成，就能省去重算，也不必在准备执行时再等存储。如果读取晚于调度，只有省下的计算时间超过新增等待，继续等才划算。读取只完成一部分时，请求可以复用已就绪的前缀，重算剩余部分。

#### 备份

较低层能命中，前提是此前做过备份。保存每段缓存可以保留更多复用机会，却也会为以后不再请求的前缀消耗带宽。容量较小的下层存储还可能被这些副本填满。

HiCache 提供三种策略，决定何时支付这笔成本：

| 策略 | 备份时机 | 主要取舍 |
| --- | --- | --- |
| Write-through | 主动备份已缓存的 KV | 保留更多数据，增加 I/O |
| Write-through-selective | 根据命中次数备份热点 | 减少 I/O，降低冷数据覆盖率 |
| Write-back | 延迟到较快层驱逐时再备份 | 减少提前备份的流量，在驱逐路径上增加工作 |

这些策略让部署可以用部分缓存覆盖率换取较低的传输与容量压力。带宽充足时，主动备份有利于保留历史；选择性备份则避免给每段冷数据都花带宽。延迟备份推迟了复制，但在数据必须离开较快层时增加工作。

### 混合模型的状态

传输足够快，还要保证恢复的数据足够完整。混合模型给 HiCache 增加了正确性问题：普通 KV 可能已经覆盖某段前缀，另一种必需状态却仍然缺失。SGLang 因此扩展缓存表示与备份流程，把这些状态一起保留下来。

#### 复用边界

Full attention 需要可复用前缀的 KV。滑窗注意力需要复用边界处的尾部窗口。递归层则需要恰好位于该边界的 checkpoint。递归状态随 token 到来不断变化，不能把较晚的 checkpoint 简单截短，得到较早的状态。

SGLang 的 Unified Radix Cache 把这些组件记录在同一棵 token 树上，分别保存池索引、检查复用条件。只有所有必需组件都接受某个边界，才能从那里复用。HiCache 跨层备份和恢复各组件的数据，并带上关联的辅助 buffer。例如，Qwen3.5 需要递归状态，DeepSeek-V3.2 需要稀疏注意力的 indexer buffer。

效果是，恢复决策能够覆盖模型的完整需求。所需窗口或 checkpoint 缺失时，仅有 Full KV 命中不能授权复用。这让分层缓存可以扩展到混合模型；后面的多轮基准再测量保留这些模型历史所带来的收益。

#### 分支 checkpoint

完整恢复还要求保存初次备份之后新出现的状态。假设 host 已保存截至 P3 的 Full KV，以及 P3 处的递归 checkpoint S0。新请求从 P2 分支，并在那里生成 S1。S0 包含 P2 之后的 token，不能用于新分支。如果备份只检查节点是否已有 host 副本，就会跳过 S1，导致后续请求无法从 P2 继续执行。

SGLang 为新生成的 checkpoint 增加增量备份。已有 Full KV 留在原处，只需再传输 S1。因此，即使前缀的其他数据已经保存，备份流程仍会跟踪新出现的组件。

<StateRestoreViz client:visible />

恢复测试采用 write-through 策略，在两轮 GPU 驱逐之间创建分支状态。最终阶段中，完整恢复 6.4K 共享前缀的请求从 **1/10 增至 10/10**，token 命中率从 **15.74% 增至 64.00%**。每个请求还有 3.6K 独有后缀，因此 64% 就代表共享部分全部恢复。详见[分支备份测试](https://github.com/sgl-project/sglang/pull/33639)。

### Draft 状态恢复

投机解码又增加了一个使用前缀的模型。Draft 模型提出候选 token，target 模型负责验证，draft 也可能保存自己的 KV 或历史 buffer。如果 HiCache 只恢复 target KV，draft 就可能丢失历史，或者读到错误槽位。即使 target 成功命中缓存，后续解码的 draft 接受率仍可能下降。

SGLang 把配套的 draft buffer 加入 target 的缓存传输。布局兼容时，draft 数据打包进对应的 target host 池；其他布局则使用独立的 sidecar 池，索引跟随 target 的 KV 或滑窗索引。两条路径都会在 L2、L3 备份和恢复时带上关联的 draft 状态。

<DraftRestoreViz client:visible />

DSpark 测试在 DeepSeek-V4-Flash-0731 上，对同一批 200 个 prompt 做冷运行和 L3 恢复运行。改动前，恢复运行的接受率从 **46.77% 降至 33.57%**；改动后，冷运行和恢复运行分别为 **46.12% 和 46.86%**。恢复 draft 状态保住了缓存命中后 draft 的有效性，收益延伸到了 target KV 复用所节省的 prefill 之后。详见 [draft 恢复验证](https://github.com/sgl-project/sglang/pull/30393)。

### Host 内存作为缓冲

原始分层设计让 CPU 内存长期保留第二份缓存，L2 命中可以省去读取存储。但每个服务实例都有自己的 L2 池。多个实例可能各自保留 host 副本，同时又向共享 L3 备份。Host 内存较少时，即使 L3 已经保存了历史，长期保留这份工作集仍会带来容量压力。

Buffer-only 方案改变了 L2 的用途。备份经 host 缓冲写入 L3，预取经 host 缓冲加载到 GPU。一次操作完成并释放槽位后，后续传输就能复用这些空间。L3 负责长期保留历史，host 内存只保存中转数据。模型配置兼容的实例可以复用同一份 L3 缓存。

<HostModeViz client:visible />

这个设计允许按正在进行的传输配置 host 容量，不必再容纳长期保存的第二份工作集。代价是失去持久 L2 命中，并可能增加 L3 流量；缓冲较小也会限制并发传输。原本由持久 L2 命中承接的读取，改由 L3 承担。

### 存储后端

HiCache 还要接入查询、读写方式不同的存储系统。如果每接一个后端都重建调度和同步逻辑，每次集成都将变成一套独立的缓存实现。

SGLang 把这些存储操作放在统一的后端接口之后。后端负责键查询、读和写，中央 controller 负责调度与同步。后端包括 Mooncake、DeepSeek 3FS、NIXL 和本地文件。其中 NIXL 通过传输库连接其他存储系统。

收益是共用同一条集成路径：后端只需提供存储访问能力，就能使用 HiCache 的缓存控制逻辑，不必重新实现。这扩大了部署时的选择范围。

## 整体效果

长输入和多轮对话的历史会超过 GPU 显存容量。下面的基准依次加入 CPU 内存和外部存储，观察保留更多历史之后，首 token 延迟和输入吞吐怎样变化。

### 长上下文 · 2025

原文的 LooGLE 测试验证较低层缓存能否减少长输入的重复 prefill。它在八张 H20-3e 上运行 DeepSeek-R1，比较仅 GPU 缓存、增加 CPU L2、增加 3FS L3，以及单独预先填充 L3 的情况。图中可以查看平均 TTFT 和输入吞吐。

<ResultsViz client:visible />

普通 L3 的输入吞吐为 51,168 tokens/s，平均 TTFT 为 1.83 秒。如果在请求到来之前，就把可复用的 KV 填入 L3，更多请求可以直接加载缓存前缀。输入吞吐提高到 76,322 tokens/s，平均 TTFT 降至 1.43 秒。

### 混合模型多轮对话 · 2026

多轮对话提供了不断增长的工作集：每一轮都新增后续请求可能复用的历史。2026 年 8 月的测试比较 GPU L1、L1 加 CPU L2，以及再加 500 GiB Mooncake L3。DeepSeek-V4-Flash 使用 FULL 与 SWA，Inkling-Small 使用 FULL、SWA 与 MAMBA。

<MultiTurnBenchViz client:visible />

L1 最先丢失可复用历史，L2 推迟了容量上限出现的时刻。相比仅 L1，增加 L3 后，DeepSeek-V4-Flash 的有效输入吞吐从 9.4K 增至 145.5K tokens/s，缓存命中率保持在约 98%。Inkling-Small 从 15.5K 增至 67.1K，最终命中率为 96.8%。结果表明，当混合模型的对话历史超过较小缓存的容量时，较低层仍能保住复用机会。详见[多轮基准](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/)。

输入吞吐统计服务每秒处理的所有输入 token，包括命中缓存的部分。复用一段长前缀，就能省去这段前缀的 KV 重算，把更多 GPU 时间留给新增输入。

## 总结

HiCache 把可复用前缀的保存时间延长到了 GPU 显存之外。各项工程选择让新增容量真正可用：布局和加载方式减少搬运开销，策略控制何时值得做 I/O，组件与 draft 恢复保住所需的完整状态，host 缓冲与后端选择则让同一套分层机制适应不同部署资源。

当省下的 prefill 工作超过恢复成本，而且较低层保住了原本会丢失的历史，系统就能获得整体收益。长输入和不断增长的对话基准验证了这种效果。
