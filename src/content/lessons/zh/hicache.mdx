## 背景

模型为读入的 token 计算 key 和 value，简称 KV。生成时，attention 通过这些 KV 读取前文。如果后续请求以相同的 token 前缀开头，SGLang 就能复用对应的 KV，只计算新增的后缀。这既减少了 prefill 工作，也缩短了首 token 延迟，即 TTFT。

难点在于保住旧 KV。长对话每一轮都占用更多空间，更多客户端又带来更多历史。GPU 缓存满了以后，某段前缀可能刚被驱逐，下一个请求就需要它。扩大缓存要有收益，还得满足一个条件：加载旧 KV 比重新计算更便宜。

## 开发时间线

最初的分层缓存提案 #2693 于 2025 年 1 月 1 日提出，2 月 24 日合入，存储层在 7 月陆续接入。2026 年的工作进一步加入新的状态类型、投机解码、并行布局和 host 内存模式。时间线使用合入 main 的 UTC 日期；其中 MLA 去重标注为基础组件，不代表完整去重功能已经落地。

## HiCache

### 设计与机制

SGLang HiCache 在 GPU HBM、CPU DRAM 和外部存储中保留可复用的 KV。Attention 仍由 GPU 执行。CPU 内存和存储保留原本会被丢弃的 KV，cache controller 负责层间传输。

HiRadixTree 用 token 序列索引本地缓存。每个节点存一段 token，以及对应 KV 在 GPU 和 CPU 池中的索引。沿一条路径把 token 段连起来，就是共享前缀。GPU 命中可以直接使用；CPU 命中则需要把数据传到新分配的 GPU 槽位。如果前缀不在本地，controller 可以用前缀派生的键查询外部存储，把命中的页预取到 CPU 内存。本地树未命中，并不意味着外部存储一定命中。

<CacheTreeViz client:visible />

图中用短 token 段和任意池索引作示意。对于前缀 A → B，A 已在 GPU 上，B 从 CPU 内存取回。对于 A → C，C 最初不在本地树上，成功从存储读取后才出现。备份可以同时存在于多个层级。搬运 KV 不要求删除来源层中的所有副本。

### 存储后端

2025 年的设计支持 Mooncake、DeepSeek 3FS、NIXL 和本地文件后端。后端提供键查询、读和写，中央 controller 负责调度与同步。NIXL 是连接其他存储系统的传输库，因此不能把这四个后端理解成四种完全等价的存储设备。

## 数据搬运

### 内存布局

模型逐层使用 KV，因此 GPU 内存保留计算 kernel 所需的 layer-first 布局。存储 I/O 则受益于更大的连续传输。HiCache 让 host 池采用 page-first 布局，把同一页在不同层的 KV 放在一起。两边是同一份数据，但物理排列顺序不同。

<LayoutViz client:visible />

SGLang 用 GPU 辅助的 I/O kernel 搬运 CPU–GPU 数据。博客报告，相比标准的 `cudaMemcpyAsync` 路径，传输吞吐最高达到 3 倍。Page-first 布局结合 zero-copy I/O，在典型部署中让 host 内存与存储之间的吞吐最高达到 2 倍。这些优化作用于不同的传输路径，不能相乘当作端到端加速比。Mooncake 和 3FS 的改动链接见参考资料。

### 逐层加载

CPU 命中时，不必等全部层的 KV 都加载完才开始计算。第 0 层加载好以后，GPU 就能执行这一层，同时继续传输后续层的 KV。每层都必须等自己的 KV 就绪，但不需要等待所有后续层。这种重叠可以隐藏一部分传输时间。

<OverlapViz client:visible />

第一次加载仍然需要时间。如果传输比计算更慢，后续层仍可能停下来等数据。动画假设传输和计算耗时固定，用来展示依赖关系；时间轴不是硬件基准。

## 缓存策略

### 预取

存储延迟通常比 CPU–GPU 延迟更高，也更难预测。HiCache 在请求等待调度时，开始把数据预取到 CPU 内存。尽力预取可以在请求准备运行时停止，复用已就绪的前缀，重新计算缺失部分。多等一会儿可能保住更多复用机会，也会推迟请求执行。超时策略则为等待设置上限。

<PrefetchViz client:visible />

示例把请求前缀视为一个不可拆的块，真实请求可以复用较大传输中已完成的一段前缀。存储快时，两种策略都会在调度前完成读取。读取稍晚时，等待可能省下更长的重算。存储很慢时，等待反而吃亏。命中更多缓存，本身并不保证 TTFT 更低。

### 备份

备份每段缓存，会在当前消耗带宽，以提高后续复用的机会。HiCache 提供三种选择：

| 策略 | 备份时机 | 主要取舍 |
| --- | --- | --- |
| Write-through | 主动备份已缓存的 KV | 保留更多数据，增加 I/O |
| Write-through-selective | 根据命中次数备份热点 | 减少 I/O，降低冷数据覆盖率 |
| Write-back | 延迟到较快层驱逐时再备份 | 减少提前备份的流量，在驱逐路径上增加工作 |

合适的配置取决于传输带宽和较低层的容量。增加存储并不会消除这些限制。

## 混合模型

前面的章节解释 2025 年原始设计。下面补充截至 2026 年 9 月 11 日核验的已合入工作与公开测试结果。

### 不只是 Full KV

新模型保留历史的方式并不相同。Full attention 保留整段可复用前缀的 KV；滑窗注意力只需要尾部窗口；递归层则需要恰好位于前缀边界的状态。只保存 Full KV，无法在不增加计算的情况下重建这个状态。SGLang 的 Unified Radix Cache 把这些组件放在同一棵 token 树上，由每个组件检查自己的数据是否满足复用条件。

HiCache 因此扩展到新的组合。#21259 为 Mooncake 加入 DSA 与 Mamba 状态存储，并验证了 Qwen3.5-9B 和 DeepSeek-V3.2-Exp。#29191 为 NIXL 加入混合模型的辅助池存储，包括 Qwen3.5 的递归状态和 DSA 的 indexer buffer。存储后端除了处理普通 KV，还必须处理这些额外 buffer。MAMBA 组件是递归状态缓存的抽象名称，不代表使用它的模型都采用原始 Mamba 架构。

### 分支 checkpoint

共享前缀的 Full KV 可能已经在 CPU 内存中备份，随后一个新请求又在这段前缀上生成新的递归状态 checkpoint。如果把整个节点视为「已经备份」，就会漏掉新状态。GPU 驱逐以后，Full KV 能恢复，新 checkpoint 却找不到。#33639 为新增组件补上增量备份，不必重新复制 Full KV。

<StateRestoreViz client:visible />

PR 的验证先构建共享前缀，把它们挤到 Host，再创建新的分支状态、再次驱逐，最后检查恢复。在末轮十个请求中，完整命中 6.4K 前缀的请求从 1/10 增至 10/10。这是恢复能力的验证，不是吞吐测量。该改动最初覆盖 write-through，不能据此认定 write-back 已具有相同的增量备份行为。

### 混合模型结果

2026 年 8 月的 Unified Radix Cache 测试比较 GPU L1、L1 加 CPU L2，以及再加 500 GiB Mooncake L3。DeepSeek-V4-Flash 使用 FULL 与 SWA，Inkling-Small 使用 FULL、SWA 与 MAMBA。两种模型的配置和规模不同，因此应在每种模型内部比较缓存层级。

<MultiTurnBenchViz client:visible />

DeepSeek-V4-Flash 的有效输入吞吐从 9.4K 增至 145.5K tokens/s，L3 命中率保持在约 98%。Inkling-Small 从 15.5K 增至 67.1K，最终命中率为 96.8%。这些测量把已缓存的输入 token 也计入服务处理进度。结果体现的是保留不断增长的对话历史带来的收益，不代表 GPU 原始计算速度提高了同样的倍数。

## Agent 与投机解码

### Draft 状态恢复

投机解码让 draft 模型先提出候选 token，再由 target 模型验证。Draft 可以有自己的 KV、indexer 或滑窗 buffer。只恢复 target 缓存，可能让 draft 状态缺失，或映射到错误槽位。因此，target 侧显示缓存命中时，draft 接受率仍可能下降。#30393 让配套的 target 与 draft 状态一起搬运。

SGLang 使用两种布局。兼容的 NextN MTP/EAGLE 模型，以及 DeepSeek-V4 DSpark，把 draft buffer 追加到对应 target host 池的尾部。独立 EAGLE、DFlash 和其他受支持的 DSpark 拓扑则使用独立 sidecar 池，其索引跟随 target KV 或 SWA。两条路径都把 draft buffer 加入同一次 L2/L3 操作。该 PR 明确不支持 Inkling HiCache MTP。

<DraftRestoreViz client:visible />

图中使用 PR 对同一批 prompt 做冷运行和 L3 恢复的验证结果。改动后，恢复运行的接受率接近冷运行，不再因缓存恢复而下降。这里测量的是接受率，这组数字不是端到端吞吐基准。

### DCP 适配

Decode context parallelism，即 DCP，会把上下文 KV 分到不同 rank。单个 rank 的物理缓存行数不再覆盖整个逻辑索引范围。这对继承 target 索引的 draft 池很重要：如果只按单个 rank 的物理行数分配，合法的逻辑索引可能超出 host 池边界。

SGLang 在 #33112 中加入 DCP 与 HiCache L2 的组合。#35221 随后启用 DSpark，并按 target 的逻辑容量分配 draft host 池。PR 在八张 B300 上，以 TP8/DCP8 验证 Kimi-K3 及其 DSpark draft，驱逐压力下 64/64 个请求全部完成。这验证了该组合，不代表所有投机算法都能与 DCP 一起使用。

### 会话感知驱逐

Agent 调用工具后，经常回到同一段前缀。普通 LRU 知道 KV 最近何时被访问，却不知道活跃会话是否还需要它。#29173 为 Unified Radix Cache 加入会话引用。GPU 和 Host 驱逐优先选择没有引用的条目；如果仍需要更多空间，有引用的条目也可以被驱逐。关闭会话会释放引用，但不会立刻删除 KV。

<SweBenchViz client:visible />

2026 年的 SWE-bench 测试中，会话感知的 Unified 配置让 TTFT 最多降低 16.6%。相对普通 HiRadixCache 加 LRU 的基线，对照组同时改变了树实现和驱逐策略，因此不能把差异全部归因于会话引用。这个会话策略覆盖 L1 与 L2，不负责外部 L3 服务内部的驱逐。

## Host 内存与存储

### 私有 L2 与共享 L3

每个服务实例拥有自己的 GPU 和 CPU 缓存池。同一台机器上的两个实例，也不会自动共享一个 L2。外部 L3 可以让兼容实例访问已存储的 KV。增大一个实例的 host 内存预算，只会扩大它自己的 L2。#37050 的文档明确了这个共享边界；#31920 还为 Mooncake 的键加入模型隔离。仅仅 token 文本相同，并不意味着不同模型配置产生的 KV 可以互换。

### Buffer-only 模式

原始设计把 CPU 内存视为另一个长期缓存层。#34798 增加了另一种选择：让 host 内存只充当 GPU 与 L3 之间的临时传输缓冲。备份经它写入存储，预取经它加载到 GPU。传输完成并释放占用后，同一块中转空间就能服务下一次传输。Host 池不再需要长期保留工作集的大量副本。

<HostModeViz client:visible />

这种模式需要存储后端，数据仍经过 CPU 内存，并不意味着所有后端都有 GPU 直连存储的路径。较小的 host 池也会限制同时进行的 I/O 数量；放弃长期 L2 复用，可能增加 L3 流量。Buffer-only 初始 PR 没有给出通用加速比，它主要提供了一种使用有限 host 内存的新方式。

### Buffer-only 与 sidecar

9 月 4 日合入的 #37424 把 sidecar 池接入 buffer 模式。验证使用八张 H100，组合 DeepSeek-V4-Flash-0731、Mooncake L3 和 DSpark。先运行完整的 198 道 GPQA Diamond 题目填充存储，清空 device/radix 缓存，再从 L3 运行同一数据集。

两轮都答对 181/198，得分为 91.41%。DSpark 接受率从首轮的 45.84% 变为恢复运行的 45.83%。140 条至少包含一个可缓存页的 prompt，全部从 L3 加载了预期数量的 token；另外 58 条太短，没有可缓存页。这验证了缓存与 draft 状态的组合路径，不是在宣称新的延迟纪录。

## 平台适配

**AMD 与 DeepSeek-V4。** #29417 为 `unified_kv_triton` 布局加入 HiCache。它保留压缩后的 C4/C128 KV，SWA ring 的尾部窗口则重新 prefill。PR 的 TP4 测试使用 50K 输入 token、200 输出 token、并发 64；warm run 的输出吞吐从 66 增至 789 tokens/s，中位 TTFT 从 91.128 秒降至 3.982 秒。仅 GPU 缓存的 warm run 无法保住这个工作集。这是容量压力下的热缓存结果，不是冷启动收益。

**新增存储。** #25377 加入 AMD 的 UMBP 分层存储接入。其公开 DRAM 测试在八张 MI355X 上运行五层 DeepSeek-V3 模型，平均 TTFT 从 175.6 降至 50.0 ms。标有 SSD 配置的那一行实际关闭了 SSD，因此只是配置冒烟测试，不能作为 SSD 性能依据。NIXL 后续的混合模型支持，也让存储接入从 Full KV 扩展到递归状态与辅助池。

**Ascend I/O。** 9 月 10 日合入的 #38826 为 L2 传输加入 Memfabric 映射的 host 内存和 AscendC sparse-copy 路径。它还避免了一次 H2D 上传同步，以免排空 stream，让流水线串行等待。这是新的 host 内存与 I/O 适配，不能据此宣称所有 Ascend 模型都获得相同加速。

另有两项相关工作需要区别看待。#36800 只合入了 MLA host 副本去重的基础组件；连接 scheduler/controller 的 #26691 在核验时仍然开放。Ascend Mamba 异步 I/O 的 #35815 合入了 `qwen_optimize` 分支，对应 main 的 #32500 仍然开放。这两项都不能写成已经完整落地主线、普遍可用的能力。

普通 L3 的输入吞吐为 51,168 tokens/s，平均 TTFT 为 1.83 秒。预先填充 L3 后，结果为 76,322 tokens/s 和 1.43 秒，但缓存预热条件已经改变。理解标题中的收益时，要区分这些条件。缓存复用场景中的输入吞吐包含已缓存输入的处理进度，不等于 GPU 为每个 token 新计算 KV 的速度。

### 多轮对话

Mooncake 实验在八张 H800 和八张 RDMA 网卡上运行 Qwen3-235B-A22B-Instruct-2507。80 个客户端进行 10 轮对话，每个请求新增 2,048 个输入 token、生成一个输出 token，用来近似 prefill/decode 分离中的 prefill 一侧。最后一轮，原图中仅 GPU 的 TTFT 约为 4.5 秒，L3 约为 0.8 秒。L3 命中率约为 90%，较小的缓存层则已丢失大量可复用历史。这些是从图中读取的近似值，不是公开的原始采样数据。

社区报告来自不同工作负载。Novita AI 在使用 3FS 的 Qwen3-Coder-480B 编程 agent 中，报告平均 TTFT 降低 56%、推理吞吐翻倍。蚂蚁集团在使用 Mooncake 的 DeepSeek-R1-671B 问答请求中，报告缓存命中相比完整重算降低了 84% 的 TTFT。两者都不是这两个后端之间的受控对比。
