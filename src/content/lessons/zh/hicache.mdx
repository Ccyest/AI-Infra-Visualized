## 背景

模型为读入的 token 计算 key 和 value，简称 KV。生成时，attention 通过这些 KV 读取前文。当另一个请求以相同的 token 前缀开头，SGLang 就能复用对应的 KV，只计算新增的后缀。这减少了 prefill 工作，也缩短了首 token 延迟，即 TTFT。

GPU 显存容量限制了这种复用。对话每一轮都在增长，更多客户端又带来更多历史。缓存满了以后，某段前缀可能刚被驱逐，下一个请求就需要它。SGLang 的 HiCache 用容量更大的存储层保留这些前缀。要让新增容量产生收益，恢复前缀必须比重新计算更划算，而且恢复的状态必须足以让模型从这个前缀继续执行。

HiCache 先接入 CPU 内存，再扩展到外部存储。后续工作把恢复范围扩展到混合模型和 draft 状态，并提出了让 host 内存只作传输缓冲的方案。时间线展示这些变化的背景，后文则沿着它们解决的工程问题展开。

## HiCache

### 设计与机制

把所有可复用前缀都留在 GPU 上，会挤占活跃请求所需的显存。因此，HiCache 把前缀的保存位置与模型的使用位置分开：GPU HBM 是 L1，CPU DRAM 是 L2，外部存储是 L3。Attention 仍由 GPU 执行，较低层保留原本会被丢弃的数据，cache controller 负责备份和加载。

<StorageLocationViz client:visible />

HiRadixTree 用 token 序列索引本地缓存。每个节点存一段 token，以及对应 KV 在 GPU 和 CPU 池中的索引。沿一条路径把 token 段连起来，就是共享前缀。L1 命中可以直接使用；L2 命中需要先分配 GPU 槽位，再从 CPU 搬运数据。本地副本缺失时，controller 可以用前缀派生的键查询 L3，把命中的页预取到 CPU 内存，再加载到 GPU。如果存储也未命中，SGLang 就通过普通 prefill 计算缺失的后缀。

<CacheTreeViz client:visible />

图中让一个服务实例依次处理五个请求。前缀 A 只计算一次，随后被备份。B 被 GPU 驱逐后仍留在 CPU 内存，被 CPU 驱逐后又能从外部存储取回，两次后续命中都不必重新计算 B。最后一个请求在存储中也未命中，因此需要 prefill。这就是分层设计带来的收益：GPU 驱逐不再必然终止复用。备份可以同时存在于多个层级，而本地未命中仍需查询存储，才能确定是否为 L3 命中。

### 工程问题纵览

分层设计提供了保留和恢复前缀的路径。要让这条路径真正有用，实现中还需要解决几类问题：

- **内存布局：** GPU 计算和存储 I/O 偏好的数据顺序不同，怎样让两段搬运都高效？
- **逐层加载：** 等全部层的 KV 到齐才计算会推迟执行，哪些传输可以与 GPU 计算重叠？
- **缓存策略：** 预取和备份都消耗时间、带宽与容量，什么时候值得等待，什么时候值得多存一份？
- **混合模型与 draft 状态：** token 匹配到了，所需历史状态却可能不完整，哪些数据必须随前缀一起恢复？
- **Host 内存：** 每个实例都有私有 L2 池，L3 已经保留历史时，host 还需要长期保存多少数据？
- **存储后端：** 不同系统的 I/O 实现各异，怎样共用 HiCache 的调度与恢复机制？

接下来每一节都对应 HiCache 中的一项实现问题。传输测量回答某段搬运是否更快，恢复测试回答所需状态是否保住，最后的整体基准再回答这些机制结合起来能带来多少服务收益。

### 内存布局

第一个问题是，怎样排列 KV 才能兼顾两种访问方式。模型逐层使用 KV，因此 GPU 采用 layer-first 布局。存储则按缓存前缀的页进行读写。如果 host 池照搬 layer-first 顺序，同一页的数据就会分散在各层，搬运一页需要处理多段零散的 I/O。

SGLang 把两侧的布局解耦。GPU 保留计算 kernel 所需的顺序，host 的 page-first 布局则把同一页在不同层的 KV 放在一起，让单次存储事务可以搬运更大的数据块。CPU–GPU 路径使用 GPU 辅助的 I/O kernel，host–存储路径再结合后端的 zero-copy 机制，避免中间拷贝。

<LayoutViz client:visible />

实测效果是两段搬运的吞吐都有提升：相比标准的 `cudaMemcpyAsync` 路径，GPU 辅助 kernel 的 **CPU–GPU 传输吞吐最高达到 3 倍**；page-first 布局结合 zero-copy，在典型部署中的 **host–存储吞吐最高达到 2 倍**。后一项测量的是布局与 zero-copy 的组合，不能单独归因于布局。这两个数字也都不是端到端服务加速比。数据来自 [2025 年 HiCache 博客](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/)。

### 逐层加载

搬运变快以后，传输仍然需要时间。如果 L2 命中要等整个模型的 KV 全部到齐，哪怕第一层的数据已经就绪，GPU 也无法开始工作。这里要解决的是请求关键路径上的传输等待。

HiCache 按层加载 KV。第 0 层就绪以后，GPU 执行这一层，controller 同时搬运后续层的数据。同步机制保证每层等到自己的 KV 就绪，但不要求它等待所有后续层。

<OverlapViz client:visible />

这样一来，部分传输可以在计算期间完成，请求有机会比“先全部加载、再开始计算”更早结束。它不会提高链路带宽，也无法消除第一次加载。如果传输跟不上计算，后续层仍会停下来等数据。动画用固定耗时展示这种依赖关系；原文没有提供该机制的独立加速比。

### 缓存策略

HiCache 还要决定什么时候值得搬运。读取时，等待缓存命中可能推迟请求；写入时，保存一段再也不会复用的数据又会浪费带宽和容量。预取与备份策略分别控制这两类成本。

#### 预取

存储延迟比 CPU–GPU 延迟更高，也更难预测。如果等 GPU 准备好才开始读取 L3，请求就必须直接承担这段等待。HiCache 因此在请求等待调度时，提前把存储中命中的页预取到 CPU 内存。

请求准备执行后，策略决定还要等多久。Best-effort 可以停止预取，复用已就绪的前缀，重新计算缺失部分。等待完成的策略倾向于保留更多复用机会，timeout 则为额外等待设置上限。

<PrefetchViz client:visible />

收益在于更早启动存储 I/O，并能控制剩余等待。读取在调度前完成，就能省去重算，也不必在准备执行时再等存储。如果读取晚于调度，只有省下的计算时间超过新增等待，继续等才划算。图中把前缀视为一个不可拆的块，真实请求可以复用较大传输中已完成的一部分。它展示的是这项取舍，不能据此认定某种策略始终最快。

#### 备份

较低层能命中，前提是此前做过备份。保存每段缓存可以保留更多复用机会，却也会为以后不再请求的前缀消耗带宽。容量较小的下层存储还可能被这些副本填满。

HiCache 提供三种策略，决定何时支付这笔成本：

| 策略 | 备份时机 | 主要取舍 |
| --- | --- | --- |
| Write-through | 主动备份已缓存的 KV | 保留更多数据，增加 I/O |
| Write-through-selective | 根据命中次数备份热点 | 减少 I/O，降低冷数据覆盖率 |
| Write-back | 延迟到较快层驱逐时再备份 | 减少提前备份的流量，在驱逐路径上增加工作 |

这些策略让部署可以用部分缓存覆盖率换取较低的传输与容量压力。带宽充足时，主动备份有利于保留历史；选择性备份则避免给每段冷数据都花带宽。延迟备份推迟了复制，但在数据必须离开较快层时增加工作。原文给出了这些机制，没有提供同条件下对三种策略的完整性能排名。

### 混合模型的状态

传输足够快，还要保证恢复的数据足够完整。混合模型给 HiCache 增加了正确性问题：普通 KV 可能已经覆盖某段前缀，另一种必需状态却仍然缺失。SGLang 因此扩展缓存表示与备份流程，把这些状态一起保留下来。

#### 复用边界

Full attention 需要可复用前缀的 KV。滑窗注意力需要复用边界处的尾部窗口。递归层则需要恰好位于该边界的 checkpoint。递归状态随 token 到来不断变化，不能把较晚的 checkpoint 简单截短，得到较早的状态。

SGLang 的 Unified Radix Cache 把这些组件记录在同一棵 token 树上，分别保存池索引、检查复用条件。只有所有必需组件都接受某个边界，才能从那里复用。HiCache 跨层备份和恢复各组件的数据，并带上关联的辅助 buffer。例如，Qwen3.5 需要递归状态，DeepSeek-V3.2 需要稀疏注意力的 indexer buffer。

效果是，恢复决策能够覆盖模型的完整需求。所需窗口或 checkpoint 缺失时，仅有 Full KV 命中不能授权复用。这让分层缓存可以扩展到混合模型；后面的多轮基准再测量保留这些模型历史所带来的收益。

#### 分支 checkpoint

完整恢复还要求保存初次备份之后新出现的状态。假设 host 已保存截至 P3 的 Full KV，以及 P3 处的递归 checkpoint S0。新请求从 P2 分支，并在那里生成 S1。S0 包含 P2 之后的 token，不能用于新分支。如果备份只检查节点是否已有 host 副本，就会跳过 S1，导致后续请求无法从 P2 继续执行。

SGLang 为新生成的 checkpoint 增加增量备份。已有 Full KV 留在原处，只需再传输 S1。因此，即使前缀的其他数据已经保存，备份流程仍会跟踪新出现的组件。

<StateRestoreViz client:visible />

恢复测试在两轮 GPU 驱逐之间创建分支状态。最终阶段中，完整恢复 6.4K 共享前缀的请求从 **1/10 增至 10/10**，token 命中率从 **15.74% 增至 64.00%**。每个请求还有 3.6K 独有后缀，因此 64% 就代表共享部分全部恢复。这个结果验证了测试所用 write-through 策略下的分支状态保留，不能据此认定 write-back 有相同效果。详见[分支备份测试](https://github.com/sgl-project/sglang/pull/33639)。

### Draft 状态恢复

投机解码又增加了一个使用前缀的模型。Draft 模型提出候选 token，target 模型负责验证，draft 也可能保存自己的 KV 或历史 buffer。如果 HiCache 只恢复 target KV，draft 就可能丢失历史，或者读到错误槽位。即使 target 成功命中缓存，后续解码的 draft 接受率仍可能下降。

SGLang 把配套的 draft buffer 加入 target 的缓存传输。布局兼容时，draft 数据打包进对应的 target host 池；其他布局则使用独立的 sidecar 池，索引跟随 target 的 KV 或滑窗索引。两条路径都会在 L2、L3 备份和恢复时带上关联的 draft 状态。

<DraftRestoreViz client:visible />

DSpark 测试在 DeepSeek-V4-Flash-0731 上，对同一批 200 个 prompt 做冷运行和 L3 恢复运行。改动前，恢复运行的接受率从 **46.77% 降至 33.57%**；改动后，冷运行和恢复运行分别为 **46.12% 和 46.86%**。恢复 draft 状态保住了缓存命中后 draft 的有效性，收益延伸到了 target KV 复用所节省的 prefill 之后。这里测量的是接受率，并非端到端吞吐。详见 [draft 恢复验证](https://github.com/sgl-project/sglang/pull/30393)。

### Host 内存作为缓冲

原始分层设计让 CPU 内存长期保留第二份缓存，L2 命中可以省去读取存储。但每个服务实例都有自己的 L2 池。多个实例可能各自保留 host 副本，同时又向共享 L3 备份。Host 内存较少时，即使 L3 已经保存了历史，长期保留这份工作集仍会带来容量压力。

Buffer-only 方案改变了 L2 的用途。备份经 host 缓冲写入 L3，预取经 host 缓冲加载到 GPU。一次操作完成并释放槽位后，后续传输就能复用这些空间。L3 负责长期保留历史，host 内存只保存中转数据。共享 L3 仍要求模型配置兼容；token 文本相同，不代表不同模型的 KV 可以互换。

<HostModeViz client:visible />

这个设计允许按正在进行的传输配置 host 容量，不必再容纳长期保存的第二份工作集。代价是失去持久 L2 命中，并可能增加 L3 流量；缓冲较小也会限制并发传输。[Buffer-only 提案](https://github.com/sgl-project/sglang/pull/34798)尚未提供基准数字，因此这里不量化内存节省或延迟收益。方案是否划算，取决于 L3 能否承担相应的复用流量。

### 存储后端

HiCache 还要接入查询、读写方式不同的存储系统。如果每接一个后端都重建调度和同步逻辑，每次集成都将变成一套独立的缓存实现。

SGLang 把这些存储操作放在统一的后端接口之后。后端负责键查询、读和写，中央 controller 负责调度与同步。2025 年的设计包括 Mooncake、DeepSeek 3FS、NIXL 和本地文件后端。NIXL 是连接其他存储系统的传输库，因此这四个后端并非四种等价的存储设备。

收益是共用同一条集成路径：后端只需提供存储访问能力，就能使用 HiCache 的缓存控制逻辑，不必重新实现。这扩大了部署时的选择范围。实际吞吐仍取决于具体后端与传输路径，下面的基准会说明各自使用了哪种后端。

## 整体效果

前面的实现分别处理了搬运成本、调度、完整恢复与内存使用。接下来要回答的是：面对真实容量压力，保留更多前缀能否改善服务性能？下面在每种负载内部比较缓存层级。它们测量的是整套配置，因此不能把收益单独归因于某一种布局、策略或状态恢复改动。

### 长上下文 · 2025

原文的 LooGLE 测试验证较低层缓存能否减少长输入的重复 prefill。它在八张 H20-3e 上运行 DeepSeek-R1，比较仅 GPU 缓存、增加 CPU L2、增加 3FS L3，以及单独预先填充 L3 的情况。图中可以查看平均 TTFT 和输入吞吐。

<ResultsViz client:visible />

普通 L3 的输入吞吐为 51,168 tokens/s，平均 TTFT 为 1.83 秒。预先填充 L3 后，结果为 76,322 tokens/s 和 1.43 秒，但预热条件已经改变。这两组 L3 结果因此对应不同的可用缓存量。这个对比说明，除了传输速度，历史是否保留、请求到来时缓存是否可用，也影响最终收益。

### 混合模型多轮对话 · 2026

多轮对话提供了不断增长的工作集：每一轮都新增后续请求可能复用的历史。2026 年 8 月的测试比较 GPU L1、L1 加 CPU L2，以及再加 500 GiB Mooncake L3。DeepSeek-V4-Flash 使用 FULL 与 SWA，Inkling-Small 使用 FULL、SWA 与 MAMBA。每种模型的硬件和负载配置不同，因此应在模型内部比较缓存层级。

<MultiTurnBenchViz client:visible />

L1 最先丢失可复用历史，L2 推迟了容量上限出现的时刻。相比仅 L1，增加 L3 后，DeepSeek-V4-Flash 的有效输入吞吐从 9.4K 增至 145.5K tokens/s，缓存命中率保持在约 98%。Inkling-Small 从 15.5K 增至 67.1K，最终命中率为 96.8%。结果表明，当混合模型的对话历史超过较小缓存的容量时，较低层仍能保住复用机会。详见[多轮基准](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/)。

缓存复用场景下，输入吞吐把已缓存的输入 token 也计入服务处理进度。它衡量单位时间内服务处理了多少输入，并非 GPU 为每个 token 新计算 KV 的速度。这里更高的吞吐主要来自避免重复工作。

## 总结

HiCache 把可复用前缀的保存时间延长到了 GPU 显存之外。各项工程选择让新增容量真正可用：布局和加载方式减少搬运开销，策略控制何时值得做 I/O，组件与 draft 恢复保住所需的完整状态，host 缓冲与后端选择则让同一套分层机制适应不同部署资源。

当省下的 prefill 工作超过恢复成本，而且较低层保住了原本会丢失的历史，系统就能获得整体收益。长输入和不断增长的对话基准验证了这种效果。具体部署仍需同时考察命中率、传输成本和状态完整性，才能判断分层缓存对 TTFT 与吞吐的实际帮助。
