> **TL;DR** K3 把 93 层里的 69 层换成 KDA 线性注意力，KV cache 只剩 24 层在涨；
> 深度方向加 AttnRes，FFN 全部换成 896 选 16 的 LatentMoE。这套架构落到
> serving 栈，很多默认假设不再成立：SGLang 的 day-0 支持是显存改统一池，
> prefill 改 chunked PP，decode 改 DCP，再配合投机解码 DSpark。

## 先算账：1M token 的 KV cache

基本盘：2.8T 参数、104B 激活、93 层、原生 1M 上下文、权重 MXFP4、原生视觉
(MoonViT3d)。其中"1M 上下文"直接把"93 层全用 softmax attention"这条路
堵死了：按 MLA 压缩后 27 KB/token(24 层合计)的口径线性外推，93 层全 MLA
在 1M token 时一个请求要占约 110 GB，这还没算未压缩 MHA 那个数量级。

K3 的选择：93 层 = 69 层 KDA + 24 层 MLA，按 3 KDA + 1 MLA 交错。KDA 层是
线性注意力，状态固定大小(整机约 0.4 GB/请求)，每步原地覆写；MLA 层保留
全局 attention，并且不加 RoPE(NoPE)，位置感由 KDA 的递归天然携带：

<CacheViz client:visible />

24 层 MLA 在 1M 时约 28 GB，是全 MLA 假想值的 1/3.9。计算侧同理：softmax
attention 每生成一个 token 都要扫全部历史(O(N))，KDA 每步只碰固定状态
(O(1))。

## KDA：固定大小的状态怎么记东西

线性注意力把 attention 里的 softmax 去掉，让乘法可以重新结合：历史全部压进
一个固定大小的矩阵 S(每 head 约 128×128)，写入是 `S += k·vᵀ`，读出是
`qᵀ·S`。每步 O(1)，但"只加不减"：同一个键方向写第二次，新旧值就叠在一起，
查询读出来的是混合物。

DeltaNet 把写入换成 delta rule：先用 k 读出旧值、按写入强度 β 擦掉，再写
新值，`S_t = (I − β·k·kᵀ)·S_{t−1} + β·k·vᵀ`。这等价于对"S·k 应该等于 v"
做在线梯度下降，换绑正确了。但状态仍然只进不出：写进去的键永远占着有限的
维度，上下文一长，读出的串扰越积越多。

Gated DeltaNet 补上遗忘门，每个 head 一个标量：要忘一起忘。KDA 把它细化成
逐通道的对角门，`S_t = (I − β·k·kᵀ)·Diag(a_t)·S_{t−1} + β·k·vᵀ`，a_t 由
当前输入算出，每个通道有自己的遗忘速率。Kimi Linear 论文把这读作一种可学习
的位置编码：RoPE 的固定旋转，换成数据依赖的衰减。配套的 chunkwise kernel
在受约束的 DPLR 形式下比通用算法快约一倍，这是它能铺满 69 层的前提。

## 深度方向：Attention Residual

残差流是 transformer 的信息干线：每层从里面读、往里面加，一路传到底。93 层
共用一条干线，所有中间表征都要挤过同一个向量；深层想精确用到浅层的某个
表征，只能指望它没被沿途几十次加法淹掉。

AttnRes 给深层开了第二条路：每 12 层一组，用学到的 pseudo-query 对
embedding 和之前所有组的输出算注意力权重 α，按权重取回，汇入当前表征。
取回是选择性的，要哪组拿哪组，而不是什么都沿着一条流累加：

## FFN：896 选 16 的 LatentMoE

FFN 侧全部是 MoE：896 个 routed expert 每 token 选 16 个，外加 2 个常驻的
shared expert。激活率 16/896 ≈ 1.8%，整模型每 token 激活 104B/2.8T ≈ 3.7%
的参数(K2 是 384 选 8，K3 把稀疏度又推进了一档)。

路由和分发的位置也变了：不在 7168 维 hidden 上做，而是先降到 3584 维的
隐空间，router 在半宽向量上打分，expert 也在半宽上计算，最后再升回来。
16 份 dispatch 的 all-to-all 流量和 expert 权重体积因此都省一半：

<MoeViz client:visible />

在 1.8% 的激活率下把训练稳住靠三件事：RMSNorm、有界的 SiTU-GLU 激活，以及
Quantile Balancing：expert 配额直接从 router 分数的分位数导出，不再有
aux-loss 那个敏感系数要调。

## 训练侧的几件事

- 量化感知训练从 SFT 阶段开始，MXFP4 权重 + MXFP8 激活，发布即低精度；
- 优化器是 Per-Head Muon：Muon 按 attention head 独立做正交化更新；
- 1M 上下文按课程拉长：8K → 64K → 256K → 1M；
- RL 覆盖 general、agentic、coding 三个域和多档 reasoning effort；工具、
  prompt、memory、subagent 这些 scaffold 在训练中持续变化，避免模型绑死在
  单一工作流上。

## 从架构到 serving：两种状态

上面的架构落到推理栈里，第一个直接后果是两种性质不同的推理状态：

| | MLA(24 层) | KDA(69 层) |
| --- | --- | --- |
| 状态形式 | KV cache，逐 token 追加 | 递归状态，固定大小 |
| 增长方式 | 每 token 约 27 KB，只增不减 | 每请求约 54 MB(TP=8)，每步原地覆写 |

KV 逐 token 追加、按页共享这些默认假设对 KDA 统统不成立，SGLang 的
day-0 适配从这里开始。

## 双状态显存管理

旧方案在启动时把显存池按预估切成 KDA 区和 MLA 区。问题是 KDA 需求只跟并发数
相关，MLA 需求跟总上下文长度相关，负载一偏就会一侧耗尽、另一侧闲置。SGLang
改成统一池：KDA 固定块从左端分配，MLA 页从右端分配，中间是一段连续的空闲区，
按需取用：

<PoolViz client:visible />

注意 t=14：静态双池的 MLA 区耗尽，R2 生成到一半被驱逐，而 KDA 区还空着 6 页。
统一池在同一时刻没有任何失败。

前缀缓存(radix tree)这边，KDA 状态会被原地覆写，不能像 KV 那样直接共享。
SGLang 用三个操作管理它：copy-on-write(使用共享 checkpoint 前先拷到私有槽)、
snapshot(乒乓缓冲抓快照)、donate(按槽位索引捐给 radix tree)。整套设计
按构造无竞态，细节见文末博客。

## Chunked pipeline prefill

TP8 让 8 张卡合算同一个 chunk，但每层都要 AllReduce，通信在关键路径上。
chunked PP8 把模型按层切成 8 段，prompt 切成 chunk 依次流过各段，P2P 交接
藏在下一个 chunk 的计算后面(实测 91% 被隐藏)：

<PipelineViz client:visible />

预热气泡只付一次，稳态每 2 列出一个 chunk。实测 PP8 prefill 吞吐是 TEP8
节点的 1.45–1.72×(TEP = tensor + expert 并行，图中简化为纯 TP 作对照)。

## Decode context parallelism(DCP)

decode 阶段的瓶颈是显存：TP 下每张卡都存一份完整 KV。DCP 按 token 位置取模
分片，rank r 只存 `position mod N = r` 的 KV；每步 decode 先本地算局部
attention，再用一次 all-to-all 交换部分结果，log-sum-exp 合并后与单卡输出
一致：

<DcpViz client:visible />

K3 上的实测：DCP8 把逻辑上下文容量放大 7.9×；长 agent 会话下 TP8 在 16 个
并发 session 崩掉，DCP8 撑到 48 个，总吞吐 541 tok/s。KDA 状态没有位置轴，
KDA 层仍按 TP 切分，所以混合架构的并行策略也是按层混合的。

## 单卡数字

投机解码介入之前，BS=1 解码靠四类手段从 63.8 tok/s 提到约 113 tok/s
(括号内为博客给出的单项增益)：

| 类别 | 代表手段 |
| --- | --- |
| 启动开销消除(+19.9 tok/s) | MoE 前段合成单个 GEMM、KDA 投影合并、寄存器内路由 |
| 专用 kernel(+10.3) | 融合 KDA decode、W4A8 MoE、TMA 聚合 attention residual |
| 通信融合(+27.6) | 融合 all-reduce：multicast + NVLS 在交换机内归约，顺路做 residual/RMSNorm |
| 重叠与前奏(+10.4) | GEMV-GEMM 重叠、residual 写回融合、PDL 预热 attention |

在此之上，DSpark 投机解码把 BS=1 提到约 423 tok/s(约 3.7×)。

组合的 serving 边界：PP8 prefill + TP8 decode 达到 2,808 tok/s/GPU(fp4)；
交互式配置可以换到 116+ tok/s/用户。博客里值得记住的一句：

> AllReduce 是同步点，在那里省 1 微秒，步时就省 1 微秒；
> 藏在别的 stream overlap 里的 kernel，只值大约十分之一。
