> **一句话**:K3 在 attention、MoE、量化上同时偏离常规,serving 栈里所有
> "想当然"逐个失效。SGLang 的 day-0 支持 = 显存(统一池)、prefill(chunked
> PP)、decode(DCP)三条战线同时重写,外加投机解码 DSpark。

## K3 长什么样(60 秒)

- **2.8T 参数**,1M token 上下文,首个 3T 级开源模型;
- 93 层里 **69 层是 KDA 线性注意力,24 层是 MLA**,交错排布;
- **LatentMoE**:896 个 expert、top-16 路由,在 3584 维隐空间里做;
- 权重原生 **MXFP4**,视觉塔 MoonViT3d。

对 serving 最要命的是第二条:两种 attention 意味着**两种性质完全相反的推理状态**——

| | MLA(24 层) | KDA(69 层) |
| --- | --- | --- |
| 状态形式 | KV cache,逐 token 追加 | 递归状态,固定大小 |
| 增长方式 | 每 token 约 27 KB,只增不减 | 每请求约 54 MB(TP=8),每步**原地覆写** |

## 挑战一:两种状态,一池显存

旧方案在启动时把显存池按猜测切成两半。可 KDA 需求只看**并发数**,MLA
需求看**总上下文长度**——负载一偏,一侧饿死、另一侧闲置。SGLang 改成统一池:
KDA 固定块从左端进,MLA 页从右端进,中间始终是一段连续空闲区,谁需要谁拿:

<PoolViz client:visible />

注意 t=14:静态双池的 MLA 区耗尽,R2 生成到一半被驱逐——而 KDA 区还空着 6
页。统一池同一时刻风平浪静。

前缀缓存(radix tree)一侧,KDA 状态会被原地覆写、不能像 KV 那样直接共享,
SGLang 用三个操作把它管起来:**copy-on-write**(用共享 checkpoint 前先拷到私有
槽)、**snapshot**(乒乓缓冲抓快照)、**donate**(按槽位索引捐给 radix tree)。
按构造即无竞态,细节见文末博客。

## 挑战二:prefill 拆层流水,甩掉 AllReduce

TP8 让 8 张卡合算同一个 chunk,但每层都要 AllReduce——通信横在关键路径上。
chunked PP8 反过来:模型按层切成 8 段,prompt 切成 chunk 依次流过,P2P
交接藏在下一个 chunk 的计算后面(实测 91% 被隐藏):

<PipelineViz client:visible />

预热气泡只付一次,稳态后每 2 列出一个 chunk。SGLang 实测:PP8 prefill
吞吐是 **TEP8 节点的 1.45–1.72×**(TEP = tensor + expert 并行;图中简化为
纯 TP 作教学对照)。

## 挑战三:decode 把 KV 按位置分片(DCP)

Decode 阶段的痛点不是算力是显存:TP 下每张卡都存一份完整 KV。DCP 改成按
token 位置取模分片——rank r 只存 `位置 mod N = r` 的那些 KV,查询时本地算
局部 attention,再用一次 all-to-all 合并(log-sum-exp 保证数值与单卡一致):

<DcpViz client:visible />

K3 实测:DCP8 把逻辑上下文容量放大 **7.9×**;跑 agent 长会话时,TP8 在 16
个并发 session 就崩,DCP8 撑到 **48 个 @ 541 tok/s**。注意 KDA 状态没有
"位置"这个轴,所以 KDA 层仍按 TP 切——混合架构连并行策略都要按层混合。

## 一张 GPU 能跑多快(数字速览)

在投机解码介入之前,BS=1 解码靠四类手段从 **63.8 tok/s** 推到 **~113 tok/s**
(括号内为博客给出的单项增益):

| 类别 | 代表手段 |
| --- | --- |
| 启动开销消除(+19.9 tok/s) | MoE 前段合成单个 GEMM、KDA 投影合并、寄存器内路由 |
| 专用 kernel(+10.3) | 融合 KDA decode、W4A8 MoE、TMA 聚合 attention residual |
| 通信融合(+27.6) | 融合 all-reduce 家族:multicast + NVLS 在交换机内做归约,顺路加 residual/RMSNorm |
| 重叠与前奏(+10.4) | GEMV-GEMM 重叠、residual 写回融合、PDL 预热 attention |

在此之上,DSpark 投机解码把 BS=1 再拉到 **~423 tok/s**(约 3.7×)。

组合的 serving 边界:PP8 prefill + TP8 decode 达到 **2,808 tok/s/GPU**(fp4);
交互式配置可换到 **116+ tok/s/用户**。博客里最值得背下来的一句:

> AllReduce 是同步点——在那里省 1 微秒,步时就省 1 微秒;
> 藏在别的 stream overlap 里的 kernel,只值大约十分之一。
