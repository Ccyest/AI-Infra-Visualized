## 背景

Prefix caching 在请求共享同一段 token 前缀时复用 KV。在 full attention 下规则很简单。KV 只随新 token 追加，共享的 token 可以直接复用，所以只需要计算后到的那部分 token。

混合模型打破了这条单一规则。一个请求可能同时携带 full attention KV、滑动窗口 KV 和递归状态。Full attention KV 在整条匹配前缀上都可复用。滑动窗口 KV 只覆盖尾部窗口。递归状态逐 token 就地覆写，只在精确的 checkpoint 处有效。强行给三者定一个统一边界，要么丢掉本可复用的，要么复用了不该复用的。

<ReuseRuleViz client:visible />

这些规则在不同模型家族里以不同组合出现。DeepSeek-V4 是 FULL 加 SWA。Kimi-K3 为它的 KDA 递归状态组合 FULL 加 MAMBA。Inkling 三种全有。给每种组合写一个专门缓存类，会产生组合爆炸的类矩阵。早期实现正是这个模式，重复逻辑到处都是。统一的前缀缓存因此成了迫切的任务。

## Unified Radix Cache

### 设计与机制

Unified Radix Cache 只给 radix tree 加了一件事：每个节点上给每种组件留一个槽位。FULL 的槽存这段 token 的 KV 页号，缓存过的路径上每个节点都有。SWA 的槽存窗口槽号，只有落在尾部窗口内的节点才有；更早的节点上是一个空的 tombstone。MAMBA 的槽存 checkpoint 的位置，即「读完到这个节点为止的全部 token」时的递归状态；只有真正存过 checkpoint 的节点上才有。

<TreeReplayViz client:visible />

### 安全复用边界

匹配时，core 沿 FULL 的规范路径走查，每个经过的节点都是候选边界。每个在场组件通过自己的 validator 投票，只有所有 validator 都接受，边界才推进。某个节点被否决不会终止走查，因为组件可能接受更深的节点。以长前缀上的 SWA 为例：靠前的节点已经滑出尾部窗口，窗口槽位只剩 tombstone，SWA 否决它们；最后几个节点尾部窗口完整，SWA 在那里接受。要是第一次被否决就停下，这个更深的边界就被扔掉了。

<BoundaryVoteViz client:visible />

这就是三种复用规则不需要三棵树的原因。树只按 token 走：走到哪个节点，就说明前缀匹配到了哪里。这个节点上的数据能不能用，是各组件自己的问题，各自查自己的槽位。有数据就是能用；是 tombstone 或者根本没存过就是不能用。SWA 还要多查一步尾部窗口是否完整，上面的例子正是这样。

## 跨层 HiCache

组件决定「什么能复用」，HiCache 决定「可复用的 payload 放在哪」。Unified Radix Cache 让同一个组件身份贯穿 GPU L1、Host L2 和外部 L3 层。数据在层间搬运，不改变前缀身份，也不改变复用规则。

<TierFlowViz client:visible />

节点槽位里存的是池内页号，节点的键是 token 序列本身。L1 吃紧时，controller 把页拷到下一层，释放设备页，把新位置记到节点上。节点不删，树仍然知道这段前缀存在、在哪一层。匹配只读树。真正复用时才读槽位：还在 L1 的页直接用；在更低层的页，先申请新的设备页，把数据拷进来，再把新页号写回槽位。DeepSeek-V4 里，FULL 和 SWA 是组件，索引空间彼此独立：在博客归一化的六页例子里，同一段 token 在 FULL 是尾页 F4、F5，在 SWA 池里是 S0、S1，由分配器在运行时翻译。而 C4、C128 两个压缩 KV 池，加上 indexer buffer 和 compressor state，共五个辅助池注册为 sidecar：三个跟随 FULL，两个跟随 SWA。组件之间翻译索引，sidecar 直接抄号。

### 多轮对话基准

多轮负载每一轮都在增长可复用的对话前缀。问题是 GPU 容量耗尽后，更低的层能不能把前缀留住。下面是两个混合模型、三种存储分层的对比。

<MultiTurnBenchViz client:visible />

可以看到，DeepSeek-V4-Flash 上 L3 让命中率接近 98%，平均 TTFT 低于 9 秒，有效输入吞吐 145.5K tokens/s，仅 L1 时是 9.4K。Inkling-Small 上是 96.8% 和 67.1K。

## 会话感知驱逐

LRU 记得哪些条目最近被访问过，却完全没有会话层面的上下文。内存吃紧时，它可能扔掉活跃会话的 KV，却留着不相干的条目。会话感知驱逐补上这个信号。应用给每个请求带上稳定的 `session_id`。调用 `/close_session` 会移除该会话的引用，但不立刻删除条目。会话关闭后，缓存优先驱逐这个 `session_id` 的条目，而不是按普通 LRU 顺序。

<SessionEvictViz client:visible />

### SWE-bench 结果

在启用 HiCache 的 SWE-bench agent 轨迹上，会话感知配置把 DeepSeek-V4-Pro 的 TTFT 降低 11.0% 和 2.9%（batch 128 与 256），把 Qwen3.5-397B-A17B 降低 13.5% 和 16.6%（batch 32 与 64）。device 命中率也在涨：DeepSeek-V4-Pro 在 batch 128 从约 42% 升到 51%，Qwen 在 batch 32 从约 5% 升到 34%。基线是普通 HiRadixCache 加 LRU。对照组同时启用 Unified Radix Cache 和 `--enable-session-radix-cache`，所以这些差值不是会话感知的单一变量消融。

## Rust 树核

树核跑在 scheduler 的 CPU 关键路径上：每个请求都要付出走查、锁记账、LRU 更新等开销。Python 是解释执行的语言，类型和属性都在运行时才解析：每次访问都要经过解释器分发、属性查找和引用计数。Rust 则是编译语言，类型和字段偏移在编译期就定死，同一步变成紧凑结构体上的几条指令。所以实验性原型用 Rust 重建同一套状态机，opt-in、仅 L1：Rust 拥有 radix 拓扑、锁记账、侵入式 LRU 链表和驱逐走查，Python 保留 request 到 token 映射和物理 KV 分配，按 Rust 返回的 deferred actions 操作池。

<RustSplitViz client:visible />

在 200 轮合成对话上对比 Python 树，树开销占比越高的地方 TTFT 降得越多：SWA 负载降 38%（第 176–200 轮降 42%），全注意力降 10%（最后 25 轮降 18%），混合 SSM 降 5%（7%），后者更大的 GPU forward 把变化盖住了大半。后续的 RFC #32710 把编排和池管理留在 Python，树核可替换。
