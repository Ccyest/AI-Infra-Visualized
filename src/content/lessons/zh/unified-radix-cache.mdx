## 背景

Prefix caching 在请求共享同一段 token 前缀时复用 KV。在 full attention 下规则很简单：KV 只随新 token 追加、从不改写历史，所以共享前缀一旦算过就一直有效，后来的同前缀请求可以跳过这部分 prefill。SGLang 用一棵以 token 序列为键的 radix tree 维护这个映射；prefill 之前，树返回最长可复用前缀和它的 KV 位置。

混合模型打破了这条单一规则。一个请求可能同时携带 full attention KV、滑动窗口 KV 和递归状态——同一段 token 前缀，三种复用语义。Full attention KV 在整条匹配前缀上都可复用；滑动窗口 KV 只覆盖尾部窗口；递归状态因为逐 token 就地覆写，只在精确的 checkpoint 处有效。强行给三者定一个统一边界，要么丢掉本可复用的，要么复用了不该复用的。

<ReuseRuleViz client:visible />

这些规则在不同模型家族里以不同组合出现：DeepSeek-V4 是 FULL 加 SWA，Kimi-K3 为它的 KDA 递归状态组合 FULL 加 MAMBA，Inkling 三种全有。给每种组合写一个专门缓存类会产生组合爆炸的类矩阵，HiCache 这类正交能力再把它翻倍。早期实现正是这个模式，matching、插入、加锁、驱逐逻辑在各个缓存变体里各复制一份。

## Unified Radix Cache

### 设计与机制

这棵树在「能不能复用」这件事上是故意装傻的。它的拓扑只由 token 序列决定，给每段前缀一个唯一的规范坐标——它做的就只有这件事。每种复用规则以组件 payload 的形式挂到节点上：FULL KV 铺满缓存路径的每个节点；SWA 窗口槽只存在于尾部附近，更早的节点上可以是空 tombstone；MAMBA checkpoint 只出现在真正存过状态的节点上。空槽位是正常状态而不是错误，共享前缀的两个请求共享同样的节点，与它们的模型跑哪几种组件无关。

<TreeAnatomyViz client:visible />

一棵树之所以能同时伺候三种复用规则，就是因为规则活在组件里、不活在拓扑里。树从不回答「这段能不能复用」——它只提供坐标和挂载点，复用与否由匹配时各组件逐一回答，也就是下一节的投票。这也是新模型不需要新树的原因：DeepSeek-V4 挂 FULL 和 SWA 的 payload，Kimi-K3 挂 FULL 和 MAMBA，Inkling 三种都挂，拓扑一模一样。

落到代码上，UnifiedTreeCore 负责所有树都需要的公共机制——匹配、分裂、插入、加锁、驱逐——UnifiedRadixCache 负责池操作的编排，TreeComponent 只定义真正因规则而异的语义。FULL 永远在场，保护匹配到的祖先路径。SWA 要求一段连续的尾部窗口。MAMBA 还多一条规则：递归状态每读一个 token 就地覆写自己，树里存的状态不能直接交给请求用——两个请求推进同一份活状态会互相写坏。所以树里只存只读 checkpoint，命中后先把 checkpoint 拷贝进请求私有槽位，改动只发生在拷贝上。这套 copy-on-write 在 KDA 状态上的逐步走查见 [Kimi K3 那一课](https://yichizhang.dev/AI-Infra-Visualized/lessons/kimi-k3-day0-support/)。

### 安全复用边界

匹配时，core 沿 FULL 的规范路径走查，每个经过的节点都是候选边界。仅有 FULL 匹配并不够：每个在场组件都会创建一个 validator，只有所有 validator 都接受，边界才推进。某个节点被否决不会终止走查，因为组件可能接受更深的节点——SWA 可以否决窗口槽位已是 tombstone 的节点，又接受更深处、尾部窗口完整的那个。

<BoundaryVoteViz client:visible />

走查结束后 core 构建 MatchResult，各组件的 finalizer 把选中的值准备好供复用——包括上面说的那次 checkpoint 拷贝。

### 生命周期钩子

同一套组件契约覆盖树生命周期的其余部分：

| 生命周期 | 组件决定什么 |
| --- | --- |
| Match | `create_match_validator` 接受或否决候选边界；finalizer 准备选中的结果 |
| Split | `redistribute_on_node_split` 决定 radix 节点分裂时组件数据怎么走 |
| Insert | `update_component_on_insert_overlap` 与 `commit_insert_component_data` 决定组件拥有哪些池索引 |
| Lock | `acquire_component_lock` / `release_component_lock` 保护一条路径、一段尾部窗口或一个 checkpoint |
| Evict | `evict_device_start` / `next_node` / `end` 挑选设备侧候选；`evict_component` 移除数据；`drive_host_eviction` 回收主机内存 |

移除某个组件的 payload 不一定移除 radix 节点：剩下的拓扑还可以锚定其他组件，空槽位以 tombstone 的形式留着，直到 payload 恢复或节点不再需要。正因为组件语义始终挂在同一个前缀身份上，HiCache 才能把 payload 扩展到多级存储，而不用再引入一棵树。

## 跨层 HiCache

组件决定「什么能复用」，HiCache 决定「可复用的 payload 放在哪」。Unified Radix Cache 让同一个组件身份贯穿 GPU L1、Host L2 和外部 L3 层，数据在层间搬运不改变前缀身份、也不改变复用规则。组件描述需要的传输，HybridCacheController 执行物理 I/O。

也不是每个物理池都要当组件。Anchor 定义复用语义、或者供出页索引给其他池跟随；sidecar 存放独立的 payload，但精确复用它声明的来源池的索引，跟着来源池一起搬家，不参与边界投票，也不在拓扑上新增槽位。DeepSeek-V4 把这个区分落到实处：FULL 和 SWA 都是组件，各有独立的设备索引空间——在博客归一化的六页例子里，分配器把 FULL 尾槽 F4、F5 映射到 SWA 槽 S0、S1——而 C4、C128 压缩 KV 池、indexer buffer 和 compressor state 注册为 sidecar，三个跟随 FULL、两个跟随 SWA。

### 多轮对话基准

多轮负载每一轮都在增长可复用的对话前缀；问题是 GPU 容量耗尽后，更低的层能不能把前缀留住。博客在两个混合模型上比较三种配置：仅 GPU L1、L1 加 Host L2、以及再加一个 500 GiB Mooncake Store 作为外部 L3。

<MultiTurnBenchViz client:visible />

两个负载里都是 L1 最先丢失可复用前缀，L2 推迟容量上限，L3 在预热后一直保持高位：DeepSeek-V4-Flash 上命中率接近 98%、平均 TTFT 低于 9 秒、有效输入吞吐 145.5K tokens/s（仅 L1 时是 9.4K）；Inkling-Small 上是 96.8% 和 67.1K。关于口径说明一句：有效输入吞吐是完整 prompt 长度之和除以墙钟时间，命中的前缀 token 也计入——它衡量的是前缀复用下的服务进度，不是原始 prefill 算力。

## 会话感知驱逐

LRU 记得哪些条目最近被访问过，但不知道哪些前缀属于下一轮还会回来的会话。内存吃紧时，它可能扔掉活跃会话的 KV，却留着不相干的条目。会话感知驱逐补上这个信号：应用给每个请求带上稳定的 `session_id`，请求成功结束后，Unified Radix Cache 登记该会话的可复用区域——FULL 记它的前缀路径，SWA 记尾部窗口，MAMBA 记可复用前沿。

这些引用只改变驱逐顺序，从不 pin 内存。FULL 按是否被引用、会话引用计数和基础优先级排序候选；SWA 和 MAMBA 先扫无引用的条目，空间还不够时回退到有引用的。当前策略覆盖 GPU L1 和 Host L2，不含外部 L3。调用 `/close_session` 移除会话引用但不立刻删除条目；会话代数（generation）加上有界的已关闭会话 tombstone，防止关闭或重开之后才完成的过期请求把已释放的引用又挂回去。

### SWE-bench 结果

在启用 HiCache 的 SWE-bench agent 轨迹上，会话感知配置把 DeepSeek-V4-Pro 的 TTFT 降低 11.0% 和 2.9%（batch 128 与 256），把 Qwen3.5-397B-A17B 降低 13.5% 和 16.6%（batch 32 与 64）；device 命中率最多从约 42% 升到 51%、从 5% 升到 34%。基线是普通 HiRadixCache 加 LRU，对照组同时启用 Unified Radix Cache 和 `--enable-session-radix-cache`，所以这些差值不是会话感知的单一变量消融。

## Rust 树核

随着共享前缀变长，树的走查、锁记账、LRU 更新和驱逐扫描都压在 scheduler 的关键路径上。把树状态机从缓存编排里拆出来之后，树核自然成了原生实现的目标。实验性 Rust 原型是 opt-in、仅 L1 的：Rust 拥有 radix 拓扑、每组件的锁记账、侵入式 LRU 链表和驱逐走查，Python 仍是 request 到 token 映射和物理 KV 分配的唯一所有者。树变更之后，Rust 返回 deferred actions，由 Python 应用到池上。

<RustSplitViz client:visible />

在 200 轮合成对话上对比 Python 树，原型在树开销占比越高的地方降得越多：SWA 负载 TTFT 降 38%（第 176–200 轮降 42%），全注意力降 10%（最后 25 轮降 18%），混合 SSM 降 5%（7%）——后者更大的 GPU forward 把变化盖住了大半。这些数字背后的残差——总 TTFT 减去 CUDA event 计时的 GPU prefill——还包含调度、采样、detokenize 等未打点的工作，不是 CPU 时间的直接测量。后续的 RFC #32710 定义了目标所有权边界：编排和池管理留在 Python，树核可替换。

## 后续工作

系统里还有三块要向这个共享前缀身份收敛：

- 补完可替换的 Rust 树核（roadmap #20415）：把它扩展到 SWA、MAMBA 和 HiCache，池分配和编排继续留在 Python。
- 让 GPU L1 直连外部 L3，把 Host L2 变成可选的暂存层。这需要协同的准入、预取、传输和驱逐，而不只是再接一个存储后端。
- 在整个 serving 栈上协同 agentic KV 缓存（roadmap #21846）：把同一套缓存身份扩展到 router、prefill/decode worker 和 HiCache，让会话、子 agent 和工具调用共享预取与保留决策。
